# MCP for Cloud — Technical documentation

Português (Brasil): [README.pt-BR.md](README.pt-BR.md)

Version for **Nextcloud 32 to 35** (`info.xml` declares 32–35; the API contract has fixtures for 31 to 35, and 31 is still checked without being declared). The endpoint serves MCP 2026-07-28 clients, stateless, through `server/discover` and per-request `_meta`, and also earlier clients, which use `initialize` with 2025-06-18. It exposes MCP `2025-06-18` over sessionless Streamable HTTP without SSE, on the app's own route:

- `https://<instance>/apps/mcp/` with clean URLs;
- `https://<instance>/index.php/apps/mcp/` without clean URLs.

The exact URL of the instance appears on the administration and personal pages.

## What's new in 1.3.3, 1.3.2, 1.3.1 and 1.3.0

- **1.3.3: fixes for scanned PDFs, failure logs and calendar plans.** PDFs made searchable by ocrmypdf with Tesseract now return their existing text layer ([#31](https://github.com/sintax-tech/mcp-for-nextcloud/issues/31)). Unexpected tool failures identify the tool and exception class and code in the Nextcloud log, without private exception messages or traces. Calendar collision warnings work without Intl and keep the start visible for an invalid interval; zero-duration overlaps show the time once. Calendar plans and DAV use the same invitation setting reader for string, boolean and lazy values. No database change.
- **1.3.2: fixes for file writes.** `files_version_restore` of the current version no longer fails (with file locking it answered not found, without it a write failure). When `files_version_restore`, `files_edit`, `files_replace` or a `files_checkout` upload fails after the pre-write copy, the answer now says where the copy is, and a file that became hidden in the meantime gets only "Resource not found in Nextcloud.", without its folder or name. `collectives_remove_member` no longer answers `partial` for a removal that Teams applies in the background. No database change.
- **1.3.1: fix for HTML mail drafts ([#30](https://github.com/sintax-tech/mcp-for-nextcloud/issues/30)).** On servers with libxml2 2.14 or later (Ubuntu 25.10 and 26.04, Debian testing), every `mail_create_draft` call with `html: true` was refused; it now works there. A loose `&` ("A & B", "AT&T", a link with `?a=1&b=2`) is kept as text instead of refusing the draft, and HTML that libxml versions read differently is refused with the same message on every server. No database change.

The app is organized into capability modules, following the architecture proposed by @marcjoancr in [#14](https://github.com/sintax-tech/mcp-for-nextcloud/pull/14).

- **Tables schema and sharing ([#1](https://github.com/sintax-tech/mcp-for-nextcloud/issues/1)):** create/update tables, columns and views with `tables.schema`, and share/revoke user/group access with `tables.share`. Supported APIs include Tables 2.4.0, preserving view layouts and card sources.
- **Forms structure ([#1](https://github.com/sintax-tech/mcp-for-nextcloud/issues/1)):** add, reorder or delete questions/options and change supported question types. These actions use the existing `forms.edit` grant; review existing grants.
- **Polls writing ([#1](https://github.com/sintax-tech/mcp-for-nextcloud/issues/1)):** manage settings, state, options, shares and individual invitations with separate grants and native editing rights. No voting tool is exposed.
- **Collectives ([#22](https://github.com/sintax-tech/mcp-for-nextcloud/issues/22)):** read/search pages, create empty pages, edit Markdown and move/rename pages. On NC33–35, separate grants also support collective creation and member management.
- **Calendar reminders ([#24](https://github.com/sintax-tech/mcp-for-nextcloud/issues/24)):** create/update DISPLAY reminders and read them in event listings using the same `alarms` keys. Other reminder types are preserved; confidential events and read-only shares expose none.
- **HTML mail drafts ([#30](https://github.com/sintax-tech/mcp-for-nextcloud/issues/30)):** `mail_create_draft` accepts `html: true` under `mail.draft`. The plan shows sanitized HTML; confirmation saves a draft without a signature or sending mail.
- **Deck completion and archiving ([#27](https://github.com/sintax-tech/mcp-for-nextcloud/issues/27)):** complete/reopen and archive/unarchive cards through separate confirmed operations using `deck.edit`.
- **Task status ([PR #29](https://github.com/sintax-tech/mcp-for-nextcloud/pull/29)):** create/edit accepts `NEEDS-ACTION`, `IN-PROCESS`, `COMPLETED` and `CANCELLED`, with progress consistency checks.
- **Full in Tables and Collectives:** Full includes structure/sharing and collective creation/members. Existing grants stay unchanged; an earlier Full without these operations appears as Custom until an administrator chooses Full again.

### Fixes

- **OAuth allowed-hosts field:** a wider field makes host lists easier to read.
- **Admin radios:** focus and hover rings are round without changing the matrix layout.
- **Tables row receipts:** equivalent plain numbers such as `42` and `42.0` no longer trigger a false different-value warning.
- **Deck write results:** card deletion/movement returns `boardId` and `url`; editing preserves them after an observed partial result.
- **Filtered server logs:** bounded reads avoid timeouts; continue from `scan.nextOffset` when `scan.timeBudgetReached` is true.

- **OAuth/CIMD ([#28](https://github.com/sintax-tech/mcp-for-nextcloud/issues/28)):** withdrawing a host revokes its credentials, and authorization metadata advertises `iss` while consent preserves the issuer. Re-adding requires sign-in; Zapia interoperability awaits the reporter's test.

**Updating runs a database migration and the CIMD initialization repair step.** The host allowlist and credentials for still-allowed hosts survive; credentials from never-allowed hosts require administrator approval of the host and a new sign-in.

## Module permissions

- **Mail ([#1](https://github.com/sintax-tech/mcp-for-nextcloud/issues/1)):** `mail.read` lists accounts and cached folders; `mail.messages` reads/searches messages and threads, and `mail.attachments` reads attachment text. Reads never mark messages read. Separate opt-in `mail.draft`, `mail.send`, `mail.flags` and `mail.move` grants control writes. Drafts support plain text or sanitized HTML; sending is plain text only.
- **Tables ([#1](https://github.com/sintax-tech/mcp-for-nextcloud/issues/1)):** `tables.read` discovers tables/views/columns and reads authorized rows; `tables.create`/`tables.edit` write rows. `tables.schema` creates/updates tables, columns and views; `tables.share` shares/revokes user/group access. Native ACLs and view restrictions apply; schema/sharing have narrower supported versions than reading/rows.
- **Forms ([#1](https://github.com/sintax-tech/mcp-for-nextcloud/issues/1)):** independent `forms.read`, `forms.results`, `forms.create` and `forms.edit` grants cover structure discovery, authorized submissions, private form creation and editing. Editing includes adding, reordering and deleting questions/options and changing supported question types. Existing `forms.edit` grants include these actions; review them. Native upload-folder, answer-orphaning, editing-lock and confirmation-email-selection effects are explained in the plan.
- **Polls ([#1](https://github.com/sintax-tech/mcp-for-nextcloud/issues/1)):** `polls.read` discovers polls/options/status; `polls.results` and `polls.links` separately admit permitted results and existing direct participation links. `polls.create`, `polls.configure`, `polls.options`, `polls.options.remove`, `polls.share` and `polls.invite` control creation, settings/state, options, sharing and individual invitations. Native visibility/anonymity still apply; no voting tool is exposed.
- **Collectives ([#22](https://github.com/sintax-tech/mcp-for-nextcloud/issues/22)):** `collectives.read` reads/searches pages; `collectives.create`, `collectives.edit` and `collectives.move` write pages. On NC33–35, `collectives.collective.create` creates a collective and `collectives.members` lists/manages members. These grants are independent of `files.*`; Full includes all Collectives operations, subject to native rights.
- **Files ([#20](https://github.com/sintax-tech/mcp-for-nextcloud/issues/20)):** the separate, default-denied `files.delete` covers eligible local files/folders and permitted shared descendants, with confirmation and residual recovery risk. Received share roots and unsupported backends remain refused; see deletion below.
- **OAuth:** strict Basic public-client identification with an empty password can supply a missing `client_id`. PKCE and native client validation still apply. There is no dynamic registration or client-secret authentication; Zapia compatibility awaits the reporter's test.

**Plans and platform effects:** requested MCP writes require explicit confirmation and, where returned, the plan's `plan_state`. Files preview starts from the actor's lazy native tree; only a native NotFound reaching its adapter permits full setup and one plan retry. Policy/ACL/scope refusals never permit that retry. Native bootstrap can still normalize received share targets/folders in cold state or on a real miss. Internally mapped misses and `nodeExists=false` can make a preview refuse or predict parents/shared impact differently from the confirmed call, which rechecks permissions and `confirm_shared`. Preview is not universally free of platform effects and does not promise exact parity. Unknown grants grant nothing: an unknown group grant denies only that operation, and administrators can clear it in the group editor.

## Permission updates

The new default-denied grants are `tables.schema`, `tables.share`, `polls.configure`, `polls.options`, `polls.options.remove`, `polls.share` and `polls.invite`. `options.remove` is one exact operation. Polls presets keep their 1.2.5 operation sets and labels and preserve independent grants outside those sets; Tables Full includes `tables.schema` and `tables.share`. None is the explicit exception: it denies all operations. The matrix layout, bulk changes and Undo remain; choose new grants explicitly.

`forms.edit` already granted to a user now includes the seven structure operations below. The Edit forms help explains adding, reordering and deleting questions/options and changing a question type; review existing grants. Collectives has independent `read`, `create`, `edit`, `move`, `collective.create` and `members` grants: read starts allowed, the others denied; Full includes `collective.create` and `members`. `files.*` does not grant `collectives.*`, or vice versa. Native permissions still apply.

A user or group with an earlier Tables/Collectives Full that lacks the new operations is shown as Custom; this includes Tables Full saved in 1.2.5. Existing grants are not expanded automatically.

## Calendar reminders

`calendar_create_event` and `calendar_update_event` accept optional `alarms`, a list of 0–5 objects with integer `minutesBefore` from 0 to 40320 and optional `description` of at most 65536 characters. Omitted or empty descriptions use the final event title, or "Event reminder" when that title is empty. Duplicate reminders are retained. Without `alarms`, behavior remains unchanged: create adds none and update preserves existing VALARM components.

When present on update, the list replaces only valid DISPLAY alarms relative to the master event's start; `[]` removes that subset. Absolute, end-relative, AUDIO/EMAIL and unrecognized alarms remain. Overrides keep their own alarms; this does not update every recurrence. The plan shows replaced and preserved alarms. The receipt reports server observation, not notification delivery on a device. Existing confirmation, shared-calendar checks and DAV ETag rules apply. L01 adds no `plan_state` or approval token: on update, omitting the event ETag leaves changes between preview and confirmation unprotected. There is no new alarm grant, automatic retry or rollback.

## Forms structure writes

Seven operations use the existing `forms.edit` and native EDIT permission: `forms_add_question`, `forms_reorder_questions`, `forms_add_option`, `forms_reorder_options`, `forms_delete_question`, `forms_delete_option` and `forms_change_question_type`. These are separate from the existing point-edit tools. New structure writes require the checked Forms versions 5.3.0, 5.3.7, 5.4.0 or 5.4.1 and the expected native API; unsupported shapes hide/refuse these operations.

Plans require confirmation with their `plan_state`, plus `confirm_shared` where applicable. Reordering must name the complete relevant set. Deleting a question logically removes it and can leave answers/options orphaned; deleting an option is irreversible and can leave answer references orphaned. No restoration is exposed. Deleting an upload question can schedule native asynchronous upload-folder deletion: MCP neither examines those files nor verifies job completion. Changing a question type does not convert existing answers; `grid` and `datetime` are refused as target types. Structural writes can renew the native lock and clear the confirmation-email selector, without sending email. Receipts distinguish observed, partial and uncertain effects; no retry or rollback.

## Polls writing

The ten additions are `polls_update_poll`, `polls_set_poll_state`, `polls_add_option`, `polls_update_option`, `polls_reorder_options`, `polls_remove_option`, `polls_restore_option`, `polls_add_share`, `polls_update_share` and `polls_invite_share`. They use their separate configure/options/options.remove/share/invite grants and require native editor access, even where a participant could propose an option in the native UI. Polls levels and labels remain exactly those of 1.2.5.

The checked source families are NC32/Polls 8.6.3, NC33/9.0.7, NC34/9.1.4 and NC35/9.3.0; writing also requires the supported API shape. `allowDownload` and `timezoneName` are available only in the checked 9.x branch. Access mode, anonymity, type, owner and permanent deletion are outside these tools. Reorder applies to the full active option set of a nonexpired text poll. Soft removal/restoration can hide or reveal old votes; it does not cast a vote.

Sharing follows the actor's native policy. Public shares require public sharing to be allowed; writes never return public tokens or URLs. Delegating an admin share grants editing rights. Invitations target one active individual share and can notify/send email; the recorded native marker does not prove delivery. Confirm the plan with its `plan_state`; results may be partial or uncertain after a native attempt, with no automatic retry or rollback.

## Tables schema and sharing

The eight additions are `tables_create_table`, `tables_update_table`, `tables_create_column`, `tables_update_column`, `tables_create_view`, `tables_update_view`, `tables_share_node` and `tables_unshare_node`. `tables.schema` and `tables.share` are independent and denied by default; the Full level includes them, Read does not. Existing resources require native manage permission, not merely row create/update permission.

The initial schema/sharing ranges are Tables `[1.0.10,1.0.11)` on NC32, `[2.2.2,2.2.3)` or `[2.3.1,2.3.3)` or exactly `2.4.0` on NC33–35, with matching native signatures and fields. The upper bound is excluded. This does not narrow existing reading/row-writing support or promise schema writing for every Tables 1.0.0+ installation. Older 1.0.0/2.0.0 adapters remain disabled. The exact 2.4.0 profile preserves existing view layouts/card settings and refuses column changes that would clear a card source; 2.4.1+ is not enabled. Runtime integration is proven on NC35/MariaDB; NC33/34 are covered by official-source/shape evidence.

Create uses only the custom table template and one entity per call. No schema deletion, owner transfer, public link or federated resource write is exposed. Column type/subtype cannot be changed; existing relation columns cannot be edited. View updates can hide rows without deleting them. User/group sharing requires explicit permissions; native manage/delete bits grant those powers in the native UI even without an MCP schema-deletion tool. Changing permissions on an existing share requires separately confirmed revocation and creation.

Plans name the exact changes and need `plan_state`, confirmation and `confirm_shared` for another owner's table. Native DTO updates may rewrite omitted fields; a concurrent native edit can be overwritten between validation and writing, without a cross-service CAS guarantee. Fresh authorized observation reports the requested, different/possibly partial or unverified state. There is no automatic retry, rollback, backup or guaranteed Undo; repeated creation can duplicate an entity.

## Collectives pages

`collectives_list`, `collectives_pages`, `collectives_read` and `collectives_search` read accessible collectives/pages; `collectives_create`, `collectives_edit` and `collectives_move` create, edit Markdown, move or rename pages inside an existing collective. Native membership and permissions, hidden-file rules and resource scopes still apply. Writes use their separate grants and confirmed plans. Create does not aggregate content; create first, then edit. Edit accepts full content, append or one unique replacement, with ETag state checks; an open collaborative Text session has no shared CAS guarantee.

The approved native API ranges are Collectives 4.0.0 to below 4.8.0 on NC32–33, 4.4.0 to below 4.8.0 on NC34, and 4.5.0 to below 4.8.0 on NC35, subject to API shape checks. Before 4.4.0, content search is refused; title search remains. Where content search is supported, the index can lag. Moving/renaming can turn a leaf parent into a folder, notify members and break path-based links; IDs remain stable. In-place sibling reordering, page deletion, attachments, templates and sharing management are outside the feature. No automatic retry or rollback; direct `files.*` access to the mounted Markdown remains separate.

## Collective creation and members

Only on NC33–35, with Teams (Circles) of the same release and the native shapes and constants checked (otherwise the tools are hidden). `collectives_create_collective` (`collectives.collective.create`) calls `CollectiveService::createCollective`, which creates a new team owned by the user, the collective, its folder and its landing page. The name is checked against collectives and teams the user sees and must stay the same after Collectives and Teams normalize it; control characters and empty names are refused, and guest accounts are refused. Limitations: a team of that name administered by the user that appears between confirmation and creation is adopted by Collectives (its members get access); the receipt reports it, but after a failure halfway adoption may be unknown and the receipt is uncertain. On NC35 Teams may add a team folder. The receipt reads the collective, its folder and its landing page record without repairing anything.

`collectives_list_members`, `collectives_add_member`, `collectives_set_member_level` and `collectives_remove_member` (all under `collectives.members`) go through `CirclesManager` in the actor's own session; only admins of the collective manage members and Teams checks its own rules again. Accounts and groups of the server can be added; Teams sends no email of its own. In a team that requires invitations, an account becomes an invitation (level none) with a Nextcloud notification, unless it had already asked to join: then the request is accepted and it becomes a member at once; groups are refused. Levels are member, moderator and admin; ownership is never transferred, and the owner and the actor's own membership are never changed or removed. Receipts read the team again and report Teams' own internal records apart. No collective is deleted; nothing is retried or undone.

## HTML mail drafts

`mail_create_draft` accepts optional `html: true`; the default remains `false` (plain text). The existing `mail.draft` permission and confirmation apply. Mail's HTML sanitizer runs with a restricted configuration before planning and again before saving through `saveDraft`. Scripts, events, CSS, embedded content and all images (remote and `data:`) are forbidden. Links require an explicit `http`, `https` or `mailto` scheme.

The plan shows the complete sanitized HTML, a text preview, removal counts, names of unwrapped elements and every retained or rejected link destination. It preserves spaces and indentation in `pre`/`code`; table cells use tabs and list items have markers. Source and sanitized HTML each have a 50,000-character limit, with no truncation of the HTML confirmation. A nonempty source with no readable content after filtering is refused. If Mail's sanitizer cannot be loaded, HTML mode is refused and nothing is saved. Unsafe parser recovery and unaccounted content loss are also refused.

Mail generates a MIME plain text alternative with Horde, which may differ from the confirmation preview. No account signature is added. Each confirmation creates another draft; draft editing and HTML sending are outside this feature. Requested in [#30](https://github.com/sintax-tech/mcp-for-nextcloud/issues/30).


## Optional file deletion

`files_delete` requires the separate **files.delete** permission, denied by default for existing users and groups too. An old Files Full selection does not grant it; a new Full selection includes Delete. Administrators must grant it deliberately. Files and completely inspected folders, including nonempty folders, with a canonical source in unencrypted Local personal home storage are supported. Shared originals and descendants of local received shares are supported with native DELETE permission and explicit `confirm_shared: true`; UPDATE is not required. Original folders owned by the acting user remain eligible when shared, but received share roots are refused. External/team/federated/object storage, other mount roots, personal/selected-scope roots and current/historical backup folders (also through owner aliases) are refused. Plans disclose shared impact without recipient names. Native deletion uses the acting user’s node; the configured trash-size limit follows the effective owner. The core may put data in different users’ trash bins and may restore to another destination when the original location is not creatable. No copy to either person or restoration destination is promised. A folder is refused while any exclusion tag is configured. Every descendant must pass the same checks; an incomplete inspection refuses the entire operation without disclosing hidden names. The limits are 2,000 nodes including the source, 1 GiB of file bytes and 64 levels below the source. One native directory listing may be materialized before a wide directory is refused. The tree is rechecked before deletion, but this is not a transaction over descendants: concurrent changes or a partial native operation can leave an uncertain result. A surviving root alone does not prove all contents survived.

A call without `confirm: true` returns the exact path, ID, ETag and warning without deleting or copying anything. Show the warning and ask explicitly; echo `id` and `etag` with confirmation to detect changes since preview. The server revalidates native DELETE, scope/exclusion/Guests, backup names, available trash/backend/opt-out checks and any explicitly configured trash-size limit and locks before the native Node operation. These checks reduce risk but do not certify future transfer or metadata writes. **Nextcloud tries the trash bin first and may permanently delete the item if that fails, even while the trash bin is enabled.** Grant only if you accept that residual risk and maintain backups. No mandatory recovery copy is created; existing backup settings remain unchanged. After removing your own file or folder, the receipt says whether it was found in your trash bin at the time of the check (for a folder, only the folder itself); items of shares you received go to the owner's trash bin, which MCP never checks, so their destination is reported as not confirmed. The trash bin keeps items only for a limited time.

There is no evidence to quantify this risk or call it common in normal operation. Backends differ; Team folders can refuse a failed trash operation by exception, and is outside this feature’s initial scope. The result distinguishes original preserved (error), removal observed in your own trash bin at the time of the check, removal with destination unconfirmed, and uncertain outcome (error); it does not promise trash or recoverability, and never retries automatically. Native retention still applies: depending on its configured policy and available user quota, Nextcloud may remove items from the trash later. The preflight size check concerns the explicit trash-size limit, not a guaranteed retention period. Conversational confirmation does not prove human consent or eliminate prompt injection.

`DeleteFileHandler` delegates admission to `DeleteEligibility`/`DeleteBackendGate` and observation to `DeleteOutcome`. Native token-lock lookup retains the documented `LockAwareWrite` concurrency limits; a lock checked before the operation is not an atomic DAV-token-lock guarantee.

## Mail messages

`mail_list_messages`, `mail_search_messages`, `mail_read_message` and `mail_read_thread` read the messages of the caller's own Mail accounts. They are read tools (`operation: read`, never a plan or `confirm`, `readOnlyHint`), but only the separate grant `mail.messages` (`grantAnyOf`) opens them; like every operation but `read` it starts denied, so `mail.read` (accounts and folders) and earlier grants never open the messages. The admin matrix names the Mail levels *Accounts and folders*, *Messages* and *Messages and attachments* (see below).

| Tool | Reads | Mail API |
|---|---|---|
| `mail_list_messages` | one page of one folder, newest first | `MessageMapper::findIdsByQuery()` + `findByIds()` (cache) |
| `mail_search_messages` | one folder, every folder of one account or of every own account; sender, recipient, copy (fragments of one field are alternatives, as the Mail query ORs them), subject, `since`/`until`, unread, flagged, attachments, `body` (with `subject`, either matches) | the same folder query per folder; `body` adds `Provider::findMatches()` (IMAP SEARCH TEXT) per folder |
| `mail_read_message` | headers, body as text, attachment names/types/sizes | `MailManager::getMessage()`, `getMailbox()`, then `getImapMessage(..., true)` |
| `mail_read_thread` | the cached conversation of one message, in its account | `MailManager::getThread()` |

- **Never written:** no flag, folder or message changes; listings and searches never call `MailSearch::findMessages()`, whose `PreviewEnhancer` would log in to IMAP and write previews. The body is read by the Mail fetcher with `BODY.PEEK`. The Mail app's Horde client may keep fetched metadata in Nextcloud's cache, as it does for the Mail app itself.
- **Isolation:** every id goes through the user's own accounts (`getMessage`/`getMailbox` filter by owner, then `AccountService::find`); another user's or a delegated id reads exactly like a missing one. Folders that are not selectable, never synchronized or locked by a Mail sync are listed in `skippedFolders`, never searched. One search reads at most 100 folders, 20 with `body`; more is refused.
- **Pages:** the cache orders by the date the Mail app stores, which is when the mail server received the message (IMAP INTERNALDATE), not the Date header; `since`/`until` compare with it too. A page ends after the last message of its date (at most 200 messages of one date, more is refused), and `nextCursor` is bound to the folders and filters it came from, so no message is skipped or repeated between pages. A message that arrives later is not on the next pages, which continue strictly before the last date. Since Mail 5.5 the folder query groups by thread by default; the tools turn that off where it exists, so every message of a conversation is listed.
- **UID generation:** a cached UID names a message only within one UIDVALIDITY. Before anything of the message is fetched, the folder's UIDVALIDITY on the server (STATUS) must equal the one of the folder's cache, read from the three sync tokens the Mail app stores (`V` of the Horde sync token, the value Horde's own sync checks). A folder recreated on the server since Mail last synchronized, or without readable tokens, is refused without any FETCH; the generation of the selection the metadata FETCH opened is compared again before the body is fetched, so a folder recreated between the STATUS and that opening is refused too. The Message-ID is only a complementary check: it can repeat or be missing.
- **Body size:** one metadata FETCH (envelope, RFC822.SIZE) runs on the Mail app's own IMAP client, and the whole message size is the budget, headers and attachments included: part sizes are not used, since the Horde parser estimates base64 parts and lets a sender's Content-Disposition `size` replace them. More than 1 MiB is refused, as is a missing size. It is the size the server declares: a preflight, not a hard cap against a server that declares less than it sends.
- **Links:** every folder (`mail_list_mailboxes`, the `folders` of a page) and every message row carries `url`, built by `IURLGenerator::linkToRouteAbsolute` from the Mail app's own routes: `mail.page.mailbox` (`/box/{id}`) for a folder, `mail.page.thread` (`/box/{mailboxId}/thread/{id}`) with the message's own folder and database id for a message, the id the Mail front end reads (envelope `databaseId`) and loads the conversation of from `api/messages/{id}/thread`. That API answers only for a message with a thread root, so a message without one has `url: null`. Accounts have no Mail route and no link. A link adds no access (Mail checks the account again) and opening a message in Mail marks it read there, as Mail does. `mail-routes.json` (`generate-mail-routes.php`, `MailRoutesContractTest`) records the three routes from the SHA256-pinned 5.0, 5.5, 5.7, 5.9, 5.10.11 and 5.12.5 archives.
- **Output:** subjects, names, previews, bodies and attachment names travel in an envelope marked untrusted. The body is plain text: the plain part, or the HTML part with its markup removed (no rendering, no remote content), 20000 characters by default and at most 100000, with the cut declared. Attachment content is not read.
- **Contracts:** the Mail classes are checked against the pinned Mail releases (`mail-sources.json`); the Horde classes of the Mail vendor tree that the STATUS and metadata FETCH use, and the sync token format, against `mail-horde-surfaces.json` (`generate-mail-horde.php`, `MailHordeSurfaceContractTest`).
- **Integration cell:** `mail-cell.sh` seeds synthetic messages (many stored on the same second across folders, HTML-only, attachment, more than 1 MiB in total as plain text, as base64 text, behind `Content-Disposition: size=1` and as a large header, a thread, body-only search text, folders recreated with another UIDVALIDITY after Mail cached them) and keeps the IMAP rawlogs of alice's sessions in the artifacts.

## Mail attachment text

`mail_read_attachment` returns the text of one attachment of a message of the caller's own accounts: `message_id` as the message tools give it, `attachment_id` the MIME part number `mail_read_message` lists. It is a read tool (`operation: read`, never a plan or `confirm`, `readOnlyHint`) of its own grant `mail.attachments` (`grantAnyOf`), which starts denied. It does not need `mail.messages`: it resolves the message, its folder and its account itself and returns nothing of the message (no headers, no body) but the attachment text; in practice the ids come from `mail_read_message`. Neither `mail.read`, `mail.messages` nor any earlier level opens it; the admin matrix calls the third Mail level *Messages and attachments*, and attachments without messages stay a custom choice.

- **Mail 5.10.11 or later:** the Mail app's `IMAP\MessageMapper::getAttachment()` fetches the part and its MIME header with `BODY.PEEK` from 5.10.11 (and every 5.11+) on; earlier releases fetch with `BODY[part]`, which sets `\Seen`. The tool is not defined below that release, or when the version cannot be told (`MailAttachmentSupport`, fail-closed). Marking the message unread again would be a write, and fetching the part outside the Mail app a parallel IMAP stack, so neither is done. `mail-attachment-peek.json` (`generate-mail-attachment-peek.php`, `MailAttachmentPeekContractTest`) records from the SHA256-pinned 5.10.10 and 5.10.11 archives that the minimum is the first release that peeks.
- **Same client, same checks as a body:** `MailManager::getMailAttachment()` is not used, because it opens a client of its own. On one Mail IMAP client: STATUS UIDVALIDITY must equal the folder cache's generation; one metadata FETCH (envelope, RFC822.SIZE, BODYSTRUCTURE) opens the folder read-only; the generation of that selection is compared again; then `getAttachment()` runs on that same client. A reconnection between the last check and the read remains an undemonstrated limit, as for the body.
- **Budget before any content:** the whole message size is the budget, 1 MiB as for a body (`MailBodyPreflight::MAX_MESSAGE_BYTES`); an attachment is never larger than its message. The decoded content must again be within 1 MiB before any parser runs. The size is what the server declares: a preflight, not a hard cap against a server that declares less than it sends.
- **Which parts:** the part must exist, hold content itself, sit only under multipart parts the Mail fetcher walks into (a multipart that is neither an attachment nor named) and be an attachment as the fetcher lists it (Horde's `isAttachment()`, or a named `text/calendar`); body parts, multiparts, signatures, parts inside an attached or named multipart and parts inside an embedded message read like a missing attachment, and an embedded `message/rfc822` is refused as unsupported. An encrypted message (`multipart/encrypted`) or S/MIME container (`application/(x-)pkcs7-mime`, enveloped or opaque signed) is refused before anything is fetched, so the Mail app never decrypts or unwraps it for this tool.
- **Which kinds:** the content decides; name, extension and declared type are the sender's. Content starting with `%PDF-` is a PDF, content starting as a ZIP archive is DOCX (`[Content_Types].xml` + `word/document.xml`) or ODT (`mimetype` entry), whatever the declared type. Other content is text only under a declared `text/plain`, `text/csv`, `text/markdown`, `text/calendar`, `text/vcard`, `text/x-vcard`, `application/json` or `text/html`, converted from its declared charset to UTF-8 and without NUL bytes. HTML, declared or starting as a document, is turned into text (`MailBodyText::htmlToText`), never returned as markup, nothing remote fetched. Anything else is refused before any parser runs. No macro, script, OCR, external service or new dependency.
- **PDF budget:** smalot/pdfparser, already shipped for `files_read`, bounds only FlateDecode per stream (and, past the bound, returns the first bytes of the stream as if they were all of it), expands LZWDecode and RunLengthDecode without limit and follows indirect `/Filter` objects. The raw file is read with the parser's own lexicon (NUL ends a name and separates tokens, `%` starts a comment) and refused when it contains LZWDecode or RunLengthDecode at all (also spelled with `#xx` escapes), takes a filter from anything but a name or an array of names, has `/Encrypt`, or holds more than 128 streams. The parser then decodes with the app's own filters, set through its protected extension points (no change to the library): FlateDecode inflates in small steps and a stream past 256 KiB refuses the whole document ("could not be read completely"), never a cut text; LZW/RunLength never run. Image content is not kept, so decoding stays under 32 MiB.
- **DOCX/ODT budget:** at most 1000 entries; the document entry must not be encrypted and must declare at most 4 MiB, and is read with that cap; an ODT whose manifest declares encryption is refused. The archive is read from a server temporary file (`ITempManager`), removed at once.
- **Why not `TextExtractor`:** its limits are those of the user's own files (20 MiB in, 20 MiB inflated, 80 MiB PDF decoding), it trusts the name/extension, returns HTML as is and a notice instead of an error; the attachment reader uses the same parser, ZIP reading and paragraph breaks within attachment limits.
- **Output:** an envelope marked untrusted with the attachment id, declared name and type, detected kind, the text (20000 characters by default, at most 100000, cut declared) and its length. The text of a PDF, DOCX or ODT attachment follows the UTF-8 rules of `files_read`: always valid UTF-8, surrogate pairs rebuilt, the declared XML charset converted, other invalid bytes replaced by U+FFFD, nothing guessed. Every refusal is a fixed, translated message, never a parser's or server's text. The tool keeps no cache of its own; the Mail app's Horde client may keep fetched metadata in Nextcloud's cache, as for a body.


## Mail flags

`mail_set_flags` marks one message of the caller's own accounts read or unread (`seen`) and flagged or not (`flagged`), as a wanted state: a flag already so is left as it is, so repeating the call changes nothing. No other flag (deleted, draft, answered, recent, custom keywords), no move, no deletion and no sending is reachable. It is one of the Mail module's four writes (the others are the move, the draft and the send below): operation `flags`, a separate grant that starts denied, also for policies stored before it existed, and that neither needs nor opens `mail.read`, `mail.messages` or `mail.attachments`. The admin matrix lists it as the fourth Mail level, *Messages, attachments and flags* (flags alone stays a custom choice), and every way of granting it (cell, bulk change, level popover, group policy) first asks the administrator with a warning about prompt injection.

- **Plan:** a call without `confirm` reads only the Mail cache and contacts no server. It names the message by its ids; the account address and folder path only for a user with `mail.read`, the subject, sender and date (marked untrusted) only with `mail.messages`, so the flags grant never reads a message through a plan. It lists each flag that changes (from the cached state) and each one already as asked, and carries `plan_state`, an HMAC of the cached identity (message, folder and account ids, UID, the folder's UID generation, Message-ID) and of the asked flags. There is no ETag: the Mail app has none for flags.
- **Confirmation:** `confirm: true` needs that `plan_state`; the message is resolved again through the user's own accounts (another user's message reads like a missing one) and a different cached identity or other arguments answer with the new plan, nothing written. Then, on one IMAP client of the Mail app and one selection: STATUS UIDVALIDITY equals the folder cache's generation; the folder is selected read-write (SELECT); the generation of that selection is compared again; one FETCH reads envelope and flags (the message must exist and keep its Message-ID); only the asked flags that differ are stored with the Mail app's own `IMAP\MessageMapper::addFlag()`/`removeFlag()` (`STORE +FLAGS/-FLAGS`). `MailManager::flagMessage()` is not used for the STORE, because it opens a client of its own where these checks would not hold. A UID of another generation is never changed.
- **Mail cache:** after each change the tool dispatches the Mail app's own `MessageFlaggedEvent`, as `flagMessage()` does, so the Mail app's `MessageCacheUpdaterListener` updates its cache (its spam/ham/junk listeners act only on `$junk`/`$notjunk`). The event takes the UID up to Mail 5.10.x and the message from 5.11.0 on; the shape is read from the installed class. `mail-flag-event.json` (`generate-mail-flag-event.php`, `MailFlagEventContractTest`) records both shapes from the SHA256-pinned 5.10.11, 5.11.0 and 5.12.5 archives; the older pins come from the main fixtures. If a listener fails, the server keeps the change and the answer says the Mail app shows it after its next synchronization.
- **Limits:** the SELECT, like every write the Mail app does, takes `\Recent` away for later sessions. A server failure in the middle of two changes can leave one of them done; the answer says so without the server's text. A reconnection between the selection check and the STORE remains an undemonstrated limit.

## Mail move

`mail_move_message` moves one message of the caller's own accounts to another folder of the same account (`message_id`, `mailbox_id`). Another account's folder is refused, as the Mail app's own move refuses it; another user's folder reads like a missing one; a folder that only groups others is refused. It is the Mail module's second write: operation `move`, a separate grant that starts denied, also for policies stored before it existed, and that neither needs nor opens the read grants or `mail.flags`. The admin matrix lists it as the fifth Mail level, *Messages, attachments, flags and moving* (moving alone stays a custom choice), and every way of granting it asks the administrator first with the same warning as flags. It never deletes, purges, changes a flag or sends.

- **Plan:** a call without `confirm` reads only the Mail cache and contacts no server. It names the message, the folder it leaves (`from`) and the folder it goes to (`to`, with its `kind`) by their ids; the account address and both paths only with `mail.read`, the subject, sender and date (marked untrusted) only with `mail.messages`, so the move grant never reads a message through a plan. The kind is `same` (the message's own folder: the plan says nothing will move and the confirmation contacts no server), `junk` (the account's Junk folder: a plain move; the Mail app reports spam on the `$junk` keyword, not on a move, so the note says moving neither marks nor reports it), `trash` (the account's Trash) or `folder`.
- **Trash:** moving to the account's Trash is allowed with a warning in the plan. With a Trash retention set in the Mail app, the plan gives its days (`retentionDays`): the Mail app's `TrashRetentionJob` deletes for good what stays longer, and emptying the Trash or the mail server's own policies can delete it sooner. Without one, the plan says the Mail app has no automatic deletion set, but emptying the Trash or the mail server's policies can still delete the message for good. No duration is promised: other policies of the provider or administrator are not known here.
- **Plan state:** `plan_state` is an HMAC of the cached identity (message, folder and account ids, UID, the source folder's UID generation, Message-ID) and of the destination as stored (id, path, kind and the Trash retention the plan showed). A confirmed call whose message, destination, classification or retention differs (a folder that became the Trash, a retention that changed) or whose arguments do gets the new plan with a warning, nothing moved.
- **Confirmation:** the message and the destination are resolved again through the user's own accounts. Then, on one IMAP client of the Mail app and one selection: STATUS UIDVALIDITY of the source equals its cache's generation; the source is selected read-write (SELECT); the generation of that selection is compared again; one FETCH reads the envelope (the message must exist at that UID and keep its Message-ID); the server must report MOVE or UIDPLUS among its capabilities (Horde's `capability`), otherwise the move is refused with a fixed message, nothing asked of the server; the Mail app's own `IMAP\MessageMapper::move()` moves it (Horde: UID MOVE with MOVE, or UID COPY then UID EXPUNGE of that UID with UIDPLUS alone). `MailManager::moveMessage()` is not used, because it opens a client of its own where these checks would not hold. A UID of another generation is never moved.
- **Mail cache:** after the move the tool dispatches the Mail app's own `MessageDeletedEvent` for the source UID (the same shape in every supported release), so `MessageCacheUpdaterListener` drops it from the cache; the destination copy appears after the Mail app's next synchronization of that folder. The answer carries the destination's link and the new UID when the server gives it. If a listener fails, the server keeps the move and the answer says the Mail app catches up at its next synchronization.
- **Repetition and failure:** after a move that succeeded, a repeated confirmed call is refused: the Mail cache no longer has the source message (*not found*, no IMAP), or, when its listener failed, the server no longer has it at that UID (*not found* after STATUS, SELECT and FETCH). A failure before the move (STATUS, SELECT, FETCH, capabilities) says nothing was moved. A failure during the move has no known outcome (the server may have moved it, or copied it and kept the original, before the answer was lost): the answer says it is uncertain, to look in both folders and not to repeat; nothing is retried or undone automatically and no event is dispatched. After a copy that kept the original, the source and the plan are still valid, so confirming the same plan again could copy the message once more: there is no general protection against a duplicate after an uncertain answer. No idempotency or rollback is claimed.
- **Limits:** the SELECT takes `\Recent` away for later sessions. A reconnection between the selection check and the move remains an undemonstrated limit. A server with neither MOVE nor UIDPLUS is refused: there, Horde's fallback expunge takes `\Deleted` off the other messages of the folder for a while and puts it back afterwards, not in a `finally`, so a failure in between would change other messages. The cells prove only Dovecot, which has MOVE; the UIDPLUS-only path is the Mail app's own and is proven here by a strict double, not by a server.


## Mail drafts

`mail_create_draft` saves one new draft in the Drafts folder of one of the caller's own accounts (`account_id`, from `mail_list_accounts`), with what the request of the issue names: recipients (`to`, `cc`, `bcc`, plain addresses only, at most 50 each), a one-line `subject` (255 characters) and a `body` (50000 characters; plain text by default, sanitized HTML with `html: true`). No attachment, reply or other sender: the draft's sender is the account, as in the Mail app. It is the Mail module's third write: operation `draft`, a separate grant that starts denied, also for policies stored before it existed, and that neither needs nor opens the read grants or the other writes. The admin matrix lists it as the sixth Mail level, *Messages, attachments, flags, moving and drafts* (drafts alone stays a custom choice), and every way of granting it asks the administrator first with the Mail write warning. It never edits, replaces, deletes or sends a draft.

- **Recipients:** each entry must be one plain address (`name@example.com`): no display name, quotes, comments, group syntax, comma or semicolon. The Mail app parses the list (`AddressList::parse()`) back into exactly the addresses the plan shows. A subject with a line break or another control character, and a text with NUL, are refused.
- **Bcc needs Mail 5.10.11 or later:** up to 5.9.x the Mail app's draft save stores the message through `Horde_Mime_Mail::getRaw()`, which leaves a Bcc header out, so the saved draft would lose its Bcc recipients; from 5.10.11 on it builds the headers with Bcc. A draft with Bcc is refused, before the plan and again before the save, on an older Mail or one whose version cannot be read; drafts without Bcc are saved on every supported release. `mail-draft-bcc.json` (`generate-mail-draft-bcc.php`, `MailDraftBccContractTest`) records this from the SHA256-pinned 5.0.0, 5.5.0, 5.7.0, 5.9.0, 5.10.11, 5.11.0 and 5.12.5 sources and ties the minimum to them; the cells check the Bcc header in the draft Mail 5.12.5 stores.
- **Account and Drafts:** only the user's own accounts (another user's account, or one delegated to the user, reads like a missing one). The Drafts folder is the one the account settings name (`MailAccount::getDraftsMailboxId()`, which the Mail app sets from the folder's role or name, or the user chooses); an account without one is refused with a fixed message and no folder is created.
- **Plan:** a call without `confirm` contacts no server and saves nothing. It shows the whole draft (recipients, subject, text), the account and the Drafts folder by id (address and path only with `mail.read`), and notes that nothing is sent and that each confirmation creates one more draft. `plan_state` is an HMAC of the account, the Drafts folder (id and path) and the draft; a confirmed call whose account, folder or arguments differ gets the new plan with a warning, nothing saved.
- **Save:** the confirmed call uses the Mail app's own draft save, `MailTransmission::saveDraft()` (the one behind its `AccountsController::draft()`), with no previous draft: it builds the message with Horde's null transport (no SMTP), appends it with `\Draft` to the Drafts folder on an IMAP client of its own and dispatches `DraftSavedEvent`, whose listener deletes a previous draft only when one is given (never here). It writes no `LocalMessage`, so nothing reaches the Mail app's Outbox, send queue or SMTP; `DraftsService::saveMessage()`, which stores a local message for a background job, is not used. The answer carries the Drafts folder's link and the new UID when the save gives a positive one (the Mail app turns a UID it could not read into 0, reported as `null` while the draft still counts as created); the draft joins the Mail cache at the Mail app's next synchronization of that folder.
- **Failure and repetition:** the Mail app's refusal before writing (`ClientException`, such as no Drafts folder) says no draft was created. Any other failure may come after the append (the answer lost, the event failing): the answer says the draft may have been saved, to look in Drafts and not to repeat. The tool calls the save once and adds no retry, but the fallbacks inside the Mail app and Horde stay: Horde's append, for one, logs in again and appends once more after a disconnection while BINARY was in use, so one confirmation is not guaranteed to append exactly once when the connection fails (this branch comes from the source; the cells did not observe it). There is no receipt: confirming the same plan again creates another draft, so a repeated confirmation can duplicate it.
- **Limits:** the draft is plain text by default; optional HTML follows the restrictions above. The cells prove the save on Dovecot with Mail 5.12.5; the other pinned releases are covered by the contract of the same surfaces.


## Mail send

`mail_send_message` sends one new message from one of the caller's own accounts (`account_id`), with the fields and rules of a draft (recipients as plain addresses in `to`, `cc` and `bcc`, at least one; a one-line `subject`; a plain text `body`). No attachment, reply, forward, alias, HTML, signature, encryption, read receipt or scheduled send: the request asks to send a message, nothing more. It is the Mail module's fourth write: operation `send`, a separate grant that starts denied, also for policies stored before it existed, and that neither needs nor opens the read grants or the other writes. The admin matrix lists it as the seventh Mail level, *Messages, attachments, flags, moving, drafts and sending* (sending alone stays a custom choice), and every way of granting it asks the administrator first, with a warning that sending cannot be undone.

- **Account and sender:** only the user's own accounts (another user's account, or one delegated to the user, reads like a missing one). The sender is the account's own name and address, as the Mail app sends without an alias. The account must have a Sent folder of its own (`MailAccount::getSentMailboxId()`): the Mail app's send chain stops a message without one, so it is refused before the plan.
- **Plan:** a call without `confirm` reaches no server and writes nothing to the Outbox. It shows the whole message, the account and its Sent folder by id (the sender address and the folder path only with `mail.read`; without it, a note says the account's own address is used), and notes that the message may go to recipients outside the organization and cannot be undone, that "sent" means the account's SMTP server accepted it, not that it was delivered, and that each confirmation sends again. `plan_state` is an HMAC of the account, the sender name and address, the Sent folder (id and path) and the whole message; a confirmed call whose account, sender, Sent folder or arguments differ gets the new plan with a warning, nothing sent.
- **Send:** the confirmed call goes the way the Mail app's interface sends (`OutboxController::create()` then `send()`): `OutboxService::saveMessage()` stores an outgoing local message with its recipients, plain text and no send time, and `OutboxService::sendMessage()` runs the Mail app's send chain on it: Sent folder check, anti-abuse (which only alerts the administrator), SMTP through `MailTransmission::sendMessage()`, copy to Sent, replied flag. Bcc goes to the SMTP envelope only, never to the transmitted headers, in every supported release; the copy in Sent keeps the Bcc header from Mail 5.10.11 on, and a plan with Bcc says when the copy will not (an older Mail) or may not (a Mail version that cannot be read) show the Bcc recipients, who receive the message either way; that note is part of the plan state. Without a send time, the message is not one the background `OutboxWorkerJob` picks (`findDue()` needs one), so nothing in the path examined sends it again later; what the user does in the Outbox afterwards is theirs.
- **Outcome:** the answer follows the status the Mail app records, without claiming more:
  - `sent`: accepted by the SMTP server and copied to Sent, with the Message-ID; the Mail app removes it from the Outbox;
  - `sentNotCopied`: accepted, but the copy to Sent failed; it stays in the Outbox, do not send it again;
  - `refused`: an SMTP error the Mail app counts as a definite failure (insufficient storage, over quota, authentication required); it stays in the Outbox;
  - `notSent`: the Mail app did not hand it to the SMTP server (no Sent folder after all, or the save failed before any send);
  - `uncertain`: anything else, including any other SMTP error, a refused recipient among accepted ones (Horde stops before DATA, but the Mail app records an error and never sends that message again), a connection lost after the message, an unexpected status, an accepted status without the built message, or a failure of the send call itself, which may come after the acceptance.
  A message that was not fully sent stays in the Outbox of Mail with its id; nothing deletes it. Errors are fixed, translated messages, never a server's text.
- **Repetition:** the tool calls the save and the send once each and adds no retry and no deduplication of its own. The Mail app never sends again a message whose earlier send was unclear, but a new confirmation creates a new message, so confirming the same plan again sends again. Horde's own fallbacks inside the SMTP exchange stay as they are; one confirmation is not guaranteed to send exactly once when the connection fails.
- **Not set:** the Mail app's AI-generated header (`X-AI-Generated`, Mail 5.12 on) is left to its native default: a call through MCP does not prove the text was written by an AI.
- **Tests:** `mail-send-path.json` (`generate-mail-send-path.php`, `MailSendPathContractTest`) records from the SHA256-pinned 5.0.0 to 5.12.5 sources the send chain, the unclear-send guard, the definite-failure codes, the status values, the send-time filter of the background job, how Bcc reaches the envelope only and that Horde stops before DATA when a recipient is refused. The Mail cells send to a throwaway SMTP sink (`ci/mail/smtp-sink.php`) that runs inside the Nextcloud container, on its loopback only, relays nothing and answers by the recipients' local part (accept, 452, 530, 550, or a connection closed after the message); addresses are synthetic `example.com`/`example.org` ones.
- **Limits:** acceptance by the SMTP server is not delivery; a later bounce arrives as mail. A refused recipient among accepted ones is reported as uncertain, as the Mail app records it, although the sink shows no DATA. The cells run Mail 5.12.5; the other pinned releases are covered by the source fixture and the contract.

## Forms point editing

`forms_update_question` and `forms_update_option` require the independent, default-denied `forms.edit` grant plus native EDIT. They edit one existing active question (text, description, required and supported settings) or one option label, with an inert complete plan, `plan_state`, explicit confirmation and `confirm_shared` for shared impact. Native creation permission and MCP read/results/Files grants are not required. There is no adding, reordering, deleting or replacing lists. Explicit `unset_settings` is distinct from omission and native null; clearing a file-count limit is outside this slice.

A successful native PATCH reserves or renews a 15-minute editing lock and can identify the actor to other authorized editors. Editing a selected email question can make it ineligible for future confirmations and clear its selection, even when confirmations are already disabled. The plan explains this before confirmation. The operation does not change the enabled flag, reselect a question, send email or cancel queued jobs. Restoring validation alone does not restore a cleared selection; a later valid external selection can restore eligibility under native settings. Earlier responses are not rewritten. Concurrent edits and failures can leave partial or uncertain effects; receipts distinguish observed target, lock and selection state. No retry or rollback. Closed/expired forms remain editable if native permission allows; archived forms and another actor's active lock are refused. Text is never silently cut: question 2,048, description 4,096 and option 1,024 Unicode code points, with corresponding 4-byte limits. These are preventive and post-fetch composition limits, not a hard memory cap or an atomicity guarantee.

## Forms creation

`forms_create_form` requires the independent, default-denied `forms.create` grant and native creation permission. It creates a private form with a title/description and initial questions/options, through native Forms controllers in the exact supported pins 5.3.0, 5.3.7, 5.4.0 and 5.4.1. It accepts no existing IDs and does not publish, share, submit, send mail or edit an existing form. The full inert plan is required before confirmation with its `plan_state`; a changed plan requires review again. `forms.results` and `forms.edit` are not granted by creation.

Creation uses sequential native writes. A failure can leave an empty or partially configured form, or an uncertain result; receipts list only observed Forms changes. There is no automatic retry, rollback or deduplication. Editor links are credentials. In Forms 5.4.1, setting a title can rename/merge upload folders or remove empty folders matching the **new form ID** prefix. A native precheck refuses detected matches or read errors after the empty form was created, before its title/questions are applied. Concurrent changes can still trigger native folder effects. Every plan warns about this residual behavior; success is not a guarantee that Files stayed unchanged. The precheck adds no Files grant, directory, lock or backup.

Limits are checked before the first write: title 256, description 8192, up to 50 questions (text 2048/description 4096),200 options per category and 1000 overall,100000 text characters and 1 MiB canonical request/complete plan. Supported creation types are short/long/color/date/time/linearscale/multiple/multiple_unique/dropdown/file/grid/ranking; datetime is refused. Grid uses explicit row/column options. Only documented short validation and scale settings are accepted, never arbitrary native patches. Text and option lists are never silently shortened. Native arrays/readback may be allocated before checks; these limits are not a hard memory cap.

## Forms submissions

`forms_list_submissions` and `forms_read_submission` require the separate `forms.results` grant (denied by default), plus native Forms results access. Native owners/results collaborators can read all permitted submissions; other native prior submitters can read only their identified submissions, including historical access that survives share revocation. Anonymous submissions are not recovered as a signed-in user's own response. Respondent account IDs and names are omitted for every record; text may still contain personal data typed by respondents.

The projection contains only authorized answers to active questions and authorized files, without omitted placeholders, IDs, reasons or counts. Absence does not prove nothing was submitted. Uploads also require `files.read`, Files scope/Guests/hidden-tag checks and native READ through every alias in the actor's tree. Only current file metadata and a native viewer link are returned: no contents, download URL, owner-root fallback or new share. No read changes submissions or Files.

Submission pages default to 20, maximum 50; a complete bounded header universe of at most 50,000 is ordered before pagination, with a 50,001st header causing refusal. The cursor is authenticated but is not a snapshot of answer contents. UID `0` in own mode is refused before submission/schema lookups because of the native filter. Response budgets apply after projection: 2,000 questions/options, 2,000 answers per submission, 10,000 per page, 8,000 characters per string, 100,000 total and 1 MiB JSON. Oversized pages are refused whole, never silently truncated. Invalid UTF-8 in projected answers/schema refuses the affected page or single response without repairing bytes; answers outside that page or omitted by policy do not affect it. An unknown active schema type refuses even if the selected page has no answer to it. Native arrays can be allocated before these checks; there is no hard memory cap.

## Forms discovery

`forms_list_forms` and `forms_read_form` discover forms and read their question/option structure through the Forms app's own services, with `forms.read` (granted by default). Forms 5.3 or later must be enabled for the caller; 5.3 is this integration's support floor. These two structure tools expose no submissions or writes; the separate `forms.results` grant admits the submission tools above. `forms.create` independently admits the creation tool above; `forms.edit` independently admits the point editing tools above.

The list combines owned forms with the native shared list, rechecking access for each form. A form readable by ID may be absent from that list, including an expired/closed shared form or one open to all users but not shown in the sidebar. Pages use an authenticated cursor bound to the caller, page size and current authorized list; changes can require restarting the list. Text is marked untrusted. Only whitelisted fields and existing native links are returned: editor settings and public links require native edit permission, including for archived forms (the Forms UI hides its archived edit action). A public link is a credential: handle it accordingly. A results-page link does not grant MCP access to responses. No raw owner, shares, response counts or submission data is returned, and nothing is submitted or changed.

The direct service calls do not inherit Forms controller middleware (including its missing-form throttle, BruteForce and OCS/CORS dispatch). Native ACL remains in the services; MCP keeps its own input/call limits and the same missing/forbidden response. User strings are valid UTF-8, stripped of controls and capped at 8,000 characters, still plain untrusted data rather than HTML to execute or instructions to follow.

Responses report text cuts (8,000 characters per field, 100,000 across the response) and extra-setting lists cut to 200 items. Questions and options are never silently omitted: above 2,000 combined items or a 1 MiB serialized payload the whole response is refused. These are post-fetch response limits, not a hard memory cap on native Forms loading. At the cursor ceiling, `nextCursor` is null and `offsetLimitReached` is true even if more authorized forms exist. In admin, the writing preset excludes response reading; only the explicitly named combined preset or the individual `results` operation grants it. Existing policies are kept.

`limits` exposes the concrete response budgets; `truncation.fields` identifies each shortened field by schema path and original cleaned character count, and `truncation.lists` identifies each shortened extra-setting list and original item count. Identifiers (including question names), native permissions and URLs are not shortened; if protected data alone exceeds the JSON payload limit the entire response is refused. The candidate digest is computed before shaping and is never changed by these cuts. Payload bytes count the pretty-printed tool JSON, not the outer MCP transport envelope.

## Tables discovery

`tables_list_tables`, `tables_list_views` and `tables_list_columns` list what the caller can open in Nextcloud Tables: the tables, the views and the columns of one table or one view. They only read, behind the module's `tables.read` grant, which is granted by default like every read; the tools leave tools/list while Tables is off for the user, older than 1.0.0 (0.9 writes the read-only columns of a view, which the next slices must not inherit) or not an app the Guests app allows a guest.

- **Tables:** the user's own tables, the ones shared with them and the ones of their applications (contexts), from `TableService::findAll()` with `createTutorial = false`: its default creates a tutorial table for a user without any, a write no listing may do. Each table is authorized again for the user before anything of it is returned, and says whether the user owns it and whether its views are listed (`viewsListed`).
- **Views:** the views of the tables the user owns or manages, the views shared with the user and the views of the user's applications, each authorized again for the user, once each with where it was found (`via`). As in the Tables app, the views of a table shared without manage are not listed; `tablesWithoutListedViews` counts those tables, so the limit is never silent. A view shared without its table never brings the table.
- **Columns:** exactly one of `table_id` (needs read access to the table) or `view_id` (only the columns the view shows, with the view's read-only and mandatory settings). Type, subtype, mandatory flag and only the options the Tables app defines for the column's type (for a relation column, Tables 2.2 on, the `relationType`, `targetId` and `labelColumn` of its `customSettings`, never the related rows; display settings such as the width stay out); who created or edited a column is left out. A table or view out of reach reads exactly like a missing one.
- **Answers:** ids, titles, descriptions and links in the form the Tables app's own search builds (`#/table/<id>`, `#/view/<id>`); no owner id, share list or view filter. Text users wrote is cleaned and marked untrusted. Listings page with `limit` (default 50, at most 200) and `offset`, with `total`, `hasMore` and `nextOffset`. Every call passes the caller explicitly to Tables, never the session's user.
- **Tests:** `tables/tables-behavior.json` (`tables/generate-tables-behavior.php`, `TablesBehaviorContractTest`) records from the SHA256-pinned 0.9.12, 1.0.0, 1.0.10, 2.0.0, 2.2.2 and 2.3.2 sources the tutorial default, the serialized shapes, the context nodes and the row facts the next slices rely on; the per-major fixtures carry the Tables surfaces of 1.0.0 (NC31–33), 2.0.0 (NC34) and 2.2.2 (NC35). The opt-in Tables cell (`MCP_IT_WITH_TABLES=1`, `ci/tables/cell.sh`) installs the pinned release, seeds the scene through the Tables app's own API and checks every user against what the Tables app shows them, that no Tables row changes and that no tutorial table appears.

`tables_list_rows` reads the rows of one table or one view the caller can read, behind the same `tables.read` grant, the way the Tables app's own `RowService` does, with the user's filter, search and sort added on top:

- **Access:** the Tables app's own row permission (`PermissionsService::canReadRowsByElementId`) for the caller decides: owner, shares, manage of the parent table and applications (contexts); a share that only allows creating rows reads nothing. The call is refused unless the request's session belongs to the caller, because Tables formats team names with the session user.
- **View restriction:** through a view, only the columns it shows come back and its saved filter always applies, also when it filters on a column the view hides; that column never comes back, the user cannot filter, search or sort on it, and the user's filter is always combined with the view's, so it can never widen it. A saved filter or sort that names a column of another table, or that Tables would read differently from how it is stored, refuses the whole call.
- **Filter, search, sort:** `filter` is up to 8 groups (OR) of up to 8 conditions (AND) on visible columns or the meta columns (-1 id, -2/-3 created/edited by, -4/-5 created/edited at), with the operators and placeholders of the installed Tables release only (any other value starting with `@` is refused). `search` looks in the visible text columns and matches selection labels, which become option ids (a label is never found otherwise: Tables stores ids). The composed query is limited to 64 groups and 512 conditions, refused above that, never cut. Without `sort` the view's or table's saved sort applies; the row id always makes the order total.
- **Pages:** `limit` (default 25, at most 100) and `cursor`, an opaque value bound to the caller, the query and the state of the view: a change of the view between two pages refuses the old cursor, also a change of only the type, options or default of a hidden column its saved rules name. Pages are offsets, so rows written in between can move from one page to another. A cursor reaches offsets up to 100000: past that the page keeps `hasMore`, says `offsetLimitReached` and gives no cursor, and a narrower filter reaches the rest.
- **Answer:** each row has its id, the native authorship and dates, and `cells` as `{columnId, value}` of the visible columns with the native value (selection option ids, the related row id for a relation; nothing is resolved). Cell text loses only control characters other than tab and line breaks and direction marks, and comes back whole up to 20000 characters per cell and 100000 per page: a cell cut by either limit carries `truncated` and `totalChars`, and `truncatedCells` counts them. Everything is marked untrusted. Cells Tables did not store are absent, as natively.
- **Tests:** unit tests with strict doubles, the version gates of operators and placeholders checked against `tables-behavior.json`, and the Tables cell compares every user's pages, values included (a long text whole, a longer one cut and flagged), with `RowService` itself on Tables 1.0.10 (NC32) and 2.3.2 (NC35), with the database unchanged.

`tables_create_row` and `tables_update_row` write one row per call through the Tables app's own `RowService::create()` and `updateSet()`, in the form its controllers use, so its events, activity and notifications run. They sit behind their own `tables.create` and `tables.edit` grants, which start denied (also for policies stored before they existed) and are independent of each other and of `tables.read`:

- **Access:** the Tables app's own permission for the caller decides. Creating needs `canCreateRows` on the table or the view, so a share that only allows creating rows works, through the view too, without reading any row; updating needs read and update on the target, and through a view the row must be in it. The target is always the one given: a view never falls back to its table, and a row outside the view reads like missing. Federated tables and views (Tables 2.3) are refused, and the call is refused unless the request's session belongs to the caller.
- **Cells:** 1 to 100 `{column_id, value}`, each column once, only on the columns the table or the view shows, never read-only ones (Tables would drop those in silence). Each value is checked against its column before anything is sent: type and subtype, options, limits, mandatory columns, users and groups that exist (teams only where the Tables release checks them against the caller). What Tables' parser would lose in silence is refused instead: an unknown option, a date in another format, stars or progress out of range, null on yes/no, stars and progress (which Tables stores as false or 0), and null on a number before Tables 2.3.2, whose number mapper stores 0 for it. Stars and progress also respect the column's minimum and maximum, as Tables checks them for every number. A relation takes the related row id only, and only when the related table or view is readable for the caller.
- **Through a view:** Tables fills the columns the view hides that its saved filter sets with `is-equal`/`is-not-equal`; those values are checked first (first rule per column, as Tables does) and the creation is refused, without naming anything hidden, when one of them cannot be checked: a multiple selection, a user/group or a relation as hidden value. Nothing hidden appears in a plan, an error or an answer.
- **Plan and confirmation:** without `confirm` the answer is the plan, with each cell before (update) and after as Tables will store it, and a `plan_state` that binds the arguments, every accepted column, the view's settings and saved rules, the hidden values as resolved now, whether the table is the caller's and, for an update, the row's values whole; any change gives a new plan instead of a write. A table owned by somebody else needs `confirm_shared: true`, without naming the owner.
- **Results:** the answer holds only the cells sent, each with the value asked and the value Tables returned. Only a refusal before Tables is called says that nothing was written: any error out of `RowService` is reported as uncertain, never retried, since Tables validates and writes in the same call without a transaction and its listeners run after the write; repeating a creation can make a second row.
- **Tests:** unit tests with strict doubles, `tables/tables-write.json` (`tables/generate-tables-write.php`, `RowWriteBehaviorContractTest`) records from the five pinned sources what each parser makes of each value and the facts of the write path, and the Tables cell writes through Basic and Bearer on Tables 1.0.10 (NC32) and 2.3.2 (NC35) and reads every value back with `RowService`.

## File type policy

The optional allowlist starts **off**, including after an upgrade. Configure it in **Administration → MCP for Cloud → Data protection**. When active, it checks the final file name for MCP writes by any user, including an administrator: create and upload, checkout upload, edit/replace, version restore, copy/move (including folder descendants), batches, undo, and Notes. Notes is not exempt: include `md` and any other extension your notes use. Files scope, exclusion tags, native ACL, locks and operation grants still apply independently.

The rule uses the last ASCII extension, case-insensitively; names without an extension require the explicit administrator option. Ambiguous names (including trailing dots/spaces or a colon) are refused while the rule is active. It checks neither MIME type nor content, and does not eliminate prompt injection. An absent setting means off; an unreadable or invalid setting refuses the covered writes. Only mandatory internal `.bak` file backups and `.vcf` contact backups bypass this policy, through their backup services, never through a caller-selected extension or path.

Preview, confirmation and the write boundaries check the policy. A folder copy with the policy active first validates all descendants, then copies files from that checked list, rechecking identity, path and policy. Files added or renamed later are not copied; failure partway leaves a reported partial copy, which is not deleted automatically. Folder moves remain native after preflight, so a descendant inserted between preflight and move can travel with the folder. Undo follows the policy at the time it runs and preserves the receipt and data if refused.

The Contacts catalogs are own/shared, explicitly filtering any system principal. Reads use lazy adapters of the native backend, after the access filter; writes go through the core's Sabre (a separate CardDAV dispatcher and the existing `EmbeddedDavDispatcher` for VTODO). The session must match the actor and the principal is fixed at execution. `CalendarAccess` keeps VEVENT as the default and receives VTODO only in the Tasks module.

`GrantPolicy`/`GrantMatrix` include `contacts` and `tasks` with read/create/edit/delete, with writes off by default. Completing a task uses edit. `PreviewsWrites` produces the plan with no side effects; `WriteGate` requires confirm:true; shares require confirm_shared; a supplied ETag is checked and If-Match uses the re-read one. Editing a vCard preserves unknown fields, parameters, groups and the version; the plan includes every before/after property and the full vCard.

**Deleting a contact is PERMANENT in Nextcloud 33, with no trash bin.** Only after confirmation, `ContactBackup` saves the complete original vCard in `/MCP backups/Contacts/<catalog>/<name-or-uid>.<YYYYmmdd-HHMMSS>-<unique-suffix>.vcf`, in the account's time zone and in the actor's folder. It uses an application mutex, a random suffix and a collision check so it never selects existing files, and verifies the copy by re-reading the bytes. A failure prevents the CardDAV DELETE; the result reports backupPath. Re-import through the Contacts interface to recover. No backup is created in the preview.

**Task status:** create and edit accept `NEEDS-ACTION`, `IN-PROCESS`, `COMPLETED` and `CANCELLED`, as in the Tasks app. Status alone completes at 100% with a completion time (preserving it if already completed), reopens 100% at 99%, and starts `IN-PROCESS` at 1% when progress was zero or absent. `CANCELLED` preserves progress and the completion date and stays listed. An explicit `percentComplete` wins when consistent: `COMPLETED` requires 100, `NEEDS-ACTION`/`IN-PROCESS` reject 100, and `CANCELLED` accepts 0–100. Progress alone keeps its previous behavior, including reopening cancelled tasks. Create/edit plans show status and completion-date changes in the plan timezone. Status/progress based on PR #29 by Marc-Olivier Turgeon-Ferland (@mturgeonferland): [contribution](https://github.com/sintax-tech/mcp-for-nextcloud/pull/29).

Tasks use VTODO, include undated tasks, hide PRIVATE/CONFIDENTIAL ones of another owner and exclude objects in the trash bin. Reading recurrence is allowed; writes on series or tasks with attendees are refused. Fields that did not change stay in the iCalendar; completing writes STATUS/PERCENT-COMPLETE/COMPLETED, and lowering progress reopens the task. Deleting uses the CalDAV trash bin, refuses zero retention and checks deleted-at after the DELETE. Listings use limit/offset/nextOffset; completed tasks require include_completed. Categories (`CATEGORIES`) are free text: reading and listing return `categories`, merged from every `CATEGORIES` line (escaped commas respected), trimmed and deduplicated ignoring Unicode case, keeping the first spelling; create and edit accept `categories` (up to 50 items of 1–255 characters after trimming, no control characters, validated before any write): omitting it leaves every line untouched, `[]` removes them and a list replaces them with one multi-value line. `tasks_list_tasks` filters by `category` (exact, case-folded) before `offset`/`limit`, together with `include_completed`; the plan shows each name quoted, before and after. Categories of tasks hidden by CLASS are never read, filtered or shown. Subtasks (`RELATED-TO`, RELTYPE=PARENT or the RFC 5545 default) return `parent` (UID or null); create and edit accept `parent`: a UID replaces only the parent link (sibling, child and custom relations are kept), `null` removes it and omitting it leaves it untouched. The parent must be a readable task of the same calendar; a task cannot be its own parent or a subtask of its own descendants, and no task may end up deeper than 64 levels, the subtasks a reparenting moves included. `tasks_list_tasks` filters by `parent` (direct subtasks only) before `offset`/`limit`; the plan names the parent by title and UID, so parents with the same title stay distinct. Deleting or completing a parent leaves its subtasks unchanged. The hierarchy is checked on the state read for the plan and again at confirmation; confirmed MCP writes that set a parent in one calendar run one at a time, through the server's file locking (with `filelocking.enabled` off they are refused, while making a task top-level still works), but changes other CalDAV clients make at the same moment are not coordinated: if the parent chain read back after a write loops, the answer carries a warning.

There is no approval_id, approval record, occ requirement, extra service or auxiliary database. Descriptions/ToolGuideNotes stay in English; titles and messages use Translator with pt_BR/es/de parity (including the 47 German strings new in 1.1.0, already integrated). Tests cover plans, backup, ACL, grants, ETag, preservation and real Sabre dispatch; they do not prove the internal plugins on a real Nextcloud installation.

## Tools

Each tool only appears in `tools/list` and can only be called when the user has the grant for the operation and the required app is enabled for them. Grant and app are checked again on every call. ### Tool guide (`mcp_guide`)

`mcp_guide` (title **Tool guide**) describes the tools to the model itself, so it does not have to guess what each one does:

- **no argument** — one line per module with the tool titles, only for the modules available **to that user** (the same grant and app filter as `tools/list`: a disabled module or one without a grant does not appear);
- **with `module`** (`files`, `notes`, `calendar`, `contacts`, `tasks`, `deck`, `talk`, `people`, `logs`, `mail`, `tables`, `forms`, `polls`, `collectives`) — each tool of the module: description, whether it reads or writes, parameters with type, whether required, description, `enum` and limits, and the confirmations it requires;
- **with `tool`** — a single tool, with the module it belongs to.

The text comes from the real definitions (`ToolModule::definitions()`, `inputSchema`, `annotations` and `ToolPresentation`), so changing a tool's schema changes the guide: there is no second copy of the documentation to keep up to date. What the schema does not carry — how to find things, with which paths and IDs, and where writes stop — goes in `ToolGuideNotes::guideNotes()`, a short note per module, written next to the module. The response carries the same content in markdown and in `structuredContent`, and the tool is read-only: it reads definitions, it never runs a tool.

A module or tool the user cannot see is refused with a message that lists what they can use. There is no approval stored on the server: the rule of confirming before writing lives in the `instructions` of `initialize` and applies to every tool that changes something.

### Card completion and archiving

`deck_set_card_done` takes `cardId` and `done: true` to complete a card, or `false` to reopen it. `deck_set_card_archived` takes `archived: true` to archive it, or `false` to unarchive it. Both add status changes to the existing **deck.edit** capability; they introduce no grant or administration setting. Preview first, then repeat the returned `plan_state` with `confirm: true` and, on a received board, `confirm_shared: true`. `lastModified` is optional; a changed plan needs a new approval.

The native Deck service chooses the completion time. The returned `done` stays a Unix UTC timestamp or null; the client cannot choose it. On Deck 1.19, newly completing a card can move it to the configured done column shown in the plan. Reopening does not move it back. An already completed card keeps its timestamp and list: this tool does not retry a partial move. Unarchive a card before completing or reopening it. Archiving does not complete or delete it, and unarchiving preserves completion. To complete and archive, confirm the completion, read its result, then preview and confirm archiving separately. The calls are not atomic; native check-to-write races and partial results remain possible. Check the card before retrying an uncertain result. Guests retain native editing permissions.

### Deck: cards, boards and lists

The Deck writes use the grants `deck.create`, `deck.edit`, `deck.move` and `deck.delete`, all off by default, and `confirm_shared: true` on a board of another owner. The app always confirms with Deck whether the write was saved, even after a Deck error.

| Write tool | Grant | Behavior |
| --- | --- | --- |
| `deck_create_board` `{title, stacks?, confirm: true}` | deck.create | Creates a board of the user themselves with its lists and first cards (up to 20 lists and 100 cards), with an optional color. On a new board the assignees are the user themselves, because no one else has access. The plan shows the whole tree; if a step fails midway, nothing is undone and the result carries `created`, `failed` (with a safe reason) and `warnings`, so a retry does not duplicate anything. |
| `deck_create_stack` `{boardId, title, position?, confirm: true}` | deck.create | Adds a list to a board the user manages, at the end or at a position. |
| `deck_delete_stack` `{stackId, confirm: true}` | deck.delete | Deletes a list **only when it is empty**: any card, active or archived, refuses the call saying how many remain, and the count is redone at the confirm. It goes to the Deck trash bin. |
| `deck_delete_board` `{boardId, confirm: true}` | deck.delete | Same for the board, and only the owner can delete. If a card appears between the count and the deletion, the board comes back with Deck's own undo and the call is refused saying that nothing was deleted. |

`deck_create_card`, `deck_edit_card`, `deck_move_card`, `deck_delete_card` and the assignment of assignees use the same grants and the same confirmation; the assignees are board members.

After an error coming from Deck, every write re-reads the real state before answering: if the item was saved, the response is a success with the notice "Saved; Deck reported an error afterwards (notification or activity)"; if not, it is the usual error; and if the state cannot be read, the response is not an error and tells the assistant to read with `deck_list_cards`, `deck_read_card`, `deck_list_stacks` or `deck_list_boards`. An item found again only by similarity (same owner, same title, created a moment ago) comes as `confirmed: "probable"`, with a notice to check, and nothing else is written to it. Only the refusals the app itself makes before calling Deck (tool rules, session, conflicts, arguments) skip this re-read.

The "only when empty" deletion is not atomic: Deck does not look at the list's `deleted_at` when creating a card, so a card created by another request right after the second count may go to the trash bin together with the list or the board, from where it is recoverable. This is in the tool description and in the gateway.

### Deck labels, deadlines, dependencies and files

Labels, due time, native dependencies and a native file link are part of this release. The app does not imitate an API that is absent, and it does not upload, copy or delete the file.

- **Labels** (`deck_list_labels`, `deck_edit_card_labels`) are available on Nextcloud 32 through 35 when Deck is enabled. Proved Deck releases: 1.16.8, 1.17.7, 1.18.5 and 1.19.0. A label from another board is refused. The write changes only the requested ids.
- **Due time** is read and written with the card. Input is a local date `YYYY-MM-DD` (midnight in the account time zone), `YYYY-MM-DDTHH:MM` or `YYYY-MM-DDTHH:MM:SS` in that time zone, or a time with `Z` or `±HH:MM`. The card returns `duedate` as the local date and `dueAt` as an ISO time with the account offset. There is no IANA field. `overdue` stays day-based. A local time that does not exist (a daylight-saving gap) is refused. `dueBefore` stays date-only.
- **Dependencies** (`deck_read_card_dependencies`, `deck_add_card_dependency`, `deck_remove_card_dependency`) appear only on Nextcloud 34 and 35, proved with Deck 1.18.5 and 1.19.0. On Nextcloud 32 and 33 those tools are absent. Direction is outgoing: `cardId` is the origin and `targetId` is the card it depends on. `assignDependentCard(A, B)` stores B in the dependent cards of A. Self-relations and cycles through readable cards are refused. A relation to a card you cannot read is omitted, with no count and no id. A cycle through those cards cannot be detected. A concurrent change between the last check and the native write can still create a cycle.
- **Files** use the native Deck share (share type 12) on Nextcloud 32 through 35. `deck_list_card_files` and `deck_unlink_card_file` are on all four versions. `attachmentId` is the share id and is not the `fileId`. Listing needs `deck.read` and `files.read`. Unlinking needs `deck.edit` and `files.read`, keeps the original file, and an editor of the card can remove a visible association created by someone else. Independent shares may keep access. A missing association and one you cannot see share one refusal: no count and no handle. Opening the card in Deck is the generic next step, and that answer does not confirm that a hidden association exists. This app does not unlink a hidden file. A folder you can already see, and an archived card or board you can already see, are refused in plain language.
- **Linking** (`deck_link_card_file`) needs three grants that already exist: `deck.edit`, `files.read` and `files.share`. Reading and unlinking do not need `files.share`. The plan shows the file path, the owner, whether this is a reshare, the current recipient total, a limited list of names, the shares you created, and read-only access (READ=1) for current members and for people who later join the board, a group or a team (a Nextcloud circle). Unlinking that share removes it for everyone. Access is checked only when the link is created. The server does not revoke the link afterwards. A policy turned on later, a change of board, group or team membership, and the moment between the last check and the native share can change who can read the file. The plan hash does not make the share atomic. The server does not attest human consent. A new plan or an uncertain result is not a record that the write succeeded or that a person approved it.
- **Refusals** use the same answer when the facts cannot be read. A link is refused for a Guest (the hide-users override is not applied to this OAuth session), for group-only sharing, when group sharing is off and the board includes a group or a team, when internal expiry is mandatory, when sharing or resharing is off, and when a recipient is not a fully resolved local user, group or team. Those answers do not ask you to change a setting or to sign in another way.

### Optional Calendar diagnostics (`occ mcp:calendar-selftest`)

It is not a prerequisite: nothing depends on it for the tools to appear or work, and it neither writes nor hides anything. It is an optional, advanced diagnostic tool for those who administer the server and want to see, step by step, the real CalDAV responding. Run it at the Nextcloud root as the web server user. The organizer UID must have an enabled account, a valid email and Calendar enabled; the `dav/calendarRetentionObligation` retention must not be `0` (the cleanup would be permanent, so it fails before creating any object).

```sh
sudo -u www-data php occ mcp:calendar-selftest ORGANIZER_UID
```

Each run creates two calendars with URIs `mcp-selftest-...-a`/`-b`, touches only events created by it and moves those calendars to the trash bin at the end. Without options, the three optional proofs show `NOT TESTED`. To exercise internal invitations, transfer and ACL:

```sh
sudo -u www-data php occ mcp:calendar-selftest ORGANIZER_UID \
  --attendee-uid ATTENDEE_UID \

  --acl-probe-user NO_ACCESS_UID
```

This run has effects on both users (internal invitation, cleanup CANCEL, Activity on the shared calendar) and removes only items with the UID generated by the test. It is not proof of SMTP.

| --- | --- |
| `preflight`, `calendars` | Valid account/app/retention; two MKCALENDAR HTTP 201 visible. |
| `create` | HTTP 201, UID and ETag re-read, sync-token increased. |
| `suppression-create`, `suppression-update` | PUT 201/204, ATTENDEE `@example.invalid` without SCHEDULE-STATUS; SEQUENCE went up. |

Notes tools require the Notes app enabled for the user. Reading starts allowed; creating, editing, moving and deleting start denied until the administrator grants them. There is no timeout of its own: reading is local to PHP and the byte limit protects against large files. Slow external storage is limited to PHP's `max_execution_time`.

### Images (`files_image_view`, `files_images_view`, `files_image_search`)

Read-only tools (`files.read`) that honor the user's folder and the native Nextcloud permissions:

- **`files_image_view`**: Generates a downscaled preview of the image through `OCP\IPreview` with a configurable maximum dimension (`max_size`, default 1568 px). If the preview exceeds the byte limit (configurable in `image_single_max_bytes`, default 1 MB), the resolution is progressively reduced until it fits. If no preview is available for the format, it falls back to the original file for common formats (JPEG, PNG, WebP, GIF) as long as it is within the byte limit. Returns an `image` block (base64) and a `text` block with metadata (`path`, `mime`, original dimensions if available, `size`, `mtime`, `access`, `captured_at`).
- **`files_images_view`**: Takes a list of `paths` (up to 6) or a `folder` (with `limit`, default 6) and returns multiple image blocks under a shared budget (`image_batch_max_bytes`, default 4 MB). Files that exceed the budget or fail are listed in the `skipped` summary.
- **`files_image_search`**: Searches files with mimetype `image/%`, with optional filters by text (`query`), folder (`folder`), ISO 8601 modification range (`modified_after`/`modified_before`) and system tag (`tag`, including the automatic tags generated by the Recognize app). Returns only metadata ordered by `mtime` descending. An unknown or hidden `tag` and a failure of the tag search are errors ("Tag not found in Nextcloud.", "Failed to search images in Nextcloud."), never an empty list; `[]` means no image matched.

Invalid arguments, a nonexistent tool or one without a grant return the JSON-RPC error `-32602`, without distinguishing the reason. Execution failures return `isError: true` with a generic message, without physical path, content or stack trace.

## Resources (MCP Resources)

The server announces the `resources: {}` capability in both the legacy `initialize` flow and the modern `server/discover` flow.

### Package rule: no macOS metadata

A package with `._*` (AppleDouble), `.DS_Store` or PAX headers with `com.apple.*` xattrs is refused by the App Store and may break the installation. Therefore:

- tar runs as `COPYFILE_DISABLE=1 tar --no-xattrs --exclude='._*' --exclude='.DS_Store'`. `--no-xattrs` was added because, without it, bsdtar writes `com.apple.provenance` in the PAX headers of every entry;
- the check is done by `scripts/check_package.php`, which reads the tar with its own PHP reader, because macOS's `tar -tzf` hides the `._*` entries and `PharData` does not expose the PAX headers;
- the package is refused, deleted, and the script exits with code 1, if it has:
  - a `._*` or `.DS_Store` entry;
  - a PaxHeader entry or extended PAX header;
  - a top-level entry other than `mcp/`;
  - a package in `vendor/` outside the runtime dependencies (`smalot/`, `symfony/polyfill-mbstring/`, `composer/`, `autoload.php`), such as `sabre/*` or `symfony/console`;
  - a script or style referenced by `Util::addScript('mcp', X)`/`Util::addStyle('mcp', X)` missing from the package.

To check a standalone package: `php scripts/check_package.php build/mcp-<version>.tar.gz`.

## Server log

`logs` module, read-only and for IT only: `logs_list` lists the `nextcloud.log` entries from newest to oldest and `logs_analyze` summarizes the same window.

- **Single source:** reads the current log file published by the official `ILogFactory::get('file')` / `IFileBased::getLogFilePath` API, read-only, through one handle and fixed 64 KiB reverse blocks. No caller-selected/config-derived path, shell, `occ` or rotated `.1` file. A non-file logger is refused. Ordinary lines retain the native `loglevel` eligibility and JSON decoding semantics.
- **Double gate:** `LogsAccess` (`RestrictedModule`, checked by the `ToolRegistry` before the grant, in `tools/list` and in every `tools/call`) accepts a Nextcloud admin or a member of a group in the versioned state `mcp_logs_groups`; then the `logs.read` grant, which starts off. With `log_type` syslog/errorlog/systemd the tools disappear and the column leaves the matrix; the admin block explains it.
- **Ceiling and budget:** the existing 5,000 eligible entries per call, 20,000-entry depth ceiling and page limit (default 50, max 100) remain. A cooperative monotonic **1,000 ms** deadline covers offset seeking, block reads, decode and filtering. `scan.timeBudgetReached` with `truncated` means a resumable pause: continue using `scan.nextOffset`, even with zero matches. If seeking itself exhausts time, the unchanged requested offset is returned, without consuming entries. `scan.budgetReached` retains its depth-ceiling meaning and null continuation. A bounded JSON decode or blocking filesystem call can finish after the deadline; this is not an interruptible OS timeout. The response also keeps scanned, oldestScanned, malformed and unparsed. Numeric offsets remain relative to the current file on each call: appends/rotation between calls have the existing limitations.
- **Oversized lines:** above **16 MiB**, a line is not decoded. It occupies one explicit offset slot, increments `scan.unparsed` and is reported as `{offset, bytes, reason: "oversized"}` in `scan.oversized`. Its level cannot be verified, so this exceptional slot is counted independently of `loglevel`; normal offsets still count eligible entries. No content is invented and no oversize is silently discarded. Memory keeps a capped line buffer plus one block and the matching entries, rather than the entire candidate window.
- **`since` does not end the read:** the core stamps each entry with the `microtime` of when it builds it, and concurrent workers write in any order. An entry before `since` is skipped and the window goes on to the end; while there is budget, `nextOffset` points to the end of the window, and the response never claims that nothing older exists.
- **Dates:** `since`/`until` in ISO 8601; the entry's `time` is read in the `logdateformat`/`logtimezone`; if it does not match, the entry is left out under a date filter and counts in `scan.unparsed`.
- **Output:** envelope `{"untrusted_log_data": true, "notice": …}` after a fixed notice; controls, ANSI and invisible marks removed; IP masked (`a.b.x.x`, IPv6 /48) also inside messages; IPv6 with CIDR is also reduced to /48; before the regexes, each field has a 16 KiB limit and the token that crosses the boundary is discarded whole, so half an IP is not exposed; after the mask, the message is cut at 2,000 characters; an exception with class, message, location and 10 frames `class->function` + `file:line`, without `args`.
- **Analysis:** totals by level/app/user, top 20 signatures (quotes, paths, UUIDs, hashes and numbers become `#`), top 10 URL paths (without query; the WebDAV path folded into endpoint + account), top 10 user agents and a histogram per hour.
- **Audit:** the `ToolRegistry` hands every call to a `RestrictedModule` with the result (`denied` by role or grant, `invalid`, `read_error`, `success`), and the module fires `CriticalActionPerformedEvent`, recorded by admin_audit when active: `MCP logs read by %s: tool=%s filters=%s` only for a read actually done and `MCP logs request %s for %s: tool=%s filters=%s` for the others, never a denial as a read. Of the arguments only the known filters remain, scalar and truncated. In the app log, a denial is `warning` and the rest `info`. If the audit itself fails (dispatcher or logger), the registry writes "MCP audit failed" without arguments: a denied, invalid or errored call keeps the original response; a successful read does **not** deliver the data and answers a generic error. If the fallback logger also fails, the exception is ignored and the same behavior is preserved.
- **Privacy (1.0.6):** with hidden tags configured and the option **Hide the text of log messages** on (default), the text of messages and exceptions, the user agent and the method outside the known verbs become `[hidden]`, the URL keeps only the fixed route prefix and `contains` is refused; see [Hidden tags (1.0.6 and 1.1.0)](#hidden-tags).
- **Admin API:** `GET`/`PUT /apps/mcp/api/logs-access` (`{groups, previous, version}`, lists of strings and a non-negative integer version), admin-only with CSRF; GET returns groups and version from the same snapshot. A new nonexistent group gives 400 without writing. A packaged native migration creates the own table `mcp_logs_groups`; the first read imports and canonicalizes the old `logs_groups` of the appconfig and removes the old key, without overwriting an already migrated state. If the cleanup fails, the read keeps the table's state and tries to remove the key again on the next reads. The `QBMapper` reads the table directly and writes with CAS (`UPDATE … SET groups=?, version=version+1 WHERE id=1 AND version=?`): zero rows changed or a busy lock gives 409 with the current state. The exclusive lock of `ILockingProvider` is an extra layer: with `filelocking.enabled=false`, the provider becomes Noop, but the CAS still protects against a revocation undone by concurrent saves or old appconfig snapshots. Ids are text: `"1"` and `"01"` are two groups.

## Locked file

Notes and Files writes in the face of `files_lock` (an app up to Nextcloud 34, built in on 35). Common service: `Tools/Common/LockAwareWrite` (`ILockManager::isLockProviderAvailable` + `getLocks`), without importing files_lock classes.

- **Who blocks:** a manual lock of another person (`TYPE_USER`), an app lock (`TYPE_APP`, Text or Office) and a WebDAV client lock (`TYPE_TOKEN`). APP and TOKEN refuse even the owner. The user's own manual lock lets them write and is kept, as in the Files app; on the checkout-by-link route, which has no user session, it also refuses, as files_lock does there. Without a provider, nothing changes.
- **Where:** before the share confirmation and the backup, and again right before each write (`LockAwareWrite::run`): `putContent`, move, rename and delete of a note, each item of a batch and of an undo, version restore, checkout upload, content of a new file and backup copy. The storage's refusal (`ManuallyLockedException`) is also captured and explained (`capture`, used in the copy, which only reads the source).
- **In doubt, refuse:** a lock query that fails refuses; a folder being moved is checked with everything the user reaches inside it, up to 5,000 items (`LockAwareWrite::TREE_LIMIT`), and a listing larger than the remaining budget refuses without reading the lock of the items. The listing of each folder is read whole before this comparison: `getDirectoryListing()` has no limit on 32–35 and `Folder::search()`, which has one, queries the file cache and does not reproduce the listing. A file hidden by the `VisibilityGuard` is not named and the plan's `lock` carries only `blocking: true`.
- **Plan (`confirm` absent):** it does not refuse; it adds `lock` and a `file_locked` notice in `warnings`. In `files_move_batch` the locked item goes to `denied`, and the whole batch is refused.
- **Version restore:** with a provider, it reads the version through `IVersionManager::read()` and writes through the file, without the core's `rollback()`, whose `handleAppLocks` repeats the write in the Text/Office scope. The guarantee about the replaced content is the backup in `/MCP backups`.
- **Checkout:** lock → 423. Before the link is spent, the link remains valid; afterwards, the response cites the backup and asks for a new `files_checkout`.
- **Message:** app or person (display name; never UID, app id or token), since when, until when and what to do, in en/pt_BR/es/de. A refusal without a safe correlation by the token keeps the holder unidentified. Log only at `debug`, without path or token.
- **Limit:** TOKEN is only refused by the MCP check, which is not atomic with the write, and the files_lock `getLocks()` answers from the request cache, including a negative one: a TOKEN lock created after the first query of the file in the same request is not seen. USER and APP locks are also enforced by the files_lock storage, which reads the lock again at the write, except on deleting or renaming to/from Markdown a Text document: the Text listener (`BeforeNodeDeletedListener`/`BeforeNodeRenamedListener`) runs before the storage and does `resetDocument(..., true)`, releasing the APP lock; a Text APP lock created after the MCP query is released that way and does not prevent the deletion or rename. The MCP only refuses the lock the provider observes. files_lock offers no atomic lock acquisition (separate query and insert, `file_id` without a unique index), so the app takes no lock of its own.

## Hidden tags

`VisibilityGuard`, `FolderExposureGate` and `OutputReferenceFilter` apply system-tag exclusion across every access path of the connector: reading, search, listing, tree, images, versions, notes, Talk, Tasks, resources, checkout, writes and undo. See [`tests/Unit/Contract/EXCLUSION-MATRIX.md`](tests/Unit/Contract/EXCLUSION-MATRIX.md) and [`tests/Unit/Contract/FOLDER-EXPOSURE.md`](tests/Unit/Contract/FOLDER-EXPOSURE.md).

- **Inheritance and mount-root resolution (1.1.0):** a tag on a file or folder covers the node itself and all descendants at any depth. An item reached through a local share inherits the tags of the owner's source folder chain (storage `OCP\Files\Storage\ISharedStorage` + id in the filecache, resolved once per shared root). Team folders (`groupfolders`), external storage (`files_external`) and federated shares follow the mounted path, without querying the owner; a federated share is checked only by local tags. Above the root of a mount, Nextcloud returns a parent folder that carries another storage's id (`-1` above an external storage); `VisibilityGuard::parentOf()` resolves the folder above a mount root again by its path, so files on external storage and individually shared team-folder files walk up to the real user root instead of failing closed.
- **Folder exposure gate (`FolderExposureGate`, 1.1.0 — D7):** while at least one exclusion tag is configured (or the configuration cannot be read), MCP refuses to share a folder (`files_share` with user, group or public link), copy a folder (`files_copy`) or move a folder to another parent directory (`files_move`, `files_move_batch`, `files_undo_batch`), and masks `url: null` on existing folder public links in `files_list_shares`. Visibility is checked first (an excluded folder or unreadable tag configuration returns `CommonMessages::notFound()`); only a visible folder receives the translated D7 refusal instructing the user to perform folder operations in the Nextcloud Files UI. Individual files, renaming a folder within the same parent directory and `files_unshare` remain allowed.
- **Structured reference filtering (`OutputReferenceFilter`, 1.1.0):**
  - **Talk:** `talk_attach_file` and `talk_quote_file` check the caller's view of the file and refuse a file that is excluded or outside the caller's Files scope with `notFound()`; `talk_read_messages` checks each room share attachment the same way and returns `attachmentId: null` when its file is refused. The scope step is `FilesReferenceScope` (1.1.0), the Files scope of the operation's user.
  - **Every resolved alias must pass (N1):** `OutputReferenceFilter::fileIdVerdict()` resolves the id with `getById()` and `allowsNodes()` requires *all* the nodes returned to pass the Files scope and the exclusion, with at least one of them readable. So a reference resolved **by id** — a Talk room share, an `ATTACH` carrying `X-NC-FILE-ID` — is judged by every alias of that id in the caller's tree, while the Files tools decide by the path that was requested; a file the user also reaches through a restricted alias must not leak through Talk or Tasks. A reference resolved **only by path** takes the other route: `pathVerdict()` resolves a single node and calls `allowsNodes($userId, [$node], null)`, so a DAV URL without an id and a `FILENAME` parameter check only the node at that path. A refused id removes the `ATTACH`; an unresolved `FILENAME` parameter is stripped from it, and the `ATTACH` is still evaluated by its own content or URL; inline `BINARY`/`BASE64` content is data, not a reference, and stays.
  - **Tasks:** `ATTACH` properties pointing to local Nextcloud URLs (`/f/<id>`, `/s/<token>`, `/remote.php/dav/files/<uid>/<path>`, `/remote.php/webdav/<path>`, with or without `/index.php`, on any host, IP, loopback or alias) and Calendar `X-NC-FILE-ID`/`FILENAME` parameters are stripped from `tasks_read_task` and from the plans and results of the Tasks write tools when the referenced file is excluded or outside the caller's Files scope (the server's stored VTODO object keeps every `ATTACH` on edits); `tasks_list_tasks` carries no raw calendar; public folder links are stripped while exclusion tags are active.
  - **Calendar and Deck:** Calendar event outputs carry no `ATTACH`/file URLs, and Deck card outputs omit `attachmentCount` to avoid revealing files outside the caller's scope or hidden by exclusion tags.
- **Deck labels:** `deck_list_labels` lists labels of a readable board. `deck_edit_card_labels` adds/removes only the requested IDs, preserving all other labels. It requires `deck.edit`, an editable active card and labels from its own board. Preview first; repeat its `plan_state` with `confirm: true` (and `confirm_shared: true` on another owner’s board). A changed state needs a new plan. Partial or unverified results must be checked in Deck before further changes.
- **Native Deck dependencies:** `deck_read_card_dependencies` requires `deck.read` and appears only on NC34/35 with the compatible native API (container-proved Deck1.18.5/1.19.0; newer patches require the version/API checks). It reads outgoing relations: native `assignDependentCard(A,B)` means B is in A.dependentCards, represented as origin A → target B; this does not automatically block tasks. Only readable nodes/edges appear, ordered by IDs, with no hidden count or handle. No pagination: the whole readable reachable subgraph must fit 100 nodes, 500 edges and shortest-path depth 20; otherwise the call refuses. Cycles through unreadable cards cannot be detected, so the visible graph does not prove the global graph acyclic. `deck_add_card_dependency` / `deck_remove_card_dependency` require `deck.edit`, origin EDIT and target READ, including removal. Each call changes only A→B; both cards and boards must be active. Preview + `plan_state` + `confirm:true` (and `confirm_shared:true` when needed); self-relations and detectable cycles are refused. Changed state needs renewed approval; duplicate/absent removal performs no write. Another change between the final check and the native write can still create a cycle. Check uncertain results in the UI before retrying.
- **Deck file associations:** `deck_list_card_files` requires `deck.read` + `files.read` and lists only native `file` associations whose nodes pass Files scope, exclusion tags and READ. `attachmentId` is a share ID, distinct from `fileId`; legacy uploads and folders are unsupported. `deck_unlink_card_file` requires `deck.edit` + `files.read` and an active editable card/board. Preview and confirm with `plan_state` + unchanged `file_state` (and `confirm_shared` when needed). Unlinking preserves the original and independent shares, revoking this association for all current/future members even when another member created it. Invisible and nonexistent associations have the same refusal, without counts or handles. An absent association is a no-op only with the valid original receipt and the original file still visible; otherwise request a new preview or use Deck. A change between the final validation and native unlink remains possible. Linking a file is covered in [Deck file links](#deck-labels-deadlines-dependencies-and-files): it uses deck.edit, files.read and files.share, and the check applies only when the link is created.
- **Fail-closed:** a configuration that cannot be validated (the manager failing while the list is saved, or a stored value that is unreadable or invalid) keeps the previous configuration and refuses access, instead of turning the protection off; the admin page warns and offers the repair button, and saving the empty list asks for confirmation. Visibility decisions are invalidated after moving, creating or copying, so no old state is answered.
- **Logs:** with tags configured and the option **Hide the text of log messages** on (default; key `logs_hide_file_names`), the log tools hide the text of messages and exceptions, the user agent and the method outside the known HTTP/WebDAV verbs, reduce the URL to the fixed route prefixes and refuse the `contains` filter, which would match the hidden text. Turned off, the log comes back complete for diagnosis — the option exists because IT teams read exactly those details to map problems. The app's own error log records only the class and the code of the exception, never the message, on any installation.
- **Declared limits:**
  - The protection applies only to this MCP connector, not to other AIs, other connectors or the Nextcloud web UI.
  - Federated shares are checked only against local system tags on this server.
  - Free-text mentions of a file name in Talk messages, event descriptions, task descriptions or Deck cards are not redacted, and a bare file name written by another app into a structured log field is not redacted when log text hiding is off.
  - **External storage mounted twice with different roots:** mounting the *same* external directory twice with different roots (e.g. `/ext` and `/ext/Open`) creates two distinct Nextcloud storages with different `fileId`s; a tag on one mount does not cover reads through the other. Two mounts of the *same* root (alias) share `fileId`s and are protected together.
  - **Exclusion list cache window (~3 s across processes):** changes saved via the admin UI apply immediately on that web node. Changes made via `occ` or on another web node can be served stale for a few seconds because Nextcloud keeps the app config in its local cache for 3 s (`AppConfig::LOCAL_CACHE_TTL`, the same on Nextcloud 32–35); measured in the integration suite, the new list took effect after 2.7 to 3.9 s.

## Group permissions and policy lifecycle

Group permissions (`mcp_group_grants`) and the authorization lifecycle (`PolicyResolver`, `PolicyWriter`, `GroupSourceClassifier`, `GroupLifecycle` and `CauseProcessor`) allow administrators to grant *Can connect* (`_system.eligible`, the `eligible` preference) and module operations (`<module>.<operation>`) to native Nextcloud groups without losing immediate revocation guarantees (see [Individual overrides, preview and access inspector](#individual-overrides-preview-and-access-inspector) for the reset of overrides and the inspector).

- **Precedence and grant-only semantics:** groups only grant (`Allow`); they never deny or narrow. Individual user overrides (the `eligible` and `grant_<module>_<operation>` user preferences of app `mcp`, with values `'1'` = Allow or `'0'` = Deny) always override group grants. When no individual override exists, the user inherits `Allow` if at least one active, trusted group they belong to holds the grant in `mcp_group_grants`; otherwise the module default applies (`Allow` for `read` except `logs.read`; `Deny` for all writes and for `_system.eligible`).
- **Trusted group classification (`GroupSourceClassifier`):** a group can grant MCP permissions only when Nextcloud resolves it through **a single group backend** that implements `OCP\Group\Backend\INamedBackend` and reports `getBackendName() === 'Database'`. Groups backed by LDAP, SAML, third-party apps, an unnamed backend or multiple backends at once are not trusted and cannot grant MCP permissions; administrators must grant permissions to their members individually.
- **Lifecycle states (`mcp_group_life`) and uncertain access (`needs_confirm` / `unknown`):**
  - Each group with policy state has a row in `mcp_group_life` (`group_key` SHA-256 of `group_id`, `group_id`, `state`, `gen`, `policy_rev`).
  - If a group creation or deletion is rolled back or observed inside a foreign database transaction, or if a group with saved grants loses its single `'Database'` backend classification, its state becomes `needs_confirm` (**awaiting confirmation**). While in `needs_confirm`, the group grants nothing, and its `mcp_group_grants` rows are preserved until an administrator clicks **Confirm current policy**, which saves the group's current set again through `PUT /apps/mcp/api/group-grants`, from a preview.
  - `PolicyResolver` returns `unknown` (HTTP 503 on the MCP endpoint, without revoking OAuth tokens) **only** when a user's eligibility or tool grant depends exclusively on a group in `needs_confirm` and no individual `Allow` override or other active trusted group grants the permission. In `tools/list`, a tool whose grant resolves to `unknown` is omitted rather than failing the whole list (and for tools with alternative grants, one known `Allow` grant suffices).
  - A user's pending recheck causes (`mcp_auth_recheck`) are processed before the policy is read (`CauseProcessor::preflight`: called by `McpController` for Basic and session identities, and through `TokenOwnerGate::preflight` by `AccessTokenAuthenticator` for Bearer tokens). Only when a cause cannot be classified or consumed (`PolicyUnavailable`) does the request answer 503, whatever the user's other sources of access.
  - When an administrator removes *Can connect* (`_system.eligible`) from a group (or when a group is deleted), if `PolicyWriter` cannot verify remaining eligibility for every credential holder in that group, the write is refused (503) without modifying the database so the administrator can retry.
  - Deleting a group runs in this order: the Before of the deletion first sets the lifecycle to `needs_confirm` (`GroupLifeMapper::markSuspended()`), then lists the members that hold credentials and records their causes, and only then sets `pending_delete` (`markPendingDelete()`) when every cut was recorded; the job purges only `pending_delete`, so a failure midway leaves the group suspended with its rows intact, and what it granted answers `unknown` (503). A new connection that depended on the group renews its state and is refused if the suspension wins. Residual limit: if the suspension loses the race three times, a connection made in that interval is valid again only if an administrator explicitly confirms the group's policy.
  - A member's exit from a group is recorded even when the user has an individual `Allow`; a reset running at that moment is refused with a conflict and, repeated, cuts.
  - Resetting an individual `Allow` of eligibility to `Inherit` cuts credentials only when the user actually loses eligibility; if a group keeps the user eligible nothing is cut, and when what the user inherits is unknown the change is refused with nothing written and nothing cut.
- **Serialized policy commits, generations and foreign transactions:**
  - `PolicyWriter` serializes policy mutations through the single row of `mcp_policy_state` (`id = 1`, `revision`, `lock_seq`, `auth_epoch`). OAuth codes, tokens and spent refresh tokens carry `(auth_global_epoch, auth_gen)`, checked against `mcp_policy_state.auth_epoch` and the user's tombstone row in `mcp_auth_users` (`issue_seq`, `revoked_below`).
  - Event listeners registered in `Application.php` never execute SQL while `IDBConnection::inTransaction()` is true (a failed query inside a foreign transaction would abort Nextcloud's own transaction on PostgreSQL). Instead, causes are queued in memory (`DeferredQueue`) and processed by a shutdown function once the caller's transaction is over; what is still pending stays in `mcp_auth_recheck` and is handled by the background job `ReconcileJob` (every 15 minutes), and the app stays correct when the job does not run because each request of a user first processes that user's causes.
- **Guarantee ("by delivered events") and declared limits:**
  1. **Same-`GID` group delete + recreate when signals are lost:** if the PHP process terminates before deferred processing runs, during the window between the caller's commit and deferred processing (including delete + recreate within the same transaction), or with a foreign transaction still open at process exit, a recreated group with the same `GID` may inherit the old group's policy, and concurrent requests in that window may still evaluate the old policy.
  2. **Backend name `'Database'`:** Nextcloud does not authenticate or reserve `INamedBackend::getBackendName()`. Any admin-installed group backend returning `'Database'` is treated as the native database backend.
  3. **Unobserved backend round-trip:** if a group's backend changes away from `'Database'` and back between two observations, the intermediate change is not detected.
  4. **In-memory caches in long-running processes (`occ` / workers):** `Database::groupExists` keeps a positive cache, `AppManager` keeps its own cache of enabled apps, and `IUserManager::get` returns memoized `IUser` objects. Web requests run in a fresh PHP process per request; long-running CLI commands or workers may observe cached state until they exit.
  5. **Decided exception on undated foreign-transaction user causes:** in doubt, the app revokes OAuth credentials. The single intentional exception is when a user cause is captured inside a foreign open transaction (undated) and the user is still eligible when `CauseProcessor` processes the recheck later: in that case, neither old nor new credentials are cut.
  6. **Cost on large installations (measured, 1.1.0):** deleting a group and taking *Can connect* from a group cost time proportional to the number of users who have already connected an MCP client (not to the size of the group): with about 1,000 of them, roughly 9 to 19 seconds in one request, and the preview of taking *Can connect* away about the same; opening a group of 5,000 members takes 1.5 to 2 seconds. Figures measured on one machine with a local database; on slower hardware or a remote database they grow in proportion.
- **Upgrading, incidents and rollback:** upgrading from 1.0.8 runs the native migrations (`Version001100Date20261014000000` through `Version001100Date20261016000000` and `PolicyStateSeedStep`) automatically. **Downgrading the app code to 1.0.8 on the same database is not safe**, because 1.1.0 revokes OAuth credentials logically and removes them later, so a credential revoked in 1.1.0 and not yet removed may be valid again in 1.0.8 (do not do it: see below). After group grants or per-resource scopes have been used it is worse: 1.0.8 ignores `mcp_group_grants`, ignores `(auth_global_epoch, auth_gen)` on OAuth tables (so tokens that were cut only by generation or epoch may be accepted again), and ignores `mcp_scope_modes` / `mcp_scope_items` (so users restricted to specific resources regain access to all of them). Going back from 1.1.0: move forward to a fixed 1.1.x release (keeping the 1.1.0 schema and epochs); never put only the 1.0.8 code over the 1.1.0 database or restore database and code from different backups. If you must go back, restore the whole installation (code, configuration, database and data directory) from the same backup taken before 1.1.0, in maintenance mode and following Nextcloud's own restore procedure, then switch the MCP service off in the admin settings: that removes every OAuth connection and, while it is off, refuses app-password (Basic) clients and checkout links (`canConnect`). App passwords are Nextcloud's, not removed by the app, and the restored database brings back those revoked after the backup, so each MCP user must revoke the app passwords used with the MCP in *Personal settings → Security* before the service is switched on again (users who have not should stay ineligible). Issued checkout links expire within 15 minutes (`CheckoutService::DOWNLOAD_TTL` 300 s, `UPLOAD_TTL` 900 s), so keep the service off at least that long; then switch it on and reapply what changed after the backup, revoked app passwords and disabled accounts included. A restore loses everything done after the backup. No terminal, `occ` or SQL is needed.

## Individual overrides, preview and access inspector

Three admin-only routes sit beside the grants API; each answers 403 to a non-administrator before it looks at any user or policy, and keeps the Nextcloud CSRF check.

- **Reset to inheritance:** `POST /apps/mcp/api/grants/commands` takes `{expectedRevision, commands}` with, per cell, `{uid, module, operation, state}` where `state` is `allow`, `deny` or `inherit` (removes the individual override); at most 50 users and 2,500 cells (`PolicyWriter::MAX_UIDS`, `MAX_CELLS`). It answers `{revision, changed, receiptId}`, or 400/409/428/503. A stale `expectedRevision` answers 409 and nothing is written. `POST /apps/mcp/api/grants/undo` restores the previous values from the receipt.
- **Preview of a reset:** `POST /apps/mcp/api/grants/commands/preview` (`OverridePreviewController`, `OverridePreview`) takes the same cells with `state: "inherit"`, without `expectedRevision`, and answers `{revision, cells}`: per cell the `before` and `after` as `{allowed, source, groupIds}`, with `null` for unknown, never `false`. It is read only: no write, no transaction, no mutex and no persisted observation of group trust, and it refuses to run inside a transaction. The "after" is computed by the same resolution without the individual value (`resolve()` with `inherited: true`, exposed as `PolicyOperationContext::inherited()`) that the writer uses for the eligibility check of a reset, through `inheritedEligibility()` (F2); the answer is paired with the revision it was read at and, if the revision moved during the read, it is read again once and then answers 503. The page (`src/admin/admin-overrides.js`) sends that revision as `expectedRevision` of the reset (or, when the preview could not be read, the revision of the table), so a change since the preview ends in 409. Invalid bodies answer 400. An *Allow* over an inherited *Allow* has no direct control (the help text of the page describes the uncheck-and-check workaround).
- **Inspector:** `GET /apps/mcp/api/inspector/access?uid=` (every catalog operation: `allowed`, `reasonCode`, `blockingGate`, the grant resolution with `source` and `groupIds`, and the scope as `mode` and `count`), `GET /apps/mcp/api/inspector/path?uid=&path=` (why the Files tools reach or not a path of the user: `reason`, `gate`, `exclusion`, `folder`) and `GET /apps/mcp/api/inspector/calendar?uid=&module=&calendarId=&operation=` (one calendar or task list; `module` is `calendar` or `tasks`). The answers come from `PolicyResolver::resolveEffective()`, then the scope, the exclusion guard and the native ACL, in the order of the tools, never from a parallel rule; `allowed` is said only when every gate was evaluated, otherwise `not_evaluated` names the gate. `reason` is `allowed`, `blocked`, `out_of_scope`, `no_native_access`, `read_only` (calendars), `not_found`, `excluded` or `not_evaluated`. For an excluded path (`reason: excluded`), `exclusion` is one of `tag_direct`, `tag_folder`, `tag_share_origin`, `backup_of_excluded` or `invalid_configuration`, and `folder` is the tagged ancestor in the user's tree: this detail is for the administrator, while the tools keep answering "not found". An exclusion that cannot be evaluated comes as `reason: not_evaluated` with `gate: exclusion` and `exclusion: null`. The inspector writes nothing and persists no observation. Invalid input answers 400 and an unreadable policy 503.
- **Audit:** `InspectorController` writes one *info* line per question, `MCP access inspection` (`admin`, `target`, `action` = `inspect_access`, `inspect_path` or `inspect_calendar`, `module`, `result` code, `timestamp`), never a path, a calendar or a title; a failure writes an *error* line `MCP access inspection failed` with the class of the exception only. As with the scope audit, *info* lines are recorded only when the server `loglevel` is 1 or lower (the default, 2, does not), so this is not a guaranteed audit trail.

## Per-resource scope

`ScopeGuard`, `ResourceScopeMapper`, `NativeResourceEnumerator`, `ScopeActivation`, `FilesScope` and `FilesAccessGuard` implement the optional per-user resource allow-list. `ScopeActivation::MODULES` has `'files' => true` (B5: every Files consumer is narrowed by the Files gate), `'calendar' => true` and `'tasks' => true` (B6, through `ScopedCalendarAccess`), so a scope may be saved for every module and no module answers 422 `ScopeInactive`.

- **Schema (`Version001100Date20261015020000`):**
  - `mcp_scope_modes`: `(user_key, module, user_id, policy_rev)`, PK `(user_key, module)`. Presence of a row means the user is in `restricted` mode for that module; absence means `all` (unrestricted).
  - `mcp_scope_items`: `(user_key, module, resource_key, resource_id)`, PK `(user_key, module, resource_key)`, up to 200 items per `(user, module)`. `user_key` and `resource_key` are SHA-256 digests of the user id and of the module and resource id, so primary keys stay compact, while the exact `user_id` and `resource_id` strings are stored and verified on read.
- **Precedence and uniformity:** `Per-resource scope > Exclusion by system tag > Native Nextcloud ACL`. After the access and operation permission checks, an unreadable resource scope returns 503 before any item is looked up. An out-of-scope calendar or task list returns `CalendarException::notFound()`, the refusal of a calendar that does not exist; a scope that cannot be read fails the operation with `PolicyUnavailable` (503), also for a calendar that does not exist (`ScopeReader::assertReadable()` runs before the native lookup, so existence is never told apart by a 503). In Files, `FilesAccessGuard::assertScopeReadable()` reads the scope before the tool does anything, so an unreadable scope answers 503 for every `files_*` tool, for `nc://files` (`ResourceRegistry`) and for `files_checkout`, whatever the requested path; a node outside the scope is refused exactly like a hidden or missing one.
- **Modules:**
  - `files`: allowed folders by file ID, covering each selected folder and its descendants. A node is inside the scope when the node itself or one of its ancestors is a selected folder, in the chain the user reaches: its own tree, or above a share mount root the owner's chain (`FilesScope::candidates()` walks up by metadata, over `VisibilityGuard::parentOf()`, and resolves the owner chain of every share root it crosses). A chain that cannot be resolved is outside the scope, never inside it. `FilesAccessGuard` extends `VisibilityGuard`: `isVisible()` applies the scope first and then the exclusion, while `isTraversable()` keeps the exclusion alone, so ancestors crossed only on the way to a destination (creating a folder at or below a selected folder) answer to the exclusion only. `FilesScope::roots()` replaces `/` in a listing with the outermost selected folders, at their real paths, when the root itself is out of scope. Notes (D4), the admin pages and the native enumeration keep the plain `VisibilityGuard`. The items come from the policy snapshot of the operation (`GrantPolicy::scopeItems()`), so one operation never mixes two scopes.
  - **Limits of the Files scope (declared):**
    - **Backups (N2):** `BackupLocation` supplies the configured root name and all reserved historical names. Copies use that destination when enabled; contact deletion always requires a copy. Internal copies may be outside the selected Files scope, but that does not grant read access to them. Exclusion tags are applied before content; a failed required copy refuses the original write. `BackupFolderMatcher` recognizes only owner-root candidates, including historical names, and uses a per-request snapshot for listing; write boundaries read fresh configuration.
    - **A selected root cannot be renamed (N2):** `Reorganization::destination()` resolves the parent of the destination through the gate, and the parent of an outermost selected folder is out of scope, so renaming it through MCP is refused. Moves and copies inside the scope keep working.
    - **Owner moved the source in another process (N4):** `FilesScope` caches the resolved chains and the owner chains per operation and invalidates them on `NodeRenamedEvent`, `NodeCopiedEvent` and `NodeDeletedEvent` of the same process. A move made by the owner in another process while a request runs can therefore be judged with the old chain in that request only; the next request reads the new one. Same window as the exclusion-tag cache.
    - **Mounts:** the stored ids are the file ids `Node::getId()` returns, so the limitation of the exclusion tags applies identically: mounting the same external directory with different roots creates two storages with their own ids, each protecting only what is read through itself, while two mounts of the same root (an alias) share the ids and are protected together.
    - **Exclusion-tag list cache (~3 s across processes):** a change to the exclusion tag list made by another process or node (`occ`, or another web node of a multi-node installation) may take about 3 seconds to apply; a change through the admin page on the same node applies immediately. This window is separate from the per-request window of the owner chain described above. Nothing in the scope needs `occ`.
  - `calendar`: allowed calendars for events (`VEVENT`), keyed by the backend calendar id (a share keeps it from the owner's calendar and a rename does not change it; the URI, the display name and the path are never a key). `ScopedCalendarAccess` wraps `CalendarAccess` for the calendar tools (`ListCalendars`, `ListEvents`, `CreateEvent`, `UpdateEvent`, `DeleteEvent`, `MoveEvent`, `SharedCalendarFinder`) and for the Talk event references (`ReferenceLinker`); the scope comes before the write check, so a calendar outside it is missing, never "read-only". Moving or transferring an event requires both the source and the destination calendar to be in scope (`EventRelocator` resolves both through it).
  - `tasks`: allowed calendars for tasks (`VTODO`), independent of `calendar` even when one underlying calendar holds both: the component decides the scope module (`VEVENT` → `calendar`, `VTODO` → `tasks`). `TasksModule` uses the same wrapper, and an object read by UID looks only at the component of the tool (`CalendarStore::objectByUid($id, $uid, $component)`), so an event and a task sharing a UID never answer each other. The admin pages and the native resource enumeration keep the unscoped `CalendarAccess`, so a scope never hides a calendar from the person who configures it.
  - **Notes (`notes`) is outside the Files folder scope** and is not restricted by `files` scope items.
  - **Unsupported in 1.1.0:** per-resource scope for `notes`, `contacts`, `deck` and `talk`; per-resource scope by group (groups only grant; a user's per-resource scope continues to restrict them even when their module grant comes from a group); free-text redaction.
- **Operational guarantees:**
  - Changing a user's resource scope commits through `PolicyWriter::setResourceScope` (requiring the current `revision`; a stale one answers 409) and **does not revoke** the user's OAuth sessions: the new scope applies from the next request.
  - Admin scope queries (`GET /apps/mcp/api/scope/{uid}/{module}`, `GET /apps/mcp/api/scope/{uid}/{module}/candidates`) and updates (`PUT /apps/mcp/api/scope/{uid}/{module}`) are written to the Nextcloud log at *info* level (`MCP resource scope admin request`: administrator, target user, action, result, module and counts, never a resource name, path or title). They appear only when the server `loglevel` is 1 or lower; the default (2) does not record *info* lines, so this is not a guaranteed audit trail. A user reads their own scope, read-only, in *Personal settings → Resource scope* (`GET /apps/mcp/api/my/scope`, `src/settings/my-scope.js`): it names the folders, calendars or task lists of each module, says "every …" for an unrestricted module and says so when the scope cannot be read, never "unrestricted". The effect of a scope on one user can be inspected with the inspector above.
  - **Deleted accounts (B3):** `UserCauseListener` captures the policy revision `R_b` in `BeforeUserDeletedEvent` (in autocommit, outside a transaction) and `ScopeCleanup::deleted()` removes, on `UserDeletedEvent`, the scopes saved at or before `R_b` (`ResourceScopeMapper::removeUpTo()` on `mcp_scope_modes.policy_rev`), so a scope saved after the deletion started is kept. No signal, nothing is removed: when the event is lost (its Before ran inside a transaction or failed, or the After never came because the deletion was rolled back), the restriction stays. `ReconcileJob`'s last step calls `ScopeCleanup::reconcile()`, which removes nothing and writes no policy: it pages over the users that still have a scope (`RECONCILE_BATCH`, from the `scope_cleanup_cursor` app config) and counts them in one *info* line `MCP resource scope diagnostic pass` (`users`, `kept_account_exists`, `absent`, `blocked_or_failed`, `orphan_item_users`). Proving that an account is gone is not in the app's hands (an unreachable directory backend may answer "no such user", and the account can be recreated between the proof and the write), so an orphaned restriction is kept: an account recreated with the same UID stays restricted, which only narrows.

## Polls

`polls_list_polls` lists authorized polls; `polls_read_poll` reads their descriptions, settings, deadlines, status and a page of native visible options. Both return the native internal URL. The `polls.read` grant is enabled by default like other reads; explicit denies, Guests restrictions and per-user app enablement still apply. These two tools omit votes, results, participant counts, author identities and invitation links. Protected reads use the separate tools and grants below.

Minimum Polls version: 8.6.3. Official source contracts cover 8.6.3, 9.0.7, 9.1.4 and 9.3.0. MCP supports Nextcloud 32–35; Polls 8.6.3 is usable here on Nextcloud 32–33. Unpinned versions must pass checks of the public signatures and returned data. A matching shape does not prove semantic equivalence to a pinned release.

Native discovery and options load complete collections before MCP limits the response. Page size is 1–100, with defaults of 25 polls or 100 options. Cursors are limited to 512 bytes and offsets to 100000. There is no memory hardcap before fetching. Native access is checked before paging, including for instance admins; each list call makes at most limit+1 detail reads. Cursors bind actor, offset, app version, query and authorized state; changes require restarting. Vote activity alone does not restart the poll-list cursor, but vote-dependent option locking can restart an options cursor. There is no snapshot guarantee.

Titles, descriptions and options remain untrusted plain text, including literal angle brackets and markup. Invalid UTF-8 is repaired, controls and direction marks are removed, and tabs and line breaks are preserved. Output is limited to 20000 characters per field and 100000 per page, with explicit truncation metadata.

The tools require the real authenticated internal user and the same global Polls session used by its entities. Native cleanSession runs before reading and in finally: it removes the old public token and cache and, in 8.6.3, the persisted Polls UID and type. This also removes a previous Polls public-link context from a shared browser session; the module never switches identity or restores the old token. Poll, vote and share data are not changed by reading. Returning a URL does not open it; opening the native UI can mark poll notifications read.

The `polls.results` and `polls.links` grants are independent of `polls.read` and start denied. `polls_list_votes` reports the native `own` or `all` scope; `polls_read_results` returns native aggregates only when authorized, with `options:null` while hidden. Identities classified as anonymous by the native serializer receive a poll-bound opaque ID and generic label; this does not prevent inference from votes or change external APIs.

`polls_list_links` requires native EDIT and only reads existing direct links. URLs may contain personal credentials: disclose them only to authorized people. It creates, registers and sends no invitation; inherited shares without URLs and resolvable containers are not covered. Retrieving a URL does not open it; opening it later can have native effects. Presets explicitly name results and links and do not grant them through writing.

These three reads load complete native collections before output pagination and text cuts; vote serialization may resolve users internally. There is no pre-fetch memory ceiling or transactional snapshot. Observed changes restart a cursor, but a transient policy change returning to its prior state can yield a partial collection under `all`. Text is untrusted data; anonymity is not a universal guarantee.

### Create a private poll

`polls_create_poll` creates one private simple text or date poll, with a title and 0–100 initial options. The independent `polls.create` grant starts off, including for existing policies. Creating a poll grants no access to votes, results or credential links. The native creation policy must also allow the acting user.

The plan shows the original input, the native canonical option values, persisted-default predictions and public observations. Text options accept 1–1024 characters (4096 bytes); the title accepts 1–128 characters (512 bytes). Dates use positive Unix seconds in UTC and durations in seconds, from 0 to 2678400. Controls, bidi, malformed UTF-8, out-of-range dates and canonical duplicates are refused; text is not silently truncated. All submitted text is untrusted data.

Confirmation creates the poll, then reads it back through native authorization before adding each option. The native services may emit activity, watch and notification events. Creation and options are separate writes: a partial or uncertain result can leave a poll or options behind. There is no rollback or automatic retry; confirming again can create another poll. The receipt includes only acknowledged ids and canonical values while still authorized. Public getters normalize some database defaults (for example, a NULL description reads as an empty string); they cannot prove the raw value of every field. An observable default mismatch stops the attempt before further options. Description, general configuration and management of existing options remain outside this tool.

## Connecting through claude.ai (OAuth)

In claude.ai, under **Customize > Connectors > Add custom connector**, paste the URL shown on the personal page (e.g. `https://<instance>/apps/mcp/`), with the trailing slash, and leave the OAuth client on **published Claude identity (CIMD)**. Claude opens the Nextcloud login and the "Allow" screen; allowing is equivalent to turning on the personal connection. Everything lives under `/apps/mcp`, with no Apache/DNS change:

- `401` with `WWW-Authenticate: Bearer resource_metadata=".../apps/mcp/.well-known/oauth-protected-resource"`;
- authorization server metadata at `/apps/mcp/.well-known/openid-configuration` and `/apps/mcp/.well-known/oauth-authorization-server` (issuer `https://<instance>/apps/mcp`);
- `oauth/authorize` (consent) and `oauth/token` (PKCE S256, refresh with rotation). Access token 1 h, refresh 30 days; only hashes go to the database.

Clients should follow the `resource_metadata` URL in the 401 challenge, then use the advertised issuer for discovery. For an issuer with a path, MCP clients try the RFC 8414 path-insertion URLs first and fall back to the OIDC path-appended URL above. The app does not serve `/.well-known/oauth-authorization-server/apps/mcp` at the origin root. Use the OIDC fallback; no web-server rewrite is required. Preserve any installation subdirectory and `/index.php` in the discovered issuer.

Three kinds of client are accepted: CIMD clients with a host on the allowlist, the native client when enabled, and the self-hosted clients the administrator added. The redirect URI is matched exactly for all of them, except that an `http` loopback URI (`127.0.0.1`, `[::1]`, `localhost`) ignores the port (RFC 8252 7.3) for CIMD and native clients only; a self-hosted client matches its stored URI byte for byte, port included. App passwords (HTTP Basic) are independent of every OAuth client. The metadata document of a CIMD client is downloaded within a total budget of 5 seconds (connection and reading together; DNS resolution is outside it); when it runs out, the page says the client did not send its metadata document in time, and the same client is refused without a new download for 30 seconds. The default allowlist is `claude.ai,chatgpt.com` and is edited without a terminal in **Administration → MCP for Cloud → OAuth clients → Allowed client hosts** (exact host, without `https://`, port, path or `*`, at least one; saving replaces the whole list). Removing a host revokes its existing connections, pending consent pages, authorization codes, access tokens and refresh tokens. Adding the host again requires a new authorization; old credentials remain revoked. The `oauth_client_hosts` key does not need to be written by hand: a value saved before 0.8.0 is preserved and the default only applies when the key is absent or empty. The same section turns on **Allow local programs (native client)**, which enables the fixed public `client_id` `nextcloud-mcp-native` (off by default) for local programs such as Gemini CLI, and shows the accepted loopback redirect URIs. **Self-hosted clients (custom redirect URIs)** lists the public clients the administrator adds (none by default, at most 20): each has a name (unique, up to 64 characters, shown on the consent screen and in the connection lists), an **Enabled** setting, its own random `client_id` `nextcloud-mcp-custom-<12 hex>` and 1 to 20 exact redirect URIs (absolute `https`, `http` only on loopback; no userinfo, `*` or fragment; up to 2000 bytes; the three kinds of client differ in how the redirect URI is matched, see below). Turning the native client off, or turning a self-hosted client off, deleting it or removing one of its redirect URIs, revokes that client only, never a user's other clients: the setting change and the deletion of the client's tokens, pending codes and spent refresh records are one transaction under the policy mutex (`OAuthClientsService`, `PolicyWriter::runAdmin` with `expectedRevision`; a stale page gets 409 with the current state, a failed delete rolls the change back), and consent, code exchange and refresh admit the client again under that same mutex, so a unit that read the old state before the change commits nothing after it. A consent page opened earlier is revalidated on both allow and deny, and a per-client generation (advanced when a client is turned off or loses a redirect URI) keeps a client that was turned off and on again from reviving it. A disabled or deleted client can neither exchange a code nor refresh nor authenticate (the Bearer check reads the setting fresh on every request). The clients live in the app's table `mcp_oauth_clients`, which every admission decision reads from the database (never the AppConfig, whose cache loader may publish a snapshot older than a withdrawal); the upgrade imports the 1.0.8 native switch into it without any terminal step.

Every redirect back to a client carries `iss` with the issuer (RFC 9207), including on denial and redirectable errors; errors before the redirect validation remain local. Discovery advertises `authorization_response_iss_parameter_supported: true` so clients can require this parameter and compare it exactly with the discovered issuer. The pending consent keeps the issuer from the authorization GET, even when the form action uses a different `/index.php` prefix. Consent pages created before issuer capture must restart the connection. Clients without an identity document of their own, such as Gemini CLI, are refused with `invalid_client` while the native client is off.

Personal disconnect, loss of eligibility (including in bulk or through a group), service turned off, and a disabled or deleted account immediately invalidate access/refresh tokens and pending codes (except for the single undated foreign-transaction recheck case where the user remains eligible; see [Group permissions and policy lifecycle (1.1.0)](#group-permissions-and-policy-lifecycle)). Re-enabling the service or eligibility does not restore old credentials; sign in again. Claude connects from `160.79.104.0/21`; if Nextcloud's brute-force protection delays the token endpoint, allowlist that range. Basic + app password continues to work for other clients.

### Zapia and other OAuth-only assistants

OAuth-only authentication does not identify a client's MCP transport, registration method or redirect URI. [Zapia's connector guide](https://zapia.com/blog/ai-integrations-how-to-connect-your-apps-and-automate-tasks?lang=en), published on 2026-08-25 and checked on 2026-11-07, describes a service catalog and requests for additional integrations. It does not document an arbitrary remote MCP URL, DCR, a CIMD document, a configurable client ID or an MCP callback. This is a limit of the available evidence, not proof that the product cannot offer those features.

For [#28](https://github.com/sintax-tech/mcp-for-nextcloud/issues/28), a verified Zapia MCP setup flow and its actual registration/callback contract are still required before a Zapia connection can be claimed. If Zapia only offers catalog connectors, its provider must add Nextcloud or a generic MCP connector; a server-side OAuth change alone cannot create that client capability. Do not add `zapia.com` to allowed hosts or register a guessed callback. A client that accepts a manually configured public client ID can use **Self-hosted clients** in the existing admin page; a CIMD client needs its exact verified metadata host. DCR is optional in MCP Authorization 2026-07-28 and is not provided by this app. No terminal configuration is required for the supported registration methods.

## Connecting through ChatGPT and Gemini CLI (OAuth)

User steps, with the same URL and the same "Allow" screen, are in the root README, in the ChatGPT and Gemini CLI sections. A summary of what the server requires from each:

- **ChatGPT**: CIMD at `chatgpt.com`, accepted by the default allowlist. The real document carries `token_endpoint_auth_methods_supported: [none, private_key_jwt]` and the singular `private_key_jwt`; the plural wins, and `none` is in the list, so the client is accepted as public.
- **Gemini CLI**: it does not publish an identity document, so it uses the static native client. The user pastes the `client_id` shown in the admin section into `~/.gemini/settings.json` → `mcpServers.<name>.oauth.clientId` and runs `/mcp auth`. The redirect `http://localhost:<port>/oauth/callback` matches because `RedirectUriMatcher` ignores the port on loopback for the native client (RFC 8252 7.3).

- **Self-hosted harnesses**: a harness that takes a manually configured `client_id` and returns to its own domain uses a self-hosted client the administrator added for it. `ClientMetadata::allowsRedirect` compares the requested `redirect_uri` with that client's stored list exactly, port included, also for loopback entries (the free port belongs to the native and CIMD clients only); the consent page shows the name the administrator gave the client, says the administrator added it, and shows the redirect host. See the root README for the steps.

`iss` is mandatory because Gemini CLI rejects a return without it.

## Revoking

*Disconnect* on the personal page blocks the next MCP request, even with the same app password. The app password remains valid in Nextcloud and must be revoked under **Security**. On the same page, *Revoke* cuts a specific OAuth client of the user themselves. The administrator can also remove the user's eligibility or turn the service off; both apply on the next request. In the **Active connections** block, the administrator revokes a specific OAuth connection, or all of a user's, immediately; the user remains enabled and can sign in again.

## Manual test after installation

```sh
URL=https://<instance>/apps/mcp/
AUTH='<user>:<app-password>'
H='-H Content-Type:application/json -H Accept:application/json,text/event-stream'

curl -s -u "$AUTH" $H -d '{"jsonrpc":"2.0","id":1,"method":"initialize","params":{"protocolVersion":"2025-06-18","capabilities":{},"clientInfo":{"name":"curl","version":"1"}}}' "$URL"
curl -s -o /dev/null -w '%{http_code}\n' -u "$AUTH" $H -H 'MCP-Protocol-Version: 2025-06-18' -d '{"jsonrpc":"2.0","method":"notifications/initialized"}' "$URL"   # 202
curl -s -u "$AUTH" $H -H 'MCP-Protocol-Version: 2025-06-18' -d '{"jsonrpc":"2.0","id":2,"method":"tools/list"}' "$URL"
curl -s -u "$AUTH" $H -H 'MCP-Protocol-Version: 2025-06-18' -d '{"jsonrpc":"2.0","id":3,"method":"tools/call","params":{"name":"mcp_status","arguments":{}}}' "$URL"
```

Expected responses:

| Situation | HTTP |
| --- | --- |
| No credential, invalid credential or disabled user | 401 with `WWW-Authenticate: Basic` |
| Service off, ineligible or disconnected user | 403 |
| Eligibility temporarily unknown (the only source is a `needs_confirm` group, or a pending recheck could not be processed) | 503 |
| `Origin` of another host | 403 |
| Missing `Accept: application/json, text/event-stream` or `Content-Type: application/json` | 406 |
| Unknown or malformed `MCP-Protocol-Version`: answers `UnsupportedProtocolVersionError` (`-32022`, `data.supported`). The legacy versions accepted after `initialize` are 2025-03-26, 2025-06-18 and 2025-11-25; an absent header means 2025-03-26, and on `initialize` the header is ignored. Also 400 when `MCP-Protocol-Version`, `Mcp-Method` or `Mcp-Name` diverge from the body (`-32020`). The reason for each 400 goes to the log at debug level. | 400 |
| Invalid JSON (`-32700`), batch or invalid envelope (`-32600`) | 400 |
| Unknown method (`-32601`) or invalid parameters (`-32602`) | 200 with a JSON-RPC error |
| GET or DELETE | 405 |
