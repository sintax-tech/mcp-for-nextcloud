# MCP for Cloud — Documentação técnica

English: [README.md](README.md)

Versão para **Nextcloud 32 a 35** (o `info.xml` declara 32–35; o contrato de API tem fixtures de 31 a 35, e o 31 segue conferido sem ser declarado). O endpoint atende clientes MCP 2026-07-28, sem estado, via `server/discover` e `_meta` por requisição, e também clientes anteriores, que usam `initialize` com 2025-06-18. Expõe MCP `2025-06-18` via Streamable HTTP sem sessão e sem SSE, na rota do próprio app:

- `https://<instância>/apps/mcp/` com URLs limpas;
- `https://<instância>/index.php/apps/mcp/` sem URLs limpas.

A URL exata da instância aparece nas páginas de administração e pessoal.

## Novidades da 1.2.1-rc.1

Candidata local para testes; não é uma versão publicada. Veja [o changelog](../CHANGELOG.md#121-rc1).

- **Configuração de backups ([#17](https://github.com/sintax-tech/mcp-for-nextcloud/issues/17)):** em *Proteção de dados*, escolha um nome de pasta diretamente na raiz pessoal de cada usuário que executa a ação (padrão `MCP backups`; `.mcp-backups` é permitido). A pasta aparece na primeira cópia. Trocar o nome nunca move nem apaga conteúdo; todos os nomes anteriores, inclusive o padrão legado, continuam protegidos contra escrita MCP e mantêm as regras de visibilidade dos espelhos de backup.
- **Cópias de Arquivos:** ligadas por padrão. Um administrador pode suspender as cópias prévias MCP somente com `files_versions` nativo ativo. A disponibilidade é conferida novamente para quem executa a ação; sem versionamento as cópias são obrigatórias e as operações existentes continuam recusadas quando falta seu pré-requisito Versions. Isso não garante uma versão nativa para todo arquivo/backend. Excluir contato sempre exige cópia verificada na pasta configurada, mesmo com cópias de Arquivos suspensas. Backups anteriores são preservados.
- **Mail ([#1](https://github.com/sintax-tech/mcp-for-nextcloud/issues/1)):** `mail_list_accounts` e `mail_list_mailboxes` listam somente contas do próprio usuário e pastas/contadores em cache. Mail é opcional e exige o grant `mail.read`. Essas chamadas não sincronizam IMAP, não leem mensagens nem alteram o estado do correio. Abra a conta uma vez no Mail se o cache de pastas estiver vazio; um cache antigo pode devolver informação antiga. A célula de integração opt-in usa Dovecot e Mail descartáveis, não um servidor de produção.
- **Visibilidade:** uma pasta comum aninhada chamada `MCP backups` deixa de ser confundida com a pasta de backup na raiz pessoal. Escopo, etiquetas de exclusão e recusa em caso de falha continuam valendo.

Os caminhos de backup abaixo usam o nome padrão; o nome configurado substitui esse componente da raiz. Os recursos da 1.2.0 seguem abaixo.

### Célula de integração Mail

A célula opcional é selecionada com `MCP_IT_WITH_MAIL=1` no harness de integração existente. `tests/Integration/ci/mail-cell.sh` provisiona o Mail fixado e um servidor Dovecot descartável com duas contas de teste. Os testes conferem pastas/contadores em cache, isolamento de contas e estado Mail/IMAP inalterado, além de descoberta/chamadas MCP HTTP autenticadas por app password e OAuth. Células comuns não instalam Mail nem iniciam IMAP. Use o procedimento permitido de empacotamento/PHP em contêiner e preserve o motor compartilhado; as fixtures não são instruções para instalar servidor de correio em produção.

## Política de tipos de arquivo (1.2)

A lista opcional de extensões começa **desligada**, inclusive após atualização. Configure em **Administração → MCP for Cloud → Proteção de dados**. Quando ativa, confere o nome final do arquivo nas gravações MCP de qualquer usuário, inclusive administrador: criar e enviar, upload do checkout, editar/substituir, restaurar versão, copiar/mover (inclusive descendentes de pastas), lotes, desfazer e Notes. Notes não é isento: inclua `md` e as outras extensões usadas nas notas. Restrição por recurso, etiquetas de exclusão, ACL nativa, travas e permissões de operação continuam independentes.

A regra usa a última extensão ASCII, sem distinguir maiúsculas; nomes sem extensão exigem a opção explícita do administrador. Nomes ambíguos (inclusive ponto/espaço final ou dois-pontos) são recusados enquanto a regra está ativa. Ela não examina MIME nem conteúdo e não elimina prompt injection. Configuração ausente significa desligada; configuração ilegível ou inválida recusa as gravações abrangidas. Somente backups internos obrigatórios `.bak` de arquivos e `.vcf` de contatos não passam pela política, pelos serviços de backup, nunca por uma extensão ou caminho escolhido pelo chamador.

A prévia, a confirmação e os pontos de gravação conferem a política. A cópia de pasta com a política ativa primeiro valida os descendentes e depois copia os arquivos da lista conferida, revalidando identidade, caminho e política. Arquivos acrescentados ou renomeados depois não são copiados; uma falha no meio deixa uma cópia parcial informada, sem apagá-la automaticamente. O movimento de pasta continua nativo após o preflight, então um descendente inserido entre a conferência e o movimento pode ir junto. Desfazer segue a política vigente na execução e preserva recibo e dados se recusado.

## Contatos e Tarefas (0.8.0)

| Módulo | Tools | Dependência |
|---|---|---|
| Contacts | `contacts_list_addressbooks`, `contacts_search_contacts`, `contacts_read_contact`, `contacts_create_contact`, `contacts_edit_contact`, `contacts_delete_contact` | app Contacts habilitado; core CardDAV |
| People | `users_search` | busca de contas — e, com `include_groups: true`, de grupos, devolvendo `type` `user` ou `group` — pelo compartilhamento do Nextcloud (respeita as restrições do admin); sem app opcional |
| Logs | `logs_list`, `logs_analyze` | só leitura do `nextcloud.log` pelo `ILogFactory`/`IFileBased::getEntries` do core; exige `log_type` em arquivo (padrão); ver [Log do servidor](#log-do-servidor-102) |
| Tasks | `tasks_list_calendars`, `tasks_list_tasks`, `tasks_read_task`, `tasks_create_task`, `tasks_edit_task`, `tasks_complete_task`, `tasks_delete_task` | core DAV; não exige app Tasks ou Calendar |

Os catálogos de Contatos são próprios/compartilhados, filtrando explicitamente qualquer principal de sistema. Leituras usam adapters lazy do backend nativo, depois do filtro de acesso; escritas passam pelo Sabre do core (dispatcher CardDAV separado e o `EmbeddedDavDispatcher` existente para VTODO). A sessão precisa corresponder ao ator e o principal é fixado na execução. `CalendarAccess` mantém VEVENT como padrão e recebe VTODO apenas no módulo Tasks.

`GrantPolicy`/`GrantMatrix` incluem `contacts` e `tasks` com read/create/edit/delete, escritas desligadas por padrão. Concluir tarefa usa edit. `PreviewsWrites` produz o plano sem efeitos colaterais; `WriteGate` exige confirm:true; shares exigem confirm_shared; ETag fornecido é conferido e If-Match usa o relido. Edição de vCard preserva campos desconhecidos, parâmetros, grupos e versão; o plano inclui todas as propriedades antes/depois e o vCard completo.

**Excluir contato é PERMANENTE no Nextcloud 33, sem lixeira.** Só depois de confirmar, `ContactBackup` salva o vCard original completo em `/MCP backups/Contacts/<catálogo>/<nome-ou-uid>.<AAAAmmdd-HHMMSS>-<sufixo-único>.vcf`, no fuso da conta e na pasta do ator. Usa mutex de aplicativo, sufixo aleatório e checagem de colisão para não selecionar arquivos existentes, e confere a cópia relendo os bytes. Falha impede DELETE CardDAV; o resultado informa backupPath. Reimporte pela interface Contacts para recuperar. Nenhum backup é criado no preview.

Tarefas usam VTODO, incluem tarefas sem data, ocultam PRIVATE/CONFIDENTIAL de outro dono e excluem objetos em lixeira. Ler recorrência é permitido; escritas em séries ou tarefas com participantes são recusadas. Campos não alterados permanecem no iCalendar; completar grava STATUS/PERCENT-COMPLETE/COMPLETED, e reduzir progresso reabre a tarefa. Excluir usa a lixeira CalDAV, recusa retenção zero e verifica deleted-at após o DELETE. Listagens usam limit/offset/nextOffset; concluídas exigem include_completed. As categorias (`CATEGORIES`) são texto livre: ler e listar devolvem `categories`, reunidas de todas as linhas `CATEGORIES` (vírgulas escapadas respeitadas), aparadas e sem repetição ignorando maiúsculas Unicode, com a primeira grafia mantida; criar e editar aceitam `categories` (até 50 itens de 1 a 255 caracteres depois de aparar, sem caracteres de controle, validados antes de qualquer escrita): omitir deixa todas as linhas intactas, `[]` as remove e uma lista as substitui por uma linha de vários valores. `tasks_list_tasks` filtra por `category` (exata, sem diferenciar maiúsculas) antes de `offset`/`limit`, junto com `include_completed`; o plano mostra cada nome entre aspas, antes e depois. As categorias de tarefas ocultas por CLASS nunca são lidas, filtradas nem mostradas.

Não há approval_id, registro de aprovação, requisito de occ, serviço extra ou banco auxiliar. Descrições/ToolGuideNotes ficam em inglês; títulos e mensagens usam Translator com paridade pt_BR/es/de (incluindo as 47 strings alemãs novas da 1.1.0, já integradas). Testes cobrem planos, backup, ACL, grants, ETag, preservação e dispatch real Sabre; não provam os plugins internos em uma instalação Nextcloud real.

## Tools

Cada tool só aparece em `tools/list` e só pode ser chamada quando o usuário tem o grant da operação, e o app exigido está habilitado para ele. Grant e app são verificados de novo a cada chamada. Tudo roda como o usuário autenticado, pela pasta dele no Nextcloud, e as permissões e compartilhamentos do Nextcloud continuam valendo.

### Guia das ferramentas (`mcp_guide`)

`mcp_guide` (título **Guia das ferramentas**) descreve as ferramentas ao próprio modelo, para que ele não precise adivinhar o que cada uma faz:

- **sem argumento** — uma linha por módulo com os títulos das ferramentas, apenas dos módulos disponíveis **para aquele usuário** (o mesmo filtro de grant e app do `tools/list`: módulo desabilitado ou sem grant não aparece);
- **com `module`** (`files`, `notes`, `calendar`, `contacts`, `tasks`, `deck`, `talk`, `people`, `logs`) — cada ferramenta do módulo: descrição, se lê ou escreve, parâmetros com tipo, obrigatoriedade, descrição, `enum` e limites, e as confirmações que exige;
- **com `tool`** — uma só ferramenta, com o módulo a que pertence.

O texto vem das definições reais (`ToolModule::definitions()`, `inputSchema`, `annotations` e `ToolPresentation`), então mudar o schema de uma ferramenta muda o guia: não existe uma segunda cópia da documentação para manter em dia. O que o schema não carrega — como encontrar as coisas, com quais caminhos e IDs, e onde as escritas param — entra em `ToolGuideNotes::guideNotes()`, uma nota curta por módulo, escrita ao lado do módulo. A resposta traz o mesmo conteúdo em markdown e em `structuredContent`, e a tool é read-only: ela lê definições, nunca executa uma ferramenta.

Módulo ou ferramenta que o usuário não pode ver é recusado com uma mensagem que lista o que ele pode usar. Não há aprovação gravada no servidor: a regra de confirmar antes de escrever está nas `instructions` do `initialize` e vale para toda tool que altera algo.

Compartilhamento de outra pessoa, de arquivo de outro dono, de nó oculto, de tipo não gerenciado ou id inexistente respondem todos "não encontrado", sem revelar nada; só o anexo do Talk do próprio usuário recebe a mensagem de que se remove pelo Talk. O grant do tipo é conferido depois da posse, e tudo é conferido de novo no confirm. Como no `files_share`, o confirm devolve o `plan_state` do plano; se o compartilhamento mudou ou foi refeito desde o plano, nada é removido e a resposta é o plano novo. |
| `notes_list` `{}` | notes.read | Notas `.md`/`.txt` da pasta do app Notes (preferência `notesPath`, padrão `Notes`). |
| `notes_search` `{query, limit=20, category=""}` | notes.read | Busca por título e conteúdo Markdown (até 1 MiB), com trecho contextual da ocorrência. Opcionalmente restrita a uma categoria. |
| `notes_read` `{id}` | notes.read | Nota com conteúdo; limite de 1 MiB. |
| `notes_create` `{title, content="", category=""}` | notes.create | Nunca sobrescreve; em colisão, usa `Título (2)`. |
| `notes_edit` `{id, content?, append?, old?, new?, title?, etag?, plan_state?}` | notes.edit | Conteúdo inteiro, acréscimo ou substituição de um trecho único; os modos são mutuamente exclusivos. `old` tem limite de 64 KiB. Confirmar append/replace exige o ETag e o `plan_state` devolvidos na prévia; a nota é relida antes de gravar. O título pode mudar junto com o conteúdo. |
| `notes_move` `{id, category, etag?}` | notes.move | Troca de categoria (subpasta), sem sobrescrever. |
| `notes_delete` `{id, etag?}` | notes.delete | Exige `confirm: true`, a lixeira (`files_trashbin`) ativa e o storage da nota coberto por ela; em storage externo sem lixeira, a exclusão é bloqueada. |

| `calendar_list_calendars` `{}` | calendar.read | Calendários visíveis ao usuário, próprios e compartilhados. |
| `calendar_list_events` `{calendar?, from?, to?}` | calendar.read | Eventos no intervalo (padrão: próximos 7 dias), com recorrência expandida. |

Calendar expõe leitura e as cinco escritas, sem nenhum passo no terminal. As escritas nascem desligadas na matriz do admin (Administração → MCP) e só aparecem para quem recebeu o grant; toda escrita exige ainda `confirm: true`, a ACL do Nextcloud (e `confirm_shared` em agenda alheia) e o ETag opcional. Compatibilidade: o app declara `min-version` 32 e `max-version` 35 em `info.xml`; a parte interna (`EmbeddedCalDavServer` do core) é coberta pelos testes e por essa faixa, e uma versão nova do Nextcloud exige uma nova versão do app. O app Calendar precisa estar habilitado para o usuário. Sabre e Symfony Console vêm do core do Nextcloud e ficam fora do `vendor/` do pacote.

| Tool de escrita | Grant | Comportamento |
| --- | --- | --- |
| `calendar_create_event` | calendar.create | Evento simples; `attendees` são UIDs internos resolvidos para o e-mail da conta. |
| `calendar_update_event` | calendar.edit | Atualiza texto/datas e substitui participantes; `attendees: []` remove todos. Mudança de participantes em série ou por outro organizador é recusada. |
| `calendar_move_event` | calendar.move | MOVE no mesmo dono; participantes não são avisados, como no app Calendar. |
| `calendar_delete_event` | calendar.delete | Exclui a série na lixeira; exige retenção ativa. |
| `calendar_transfer_event` | calendar.transfer | MOVE para agenda de outro dono compartilhada com escrita; recusa participantes. |

Create, update e delete usam `send_invitations: false` por padrão (`x-nc-scheduling: false`). `true` entrega o convite ao agendamento CalDAV do Nextcloud, inclusive para convidados existentes e CANCEL. O plano e o resultado informam `imipEnabled`, lido da configuração nativa `dav/sendInvitations`: com ela desligada o servidor não envia e-mail (o iTIP interno ainda chega à caixa do convidado) e o assistente deve dizer isso ao usuário. O app nunca confirma recebimento de e-mail. Escritas em agenda de outra pessoa ainda exigem `confirm_shared: true` após confirmação do usuário.

**Confirmação antes de toda escrita (sem estado no servidor).** As cinco escritas, chamadas sem `confirm: true`, só devolvem um plano (`requiresConfirmation: true`): valores atuais e propostos, participantes adicionados/removidos, destino, consequência para convites/CANCEL/lixeira e o `etag` atual. Nada é escrito nem agendado. O assistente deve mostrar o plano, perguntar ao usuário e só após um sim explícito repetir a chamada com `confirm: true` e os mesmos argumentos, reenviando o `etag` do plano (opcional; se vier e divergir, a escrita é recusada e um novo plano é necessário). Não há tabela, token nem registro de aprovação: o servidor não prova o sim humano, mas permissões, ACL, grants e `confirm_shared` seguem valendo. O selftest usa os handlers diretamente e não passa por esse fluxo.

### Deck: cartões, quadros e listas

As escritas do Deck usam os grants `deck.create`, `deck.edit`, `deck.move` e `deck.delete`, todas desligadas por padrão, e `confirm_shared: true` em quadro de outro dono. O app sempre confirma com o Deck se a escrita foi gravada, mesmo depois de um erro do Deck.

| Tool de escrita | Grant | Comportamento |
| --- | --- | --- |
| `deck_create_board` `{title, stacks?, confirm: true}` | deck.create | Cria um quadro do próprio usuário com suas listas e primeiros cards (até 20 listas e 100 cards), com cor opcional. Num quadro novo os responsáveis são o próprio usuário, porque mais ninguém tem acesso. O plano mostra a árvore inteira; se um passo falhar no meio, nada é desfeito e o resultado traz `created`, `failed` (com motivo seguro) e `warnings`, para a repetição não duplicar nada. |
| `deck_create_stack` `{boardId, title, position?, confirm: true}` | deck.create | Acrescenta uma lista a um quadro que o usuário gerencia, no fim ou numa posição. |
| `deck_delete_stack` `{stackId, confirm: true}` | deck.delete | Exclui uma lista **somente quando está vazia**: qualquer card, ativo ou arquivado, recusa a chamada dizendo quantos restam, e a contagem é refeita no confirm. Vai para a lixeira do Deck. |
| `deck_delete_board` `{boardId, confirm: true}` | deck.delete | Igual para o quadro, e só o dono pode excluir. Se um card aparecer entre a contagem e a exclusão, o quadro volta com o próprio undo do Deck e a chamada é recusada dizendo que nada foi excluído. |

`deck_create_card`, `deck_edit_card`, `deck_move_card`, `deck_delete_card` e a atribuição de responsáveis usam os mesmos grants e a mesma confirmação; os responsáveis são membros do quadro.

Depois de um erro vindo do Deck, toda escrita relê o estado real antes de responder: se o item foi gravado, a resposta é sucesso com o aviso "Saved; Deck reported an error afterwards (notification or activity)"; se não foi, é o erro de sempre; e se o estado não pode ser lido, a resposta não é erro e manda ler com `deck_list_cards`, `deck_read_card`, `deck_list_stacks` ou `deck_list_boards`. Um item reencontrado só por semelhança (mesmo dono, mesmo título, criado há pouco) vem como `confirmed: "probable"`, com aviso para conferir, e nada mais é escrito nele. Só as recusas que o próprio app faz antes de chamar o Deck (regras da tool, sessão, conflitos, argumentos) pulam essa releitura.

A exclusão "somente quando vazia" não é atômica: o Deck não olha o `deleted_at` da lista ao criar um card, então um card criado por outra requisição logo após a segunda contagem pode ir para a lixeira junto com a lista ou o quadro, de onde é recuperável. Isso está na descrição da tool e no gateway.

### Deck na 1.2.0

Etiquetas, hora de vencimento, dependências nativas e o vínculo nativo de arquivo fazem parte desta versão. O app não imita uma API ausente e não envia, não copia e não apaga o arquivo.

- **Etiquetas** (`deck_list_labels`, `deck_edit_card_labels`) existem no Nextcloud 32 a 35 com o Deck ativo. Versões comprovadas do Deck: 1.16.8, 1.17.7, 1.18.5 e 1.19.0. Uma etiqueta de outro quadro é recusada. A escrita muda só os ids pedidos.
- **Hora de vencimento** é lida e gravada com o card. A entrada é uma data local `YYYY-MM-DD` (meia-noite no fuso da conta), `YYYY-MM-DDTHH:MM` ou `YYYY-MM-DDTHH:MM:SS` nesse fuso, ou um horário com `Z` ou `±HH:MM`. O card devolve `duedate` como a data local e `dueAt` como horário ISO com o deslocamento da conta. Não há campo IANA. `overdue` continua por dia. Um horário local que não existe (o vão do horário de verão) é recusado. `dueBefore` continua só com data.
- **Dependências** (`deck_read_card_dependencies`, `deck_add_card_dependency`, `deck_remove_card_dependency`) aparecem só no Nextcloud 34 e 35, comprovadas com Deck 1.18.5 e 1.19.0. No Nextcloud 32 e 33 essas ferramentas estão ausentes. A direção é de saída: `cardId` é a origem e `targetId` é o card do qual ela depende. `assignDependentCard(A, B)` guarda B nos cards dependentes de A. Autorrelações e ciclos por cards legíveis são recusados. Uma relação com um card que você não pode ler é omitida, sem contagem e sem id. Um ciclo por esses cards não pode ser detectado. Uma alteração concorrente entre a última verificação e a escrita nativa ainda pode criar um ciclo.
- **Arquivos** usam o compartilhamento nativo do Deck (tipo 12) no Nextcloud 32 a 35. `deck_list_card_files` e `deck_unlink_card_file` existem nas quatro versões. `attachmentId` é o id do compartilhamento e não é o `fileId`. Listar exige `deck.read` e `files.read`. Desvincular exige `deck.edit` e `files.read`, preserva o arquivo original, e quem edita o card pode remover um vínculo visível criado por outra pessoa. Compartilhamentos independentes podem manter o acesso. Um vínculo ausente e um que você não pode ver têm a mesma recusa: sem contagem e sem handle. Abrir o card no Deck é o próximo passo genérico, e essa resposta não confirma que um vínculo oculto existe. Este app não desvincula um arquivo oculto. Uma pasta que você já pode ver, e um card ou quadro arquivado que você já pode ver, são recusados em linguagem direta.
- **Vínculo** (`deck_link_card_file`) precisa de três permissões que já existem: `deck.edit`, `files.read` e `files.share`. Ler e desvincular não precisam de `files.share`. O plano mostra o caminho do arquivo, o dono, se é um recompartilhamento, o total atual de destinatários, uma lista limitada de nomes, os compartilhamentos que você criou e acesso somente leitura (READ=1) para os membros atuais e para quem entrar depois no quadro, em um grupo ou em uma equipe (círculo do Nextcloud). Desvincular esse compartilhamento o remove para todos. O acesso é conferido só quando o vínculo é criado. O servidor não revoga o vínculo depois. Uma política ligada mais tarde, uma mudança de membros do quadro, de um grupo ou de uma equipe, e o momento entre a última verificação e o compartilhamento nativo podem mudar quem lê o arquivo. O hash do plano não torna o compartilhamento atômico. O servidor não atesta consentimento humano. Um plano novo ou um resultado incerto não é registro de que a escrita ocorreu nem de que uma pessoa aprovou.
- **Recusas** usam a mesma resposta quando os fatos não podem ser lidos. O vínculo é recusado para um convidado (a exceção de ocultar usuários não se aplica a esta sessão OAuth), para compartilhamento restrito a grupos, quando o compartilhamento com grupos está desligado e o quadro inclui um grupo ou uma equipe, quando a expiração interna é obrigatória, quando compartilhar ou recompartilhar está desligado, e quando um destinatário não é um usuário local, um grupo ou uma equipe totalmente resolvido. Essas respostas não pedem para mudar uma configuração nem para entrar de outro modo.

### Diagnóstico opcional do Calendar (`occ mcp:calendar-selftest`)

Não é pré-requisito: nada depende dele para as tools aparecerem ou funcionarem, e ele não grava nem esconde nada. É uma ferramenta de diagnóstico opcional e avançada para quem administra o servidor e quer ver, passo a passo, o CalDAV real respondendo. Rode na raiz do Nextcloud como o usuário do servidor web. O UID organizador precisa ter conta habilitada, e-mail válido e Calendar habilitado; a retenção `dav/calendarRetentionObligation` não pode ser `0` (a limpeza seria permanente, então ele falha antes de criar qualquer objeto).

```sh
sudo -u www-data php occ mcp:calendar-selftest UID_ORGANIZADOR
```

Cada execução cria dois calendários com URIs `mcp-selftest-...-a`/`-b`, toca somente eventos criados nela e move esses calendários para a lixeira ao terminar. Sem opções, as três provas opcionais mostram `NOT TESTED`. Para exercitar convites internos, transferência e ACL:

```sh
sudo -u www-data php occ mcp:calendar-selftest UID_ORGANIZADOR \
  --attendee-uid UID_PARTICIPANTE \
  --shared-calendar '/remote.php/dav/calendars/UID_ORGANIZADOR/URI_COMPARTILHADO/' \
  --acl-probe-user UID_SEM_ACESSO
```

Essa execução gera efeitos nos dois usuários (convite interno, CANCEL de limpeza, Activity na agenda compartilhada) e remove somente itens com o UID gerado pelo teste. Não é prova de SMTP.

| Etapa do relatório | Resultado esperado |
| --- | --- |
| `preflight`, `calendars` | Conta/app/retenção válidos; dois MKCALENDAR HTTP 201 visíveis. |
| `create` | HTTP 201, UID e ETag relidos, sync-token aumentou. |
| `suppression-create`, `suppression-update` | PUT 201/204, ATTENDEE `@example.invalid` sem SCHEDULE-STATUS; SEQUENCE subiu. |
| `stale-tool`, `stale-dav` | Conflito no handler e HTTP 412 no DAV; dados e ETag intactos. |
| `move`, `overwrite` | MOVE 201 com UID só no destino; Overwrite F retorna 412 e preserva os dois objetos. |
| `delete` | HTTP 204, UID fora da leitura e na lixeira. |
| `invitations`, `transfer`, `acl` | `OK` se solicitadas e comprovadas; `NOT TESTED` sem as opções. |
| `cleanup`, `result` | Limpeza HTTP 204 confirmada, sessão restaurada e resultado final do diagnóstico. |

Qualquer `FAIL` retorna código não zero. Se a limpeza falhar, `cleanup-resource` indica o path/UID a conferir no servidor. O resultado não altera quais tools existem.

Tools de Notes exigem o app Notes habilitado para o usuário. Leitura começa permitida; criação, edição, movimentação e exclusão começam negadas até o administrador liberar. Não há timeout próprio: a leitura é local ao PHP e o limite de bytes protege contra arquivos grandes. Storage externo lento fica limitado ao `max_execution_time` do PHP.

### Imagens (`files_image_view`, `files_images_view`, `files_image_search`)

Ferramentas somente leitura (`files.read`) que respeitam a pasta do usuário e as permissões nativas do Nextcloud:

- **`files_image_view`**: Gera uma pré-visualização reduzida da imagem via `OCP\IPreview` com dimensão máxima configurável (`max_size`, padrão 1568 px). Se o preview exceder o limite de bytes (configurável em `image_single_max_bytes`, padrão 1 MB), a resolução é reduzida progressivamente até caber. Se não houver preview disponível para o formato, recorre ao arquivo original para formatos comuns (JPEG, PNG, WebP, GIF) desde que esteja dentro do limite de bytes. Retorna bloco `image` (base64) e bloco `text` com metadados (`path`, `mime`, dimensões originais se disponíveis, `size`, `mtime`, `access`, `captured_at`).
- **`files_images_view`**: Recebe uma lista de `paths` (até 6) ou uma pasta `folder` (com `limit`, padrão 6) e retorna múltiplos blocos de imagem sob um orçamento compartilhado (`image_batch_max_bytes`, padrão 4 MB). Arquivos que excedem o orçamento ou falham são listados no sumário `skipped`.
- **`files_image_search`**: Busca arquivos com mimetype `image/%`, com filtros opcionais por texto (`query`), pasta (`folder`), intervalo de modificação ISO 8601 (`modified_after`/`modified_before`) e tag de sistema (`tag`, incluindo tags automáticas geradas pelo app Recognize). Retorna apenas metadados ordenados por `mtime` decrescente.

Argumentos inválidos, tool inexistente ou sem grant retornam o erro JSON-RPC `-32602`, sem distinguir o motivo. Falhas de execução retornam `isError: true` com uma mensagem genérica, sem caminho físico, conteúdo ou stack trace.

## Recursos (MCP Resources)

O servidor anuncia a capability `resources: {}` tanto no fluxo legado `initialize` quanto no fluxo moderno `server/discover`.

- **`resources/list`**: expõe `mcp://guide` (Guia das ferramentas), retornando a documentação completa em Markdown renderizada dinamicamente com base nas permissões concedidas e apps ativos para o usuário.
- **`resources/templates/list`**: expõe templates de URI parametrizados:
  - `nc://files/{path}`: arquivo no armazenamento do usuário (requer grant `files.read`).
  - `nc://notes/{id}`: nota identificada pelo id numérico (requer grant `notes.read` e app Notes habilitado).
- **`resources/read`**: leitura de recursos:
  - `mcp://guide`: entrega o guia formatado em `text/markdown`.
  - `nc://files/{path}`: lê arquivos de texto (`text/*`, PDF, DOCX, ODT via extração de texto idêntica ao `files_read`, com limite de 100.000 caracteres) ou pequenos arquivos binários como `blob` (base64) até 512 KiB. Arquivos binários maiores são recusados com erro.
  - `nc://notes/{id}`: entrega o conteúdo da nota em `text/markdown` (limite de 1 MiB).
  - Recursos inexistentes, não permitidos ou ocultados por etiquetas (`VisibilityGuard`), ou fora do escopo por recurso (`ScopeGuard` para Calendário e Tarefas, `FilesAccessGuard` para `nc://files`, que é o `VisibilityGuard` precedido do escopo de Arquivos da operação), retornam erro padrão (`-32602` na era moderna, `-32002` na era legada) e nunca um array de conteúdo vazio.

## Empacotar

No diretório `mcp/`:

```sh
./scripts/package.sh
```

Gera `build/mcp-<versão>.tar.gz` com raiz `mcp/` contendo `appinfo/`, `lib/`, `templates/`, as pastas de assets que existirem (`js/`, `css/`, `img/`, `l10n/`), os dois READMEs (`README.md` em inglês e `README.pt-BR.md` em português) e um `vendor/` só de produção, criado com `composer install --no-dev`. O script precisa de `composer` e `php` na máquina que empacota.

### Regra do pacote: sem metadados do macOS

Um pacote com `._*` (AppleDouble), `.DS_Store` ou cabeçalhos PAX com xattrs `com.apple.*` é recusado pela App Store e pode quebrar a instalação. Por isso:

- o tar roda como `COPYFILE_DISABLE=1 tar --no-xattrs --exclude='._*' --exclude='.DS_Store'`. O `--no-xattrs` foi acrescentado porque, sem ele, o bsdtar grava `com.apple.provenance` em cabeçalhos PAX de todas as entradas;
- a conferência é feita por `scripts/check_package.php`, que lê o tar com um leitor próprio em PHP, porque o `tar -tzf` do macOS esconde as entradas `._*` e o `PharData` não expõe os cabeçalhos PAX;
- o pacote é recusado, apagado, e o script termina com código 1, se tiver:
  - entrada `._*` ou `.DS_Store`;
  - entrada PaxHeader ou cabeçalho PAX estendido;
  - entrada de topo diferente de `mcp/`;
  - pacote em `vendor/` fora das dependências de runtime (`smalot/`, `symfony/polyfill-mbstring/`, `composer/`, `autoload.php`), como `sabre/*` ou `symfony/console`;
  - script ou estilo referenciado por `Util::addScript('mcp', X)`/`Util::addStyle('mcp', X)` ausente do pacote.

Para conferir um pacote avulso: `php scripts/check_package.php build/mcp-<versão>.tar.gz`.

## Instalar

A instalação normal é pela App Store do Nextcloud: *Apps* → buscar **MCP for Cloud** → **Baixar e ativar** (ou `occ app:install mcp`). O pacote da loja é assinado e atualiza pelo atualizador de apps. A instalação por SSH abaixo é a alternativa, para desenvolvimento ou testes de um build local.

### Instalar via SSH

Substitua `<servidor>`, `<nextcloud>` (raiz da instalação), `<apps>` (diretório de apps gravável, por exemplo `custom_apps` ou `apps`, conforme `apps_paths` em `config/config.php`) e `<www>` (usuário do servidor web, por exemplo `www-data`).

```sh
scp build/mcp-1.1.2.tar.gz <servidor>:/tmp/
ssh <servidor>
sudo tar -xzf /tmp/mcp-1.1.2.tar.gz -C <nextcloud>/<apps>/
sudo chown -R <www>:<www> <nextcloud>/<apps>/mcp
sudo -u <www> php <nextcloud>/occ app:enable mcp
sudo -u <www> php <nextcloud>/occ app:list | grep -A1 mcp
```

Em Docker, rode os comandos `occ` dentro do container como o usuário do servidor web. Se o PHP usa OPcache com `validate_timestamps=0`, reinicie o PHP-FPM após copiar os arquivos.

Para atualizar um build instalado por SSH: `occ app:disable mcp`, remover `<apps>/mcp`, extrair o novo pacote, `occ app:enable mcp` e `occ upgrade` se o Nextcloud pedir. A pasta precisa ser trocada inteira, para não sobrarem arquivos antigos em `vendor/`. Para remover: `occ app:remove mcp`.

## Log do servidor (1.0.2)

Módulo `logs`, só leitura e só para TI: `logs_list` lista as entradas do `nextcloud.log` da mais nova para a mais antiga e `logs_analyze` resume a mesma janela.

- **Fonte única:** `ILogFactory::get('file')` e, se o writer for `IFileBased`, `getEntries($limit, $offset)`, o mesmo caminho do leitor de log do core. O app não abre arquivo, não usa shell nem `occ`. O `getEntries` só devolve o que está no `loglevel` do servidor ou acima, e linha malformada vira `null` (contada em `scan.malformed`).
- **Portão duplo:** `LogsAccess` (`RestrictedModule`, checado pelo `ToolRegistry` antes do grant, no `tools/list` e em cada `tools/call`) aceita admin do Nextcloud ou membro de um grupo no estado versionado `mcp_logs_groups`; depois o grant `logs.read`, que nasce desligado. Com `log_type` syslog/errorlog/systemd as tools somem e a coluna sai da matriz; o bloco do admin explica.
- **Teto e orçamento:** a API do core reabre o arquivo e o percorre a partir do fim, caractere a caractere, passando também pelas linhas abaixo do `loglevel`, e não oferece orçamento físico. Por isso cada resposta faz **uma única** chamada `getEntries`, com janela = min(5.000, 20.000 − `offset`) (sem filtro, só a página): uma segunda chamada pagaria a caminhada de novo e, com o log crescendo no meio, devolveria a mesma entrada duas vezes. O `readBudget` (20.000) é a profundidade em **entradas elegíveis** (no `loglevel` ou acima) a partir do fim, não um teto físico de linhas. A resposta traz `scan.scanned`, `truncated`, `budgetReached`, `readBudget`, `oldestScanned` e `nextOffset` (para continuar mais para trás); o `.1` rotacionado não é lido. Tudo continua pelo OCP: o app nunca abre o arquivo.
- **`since` não encerra a leitura:** o core carimba cada entrada com o `microtime` de quando a monta, e workers concorrentes gravam em qualquer ordem. Uma entrada anterior ao `since` é pulada e a janela segue até o fim; enquanto houver orçamento, `nextOffset` aponta para o fim da janela, e a resposta nunca afirma que não existe nada mais antigo.
- **Datas:** `since`/`until` em ISO 8601; o `time` da entrada é lido no `logdateformat`/`logtimezone`; se não casar, a entrada fica de fora sob filtro de data e conta em `scan.unparsed`.
- **Saída:** envelope `{"untrusted_log_data": true, "notice": …}` depois de um aviso fixo; controles, ANSI e marcas invisíveis removidos; IP mascarado (`a.b.x.x`, IPv6 /48) também dentro das mensagens; IPv6 com CIDR também é reduzido a /48; antes das regex, cada campo tem limite de 16 KiB e o token que cruza a fronteira é descartado inteiro, para não expor meio IP; depois da máscara, mensagem cortada em 2.000 caracteres; exceção com classe, mensagem, local e 10 frames `class->function` + `arquivo:linha`, sem `args`.
- **Análise:** totais por nível/app/usuário, top 20 assinaturas (aspas, caminhos, UUIDs, hashes e números viram `#`), top 10 caminhos de URL (sem query; caminho WebDAV dobrado no endpoint + conta), top 10 user agents e histograma por hora.
- **Auditoria:** o `ToolRegistry` entrega toda chamada a um `RestrictedModule` com o resultado (`denied` por papel ou grant, `invalid`, `read_error`, `success`), e o módulo dispara `CriticalActionPerformedEvent`, gravado pelo admin_audit quando ativo: `MCP logs read by %s: tool=%s filters=%s` só para leitura feita e `MCP logs request %s for %s: tool=%s filters=%s` para as demais, nunca uma negação como leitura. Dos argumentos ficam só os filtros conhecidos, escalares e cortados. No log do app, negação é `warning` e o resto `info`. Se a própria auditoria falhar (dispatcher ou logger), o registry grava "MCP audit failed" sem argumentos: negada, inválida ou com erro mantém a resposta original; uma leitura bem-sucedida **não** entrega os dados e responde um erro genérico. Se o logger de contingência também falhar, a exceção é ignorada e o mesmo comportamento é preservado.
- **Privacidade (1.0.6):** com etiquetas de ocultação configuradas e a opção **Esconder o texto das mensagens do log** ligada (padrão), o texto das mensagens e das exceções, o user agent e o method fora dos verbos conhecidos ficam `[hidden]`, a URL fica só com o prefixo fixo de rota e o `contains` é recusado; ver [Etiquetas ocultas (1.0.6 e 1.1.0)](#etiquetas-ocultas-106-e-110).
- **API do admin:** `GET`/`PUT /apps/mcp/api/logs-access` (`{groups, previous, version}`, listas de strings e versão inteira não negativa), admin-only com CSRF; GET retorna grupos e versão do mesmo snapshot. Grupo novo inexistente dá 400 sem gravar. Uma migration nativa empacotada cria a tabela própria `mcp_logs_groups`; a primeira leitura importa e canonicaliza o antigo `logs_groups` do appconfig e remove a chave antiga, sem sobrescrever um estado já migrado. Se a limpeza falhar, a leitura mantém o estado da tabela e tenta remover a chave de novo nas próximas leituras. O `QBMapper` lê diretamente a tabela e grava com CAS (`UPDATE … SET groups=?, version=version+1 WHERE id=1 AND version=?`): zero linhas alteradas ou lock ocupado dá 409 com o estado atual. O lock exclusivo do `ILockingProvider` é uma camada extra: com `filelocking.enabled=false`, o provider vira Noop, mas o CAS continua protegendo contra revogação desfeita por saves concorrentes ou snapshots antigos do appconfig. Ids são texto: `"1"` e `"01"` são dois grupos.

## Arquivo travado (1.0.5)

Escritas de Notes e Files diante do `files_lock` (app até o Nextcloud 34, embutido no 35). Serviço comum: `Tools/Common/LockAwareWrite` (`ILockManager::isLockProviderAvailable` + `getLocks`), sem importar classes do files_lock.

- **Quem bloqueia:** trava manual de outra pessoa (`TYPE_USER`), trava de app (`TYPE_APP`, Text ou Office) e trava de cliente WebDAV (`TYPE_TOKEN`). APP e TOKEN recusam até para o próprio dono. A trava manual do próprio usuário deixa escrever e é mantida, como no app Files; na rota do checkout por link, que não tem sessão do usuário, ela também recusa, como o files_lock faz ali. Sem provider, nada muda.
- **Onde:** antes da confirmação de compartilhamento e do backup, e de novo logo antes de cada escrita (`LockAwareWrite::run`): `putContent`, move, rename e delete de nota, cada item de lote e de undo, restauração de versão, upload do checkout, conteúdo de arquivo novo e cópia de backup. A recusa do storage (`ManuallyLockedException`) também é capturada e explicada (`capture`, usado na cópia, que só lê a origem).
- **Na dúvida, recusa:** consulta de trava que falha recusa; pasta que se move é checada com tudo o que o usuário alcança dentro dela, até 5.000 itens (`LockAwareWrite::TREE_LIMIT`), e uma listagem maior que o orçamento restante recusa sem ler a trava dos itens. A listagem de cada pasta é lida inteira antes dessa comparação: o `getDirectoryListing()` não tem limite no 32–35 e o `Folder::search()`, que tem, consulta a cache de arquivos e não reproduz a listagem. Arquivo oculto pelo `VisibilityGuard` não é nomeado e o `lock` do plano traz só `blocking: true`.
- **Plano (`confirm` ausente):** não recusa; acrescenta `lock` e um aviso `file_locked` em `warnings`. Em `files_move_batch` o item travado vai para `denied`, e o lote é recusado inteiro.
- **Restauração de versão:** com provider, lê a versão por `IVersionManager::read()` e grava pelo arquivo, sem o `rollback()` do core, cujo `handleAppLocks` repete a escrita no escopo do Text/Office. Com cópias MCP ligadas, a cópia verificada preserva o conteúdo substituído; cópias suspensas dependem do versionamento nativo e de sua política.
- **Checkout:** trava → 423. Antes de gastar o link, o link continua valendo; depois, a resposta cita o backup e pede novo `files_checkout`.
- **Mensagem:** app ou pessoa (nome de exibição; nunca UID, app id nem token), desde quando, até quando e o que fazer, em en/pt_BR/es/de. Recusa sem correlação segura pelo token fica com responsável não identificado. Log só em `debug`, sem caminho nem token.
- **Limite:** TOKEN só é recusada pela checagem do MCP, que não é atômica com a escrita, e o `getLocks()` do files_lock responde do cache da requisição, inclusive negativo: uma trava TOKEN criada depois da primeira consulta do arquivo na mesma requisição não é vista. Travas USER e APP também são aplicadas pelo storage do files_lock, que lê a trava de novo na escrita, exceto na exclusão ou na renomeação de/para Markdown de um documento do Text: o listener do Text (`BeforeNodeDeletedListener`/`BeforeNodeRenamedListener`) roda antes do storage e faz `resetDocument(..., true)`, soltando a trava APP; uma trava APP do Text criada depois da consulta do MCP é solta assim e não impede a exclusão ou a renomeação. O MCP só recusa a trava que o provider observa. O files_lock não oferece aquisição atômica de trava (consulta e inserção separadas, `file_id` sem índice único), por isso o app não toma trava própria.

## Etiquetas ocultas (1.0.6 e 1.1.0)

`VisibilityGuard`, `FolderExposureGate` e `OutputReferenceFilter` aplicam a exclusão por system tags em todos os caminhos de acesso do conector: leitura, busca, listagem, árvore, imagens, versões, notas, Talk, Tarefas, recursos, checkout, escritas e desfazer. Veja [`tests/Unit/Contract/EXCLUSION-MATRIX.md`](tests/Unit/Contract/EXCLUSION-MATRIX.md) e [`tests/Unit/Contract/FOLDER-EXPOSURE.md`](tests/Unit/Contract/FOLDER-EXPOSURE.md).

- **Herança e resolução acima de raízes de montagem (1.1.0):** a etiqueta no arquivo ou pasta vale para o próprio nó e todos os descendentes em qualquer profundidade. Um item alcançado por compartilhamento local herda as etiquetas da cadeia da pasta de origem do dono (storage `OCP\Files\Storage\ISharedStorage` + id no filecache, resolvido uma vez por raiz compartilhada). Team folders (`groupfolders`), storage externo (`files_external`) e shares federados seguem pelo caminho montado, sem consultar o dono; um federado é verificado só pelas etiquetas locais. Acima da raiz de uma montagem, o Nextcloud devolve uma pasta-pai que carrega o id de outro storage (`-1` acima de um storage externo); o `VisibilityGuard::parentOf()` resolve de novo, pelo caminho, a pasta acima da raiz da montagem, para que arquivos de storage externo e de pastas de equipe compartilhados avulsos subam até a raiz real do usuário em vez de falharem fechados.
- **Portão de exposição de pastas (`FolderExposureGate`, 1.1.0 — D7):** enquanto houver ao menos uma etiqueta de exclusão configurada (ou a configuração não puder ser lida), o MCP recusa compartilhar pasta (`files_share` com usuário, grupo ou link público), copiar pasta (`files_copy`) ou mover pasta para outro diretório pai (`files_move`, `files_move_batch`, `files_undo_batch`), e mascara `url: null` em links públicos existentes de pastas em `files_list_shares`. A visibilidade é conferida primeiro (pasta excluída ou configuração de etiquetas ilegível devolve `CommonMessages::notFound()`); apenas uma pasta visível recebe a recusa traduzida de D7 orientando o usuário a fazer operações em pastas pela interface web do Nextcloud Files. Arquivos individuais, renomear pasta dentro do mesmo diretório pai e `files_unshare` continuam permitidos.
- **Filtragem de referências estruturadas (`OutputReferenceFilter`, 1.1.0):**
  - **Talk:** `talk_attach_file` e `talk_quote_file` conferem a visão do autor da chamada sobre o arquivo e recusam com `notFound()` um arquivo excluído ou fora do escopo de Arquivos de quem chama; `talk_read_messages` confere do mesmo modo cada anexo de compartilhamento da sala e devolve `attachmentId: null` quando o arquivo é recusado. A etapa de escopo é a `FilesReferenceScope` (1.1.0), o escopo de Arquivos do usuário da operação.
  - **Todos os aliases resolvidos precisam passar (N1):** a `OutputReferenceFilter::fileIdVerdict()` resolve o id com `getById()` e a `allowsNodes()` exige que *todos* os nós retornados passem pelo escopo de Arquivos e pela exclusão, com pelo menos um deles legível. Então uma referência resolvida **por id** — um compartilhamento de sala do Talk, um `ATTACH` com `X-NC-FILE-ID` — é julgada por todos os aliases daquele id na árvore de quem chama, enquanto as ferramentas de Arquivos decidem pelo caminho que foi solicitado; um arquivo que o usuário também alcança por um alias restrito não pode vazar pelo Talk ou pelas Tarefas. Uma referência resolvida **apenas por caminho** faz outro caminho: a `pathVerdict()` resolve um único nó e chama `allowsNodes($userId, [$node], null)`, então uma URL DAV sem id e o parâmetro `FILENAME` conferem apenas o nó daquele caminho. Um id recusado remove o `ATTACH`; um `FILENAME` não resolvido é removido dele, e o `ATTACH` ainda é avaliado pelo próprio conteúdo ou URL; conteúdo `BINARY`/`BASE64` embutido é dado, não referência, e permanece.
  - **Tarefas:** propriedades `ATTACH` apontando para URLs locais do Nextcloud (`/f/<id>`, `/s/<token>`, `/remote.php/dav/files/<uid>/<path>`, `/remote.php/webdav/<path>`, com ou sem `/index.php`, em qualquer host, IP, loopback ou alias) e parâmetros `X-NC-FILE-ID`/`FILENAME` do Calendar são omitidos de `tasks_read_task` e dos planos e resultados das ferramentas de escrita de Tarefas quando o arquivo referenciado está excluído ou fora do escopo de Arquivos de quem chama (o objeto VTODO guardado no servidor mantém todo `ATTACH` ao editar); `tasks_list_tasks` não traz o calendário bruto; links públicos de pastas são omitidos enquanto houver etiquetas de exclusão ativas.
  - **Calendário e Deck:** saídas de eventos do Calendário não trazem `ATTACH`/URLs de arquivos, e saídas de cartões do Deck omitem `attachmentCount` para não revelar arquivos fora do escopo do usuário ou ocultos por etiquetas de exclusão.
- **Etiquetas do Deck:** `deck_list_labels` lista etiquetas de um quadro legível. `deck_edit_card_labels` adiciona/remove só os IDs pedidos e preserva as demais etiquetas. Exige `deck.edit`, cartão ativo editável e etiquetas do próprio quadro. Primeiro revise o plano; repita seu `plan_state` com `confirm: true` (e `confirm_shared: true` no quadro de outro dono). Estado alterado exige novo plano. Confira resultados parciais ou não verificados no Deck antes de outras alterações.
- **Dependências nativas do Deck:** `deck_read_card_dependencies` exige `deck.read` e aparece só no NC34/35 com API nativa compatível (Deck1.18.5/1.19.0 provados em contêiner; patches posteriores dependem das checagens de versão/API). `assignDependentCard(A,B)` coloca B em A.dependentCards: origem A → destino B, sem bloquear tarefas automaticamente. Só aparecem nós/arestas legíveis, ordenados por IDs, sem contagem ou identificador de ocultos. Sem paginação: o subgrafo legível alcançável deve caber em 100 nós, 500 arestas e profundidade pelo menor caminho 20; fora disso a chamada recusa. Ciclos por cartões ilegíveis não são detectáveis; o grafo visível não prova que o global é acíclico. `deck_add_card_dependency` / `deck_remove_card_dependency` exigem `deck.edit`, EDIT na origem e READ no destino, mesmo para remover. Cada chamada altera só A→B; ambos os cartões e quadros devem estar ativos. Plano + `plan_state` + `confirm:true` (e `confirm_shared:true` quando necessário); autorrelações e ciclos detectáveis são recusados. Mudança de estado exige nova aprovação; duplicata/remoção ausente não escrevem. Outra alteração entre a última checagem e a escrita nativa ainda pode criar um ciclo. Resultado incerto exige conferir a UI antes de repetir.
- **Vínculos de arquivos do Deck:** `deck_list_card_files` exige `deck.read` + `files.read` e lista só associações nativas `file` cujos nós passam pelo escopo Files, tags de exclusão e READ. `attachmentId` é o ID do compartilhamento, distinto de `fileId`; uploads legados e pastas não são suportados. `deck_unlink_card_file` exige `deck.edit` + `files.read` e cartão/quadro ativos editáveis. Revise o plano e confirme com `plan_state` + `file_state` inalterado (e `confirm_shared` quando necessário). Desvincular preserva o original e compartilhamentos independentes, revogando este vínculo para membros atuais/futuros mesmo quando criado por outro membro. Vínculos invisíveis e inexistentes têm a mesma recusa, sem contagem ou handle. Um vínculo ausente só vira no-op com o recibo original válido e o arquivo original ainda visível; fora disso solicite novo plano ou use o Deck. Ainda existe uma janela entre a última validação e a desvinculação nativa. O vínculo de arquivo está em [Deck na 1.2.0](#deck-na-120): usa deck.edit, files.read e files.share, e a checagem vale só quando o vínculo é criado.
- **Fail-closed:** uma configuração que não pode ser validada (o manager falhando enquanto a lista é salva, ou um valor gravado ilegível ou inválido) preserva a configuração anterior e recusa o acesso, em vez de desligar a proteção; a tela de admin avisa e oferece o botão de reparo, e salvar a lista vazia pede confirmação. As decisões de visibilidade são invalidadas depois de mover, criar ou copiar, para não responder com estado antigo.
- **Logs:** com etiquetas configuradas e a opção **Esconder o texto das mensagens do log** ligada (padrão; chave `logs_hide_file_names`), as ferramentas de log escondem o texto das mensagens e das exceções, o user agent e o method fora dos verbos HTTP/WebDAV conhecidos, reduzem a URL aos prefixos fixos de rota e recusam o filtro `contains`, que bateria no texto escondido. Desligada, o log volta completo para diagnóstico — a opção existe porque equipes de TI leem exatamente esses detalhes para mapear problemas. O log de erros do próprio app grava só a classe e o código da exceção, nunca a mensagem, em qualquer instalação.
- **Limites declarados:**
  - A proteção vale apenas para este conector MCP, não para outras IAs, outros conectores nem para a interface web do Nextcloud.
  - Compartilhamentos federados são verificados apenas pelas etiquetas de sistema locais deste servidor.
  - Menções em texto livre ao nome de um arquivo em mensagens do Talk, descrições de eventos, descrições de tarefas ou cartões do Deck não são redigidas, e um nome solto que outro app grave em campo estruturado do log não é redigido quando a ocultação de texto do log está desligada.
  - **Storage externo montado duas vezes com raízes diferentes:** montar o *mesmo* diretório externo duas vezes com raízes diferentes (ex.: `/ext` e `/ext/Open`) cria dois storages distintos no Nextcloud com `fileId`s diferentes; uma etiqueta aplicada em uma montagem não cobre leituras pela outra. Duas montagens da *mesma* raiz (alias) compartilham `fileId`s e ficam protegidas juntas.
  - **Janela de cache da lista de etiquetas (~3 s entre processos):** alterações salvas pela interface de admin valem imediatamente naquele nó web. Alterações feitas via `occ` ou em outro nó web podem ser servidas desatualizadas por alguns segundos, porque o Nextcloud guarda a configuração do app em cache local por 3 s (`AppConfig::LOCAL_CACHE_TTL`, igual no Nextcloud 32–35); medido na suíte de integração, a nova lista passou a valer entre 2,7 e 3,9 s.

## Permissões por grupo e ciclo de vida da política (1.1.0)

As permissões por grupo (`mcp_group_grants`) e o ciclo de vida de autorização (`PolicyResolver`, `PolicyWriter`, `GroupSourceClassifier`, `GroupLifecycle` e `CauseProcessor`) permitem ao administrador conceder *Pode conectar* (`_system.eligible`, a preferência `eligible`) e operações de módulos (`<módulo>.<operação>`) a grupos nativos do Nextcloud sem perder garantias de revogação imediata (veja [Overrides individuais, prévia e inspetor de acesso](#overrides-individuais-prévia-e-inspetor-de-acesso-110) para a redefinição de overrides e o inspetor).

- **Precedência e semântica somente concessiva:** grupos apenas concedem (`Allow`); nunca negam nem estreitam. Overrides individuais por usuário (as preferências de usuário `eligible` e `grant_<módulo>_<operação>` do app `mcp`, com valores `'1'` = Permitir ou `'0'` = Negar) sempre prevalecem sobre concessões de grupo. Quando não há override individual, o usuário herda `Allow` se ao menos um grupo ativo e confiável ao qual pertence tiver a concessão em `mcp_group_grants`; caso contrário, aplica-se o padrão do módulo (`Allow` para `read`, exceto `logs.read`; `Deny` para todas as escritas e para `_system.eligible`).
- **Classificação de grupo confiável (`GroupSourceClassifier`):** um grupo só pode conceder permissões MCP quando o Nextcloud o resolve por **um único backend de grupo** que implementa `OCP\Group\Backend\INamedBackend` e informa `getBackendName() === 'Database'`. Grupos atendidos por LDAP, SAML, apps de terceiros, backend sem nome ou múltiplos backends ao mesmo tempo não são confiáveis e não podem conceder permissões MCP; o administrador deve conceder permissões aos membros individualmente.
- **Estados de ciclo de vida (`mcp_group_life`) e acesso incerto (`needs_confirm` / `unknown`):**
  - Cada grupo com estado de política possui uma linha em `mcp_group_life` (`group_key` SHA-256 de `group_id`, `group_id`, `state`, `gen`, `policy_rev`).
  - Se a criação ou exclusão de um grupo sofrer rollback ou for observada dentro de uma transação de banco alheia, ou se um grupo com concessões salvas perder sua classificação de backend único `'Database'`, seu estado passa a `needs_confirm` (**aguardando confirmação**). Enquanto estiver em `needs_confirm`, o grupo não concede nada, e suas linhas em `mcp_group_grants` são preservadas até que um administrador clique em **Confirmar política atual**, que grava de novo o conjunto atual do grupo por `PUT /apps/mcp/api/group-grants`, a partir de uma prévia.
  - O `PolicyResolver` retorna `unknown` (HTTP 503 no endpoint MCP, sem revogar tokens OAuth) **somente** quando a elegibilidade ou a permissão da ferramenta de um usuário depende exclusivamente de um grupo em `needs_confirm` e nenhum override individual `Allow` nem outro grupo ativo confiável concede a permissão. Em `tools/list`, uma ferramenta cuja concessão resolva para `unknown` é omitida em vez de falhar a listagem inteira (e, em ferramentas com concessões alternativas, basta uma concessão conhecida `Allow`).
  - As causas de revalidação pendentes de um usuário (`mcp_auth_recheck`) são processadas antes de a política ser lida (`CauseProcessor::preflight`: chamado pelo `McpController` para identidades Basic e de sessão, e, para tokens Bearer, pelo `AccessTokenAuthenticator` por meio de `TokenOwnerGate::preflight`). Só quando uma causa não pode ser classificada ou consumida (`PolicyUnavailable`) a requisição responde 503, quaisquer que sejam as outras fontes de acesso do usuário.
  - Quando o administrador retira *Pode conectar* (`_system.eligible`) de um grupo (ou quando um grupo é excluído), se o `PolicyWriter` não puder comprovar a elegibilidade remanescente de todos os portadores de credencial daquele grupo, a gravação é recusada (503) sem alterar o banco para que o administrador possa tentar novamente.
  - A exclusão de um grupo corre nesta ordem: o Before da exclusão primeiro põe o ciclo de vida em `needs_confirm` (`GroupLifeMapper::markSuspended()`), depois levanta os membros que têm credencial e registra as causas deles, e só então põe `pending_delete` (`markPendingDelete()`) quando todos os cortes foram registrados; o job só purga `pending_delete`, então uma falha no meio deixa o grupo suspenso com as linhas intactas, e o que ele concedia responde `unknown` (503). Uma nova conexão que dependia do grupo renova o estado dele e é recusada se a suspensão vencer. Limite residual: se a suspensão perder a corrida três vezes, uma conexão feita nesse intervalo só volta a valer se o administrador confirmar explicitamente a política do grupo.
  - A saída de um membro do grupo é registrada mesmo quando o usuário tem um `Allow` individual; um reset em andamento nesse momento é recusado com conflito e, repetido, corta.
  - Voltar um `Allow` individual de elegibilidade para `Inherit` corta credenciais só quando o usuário realmente perde a elegibilidade; se um grupo mantém o usuário elegível, nada é cortado, e quando o que o usuário herda é desconhecido a mudança é recusada sem gravar nem cortar.
- **Commits de política serializados, gerações e transações alheias:**
  - `PolicyWriter` serializa mutações de política pela linha única de `mcp_policy_state` (`id = 1`, `revision`, `lock_seq`, `auth_epoch`). Códigos OAuth, tokens e refresh tokens gastos carregam `(auth_global_epoch, auth_gen)`, conferidos contra `mcp_policy_state.auth_epoch` e a linha tombstone do usuário em `mcp_auth_users` (`issue_seq`, `revoked_below`).
  - Os listeners de eventos registrados em `Application.php` nunca executam SQL enquanto `IDBConnection::inTransaction()` for verdadeiro (uma consulta com erro dentro de uma transação alheia abortaria a própria transação do Nextcloud no PostgreSQL). Em vez disso, as causas são enfileiradas em memória (`DeferredQueue`) e processadas por uma função de encerramento quando a transação chamadora termina; o que ainda estiver pendente fica em `mcp_auth_recheck` e é tratado pela tarefa em segundo plano `ReconcileJob` (a cada 15 minutos), e o app continua correto quando a tarefa não roda, porque cada requisição de um usuário processa antes as causas dele.
- **Garantia ("por eventos entregues") e limites declarados:**
  1. **Exclusão + recriação de grupo com o mesmo `GID` quando sinais se perdem:** se o processo PHP terminar antes do processamento diferido rodar, durante a janela entre o commit do chamador e o processamento diferido (incluindo exclusão + recriação na mesma transação), ou com transação alheia ainda aberta no encerramento do processo, um grupo recriado com o mesmo `GID` pode herdar a política do grupo antigo, e requisições concorrentes nessa janela ainda podem avaliar a política antiga.
  2. **Nome de backend `'Database'`:** o Nextcloud não autentica nem reserva `INamedBackend::getBackendName()`. Qualquer backend de grupo instalado pelo administrador que retorne `'Database'` é tratado como o backend nativo de banco de dados.
  3. **Ida e volta de backend não observada:** se o backend de um grupo mudar de `'Database'` para outra fonte e voltar entre duas observações, a mudança intermediária não é detectada.
  4. **Caches em memória em processos longos (`occ` / workers):** `Database::groupExists` mantém um cache positivo, o `AppManager` mantém seu próprio cache dos apps habilitados e `IUserManager::get` devolve objetos `IUser` memorizados. Requisições web rodam num processo PHP novo por requisição; comandos longos de CLI ou workers podem observar estado em cache até terminarem.
  5. **Exceção decidida em causas de usuário sem data em transação alheia:** na dúvida, o app revoga credenciais OAuth. A única exceção intencional ocorre quando uma causa de usuário é capturada dentro de uma transação aberta por outro código (sem data) e o usuário continua elegível quando o `CauseProcessor` processa a revalidação depois: nesse caso, nem credenciais antigas nem novas são cortadas.
  6. **Custo em instalações grandes (medido, 1.1.0):** excluir um grupo e retirar *Pode conectar* de um grupo custam um tempo proporcional ao número de usuários que já conectaram um cliente MCP (e não ao tamanho do grupo): com cerca de 1.000 deles, de 9 a 19 segundos numa única requisição, e a prévia da retirada de *Pode conectar* leva quase o mesmo; abrir um grupo de 5.000 membros leva de 1,5 a 2 segundos. Os números vêm de uma máquina com banco local; em hardware mais lento ou com banco remoto crescem na mesma proporção. A otimização está prevista para uma versão futura (1.3.0 no roadmap).
- **Atualização, incidentes e rollback:** atualizar a partir da 1.0.8 executa automaticamente as migrações nativas (`Version001100Date20261014000000` até `Version001100Date20261016000000` e `PolicyStateSeedStep`). **Voltar o código do app para a 1.0.8 sobre o mesmo banco não é seguro**, porque a 1.1.0 revoga credenciais OAuth de forma lógica e as remove depois, então uma credencial revogada na 1.1.0 e ainda não removida pode voltar a valer na 1.0.8 (não faça isso: veja abaixo). Depois de usadas permissões por grupo ou restrição por recurso, é pior: a 1.0.8 ignora `mcp_group_grants`, ignora `(auth_global_epoch, auth_gen)` nas tabelas OAuth (de modo que tokens cortados apenas por geração ou época podem voltar a ser aceitos) e ignora `mcp_scope_modes` / `mcp_scope_items` (de modo que usuários restritos a recursos específicos recuperam acesso a todos eles). Voltar da 1.1.0: avance para uma versão 1.1.x corrigida (mantendo o esquema e as épocas da 1.1.0); nunca ponha só o código da 1.0.8 sobre o banco da 1.1.0 nem restaure banco e código de backups diferentes. Se for preciso voltar, restaure a instalação inteira (código, configuração, banco de dados e diretório de dados) do mesmo backup feito antes da 1.1.0, em modo de manutenção e seguindo o procedimento de restauração do próprio Nextcloud, e então desligue o serviço MCP nas configurações de administração: isso apaga todas as conexões OAuth e, enquanto desligado, recusa clientes por app password (Basic) e links de checkout (`canConnect`). App passwords são do Nextcloud, não são apagadas pelo app, e o banco restaurado traz de volta as revogadas depois do backup; por isso cada usuário do MCP deve revogar as app passwords usadas com o MCP em *Configurações pessoais → Segurança* antes de o serviço ser religado (quem não o fez deve ficar sem elegibilidade). Links de checkout emitidos expiram em até 15 minutos (`CheckoutService::DOWNLOAD_TTL` 300 s, `UPLOAD_TTL` 900 s), então mantenha o serviço desligado pelo menos esse tempo; depois religue e reaplique o que mudou depois do backup, inclusive app passwords revogadas e contas desativadas. Uma restauração perde tudo o que foi feito depois do backup. Não é preciso terminal, `occ` nem SQL.

## Overrides individuais, prévia e inspetor de acesso (1.1.0)

Três rotas só de administrador ficam ao lado da API de grants; cada uma responde 403 a quem não é administrador antes de olhar qualquer usuário ou política, e mantém a checagem CSRF do Nextcloud.

- **Redefinir para a herança:** `POST /apps/mcp/api/grants/commands` recebe `{expectedRevision, commands}` com, por célula, `{uid, module, operation, state}` em que `state` é `allow`, `deny` ou `inherit` (remove o override individual); no máximo 50 usuários e 2.500 células (`PolicyWriter::MAX_UIDS`, `MAX_CELLS`). Responde `{revision, changed, receiptId}`, ou 400/409/428/503. Um `expectedRevision` desatualizado responde 409 e nada é gravado. `POST /apps/mcp/api/grants/undo` restaura os valores anteriores a partir do recibo.
- **Prévia de uma redefinição:** `POST /apps/mcp/api/grants/commands/preview` (`OverridePreviewController`, `OverridePreview`) recebe as mesmas células com `state: "inherit"`, sem `expectedRevision`, e responde `{revision, cells}`: por célula, o `before` e o `after` como `{allowed, source, groupIds}`, com `null` para desconhecido, nunca `false`. É só leitura: sem escrita, sem transação, sem mutex e sem observação persistida da confiança de grupo, e recusa rodar dentro de uma transação. O "depois" é calculado pela mesma resolução sem o valor individual (`resolve()` com `inherited: true`, exposta como `PolicyOperationContext::inherited()`) que o writer usa na checagem de elegibilidade de uma redefinição, por meio de `inheritedEligibility()` (F2); a resposta vem junto com a revisão em que foi lida e, se a revisão mudar durante a leitura, é lida de novo uma vez e depois responde 503. A página (`js/admin-overrides.js`) envia essa revisão como `expectedRevision` da redefinição (ou, quando a prévia não pôde ser lida, a revisão da tabela), então uma mudança desde a prévia termina em 409. Corpos inválidos respondem 400. Um *Allow* sobre um *Allow* herdado não tem controle direto (o texto de ajuda da página descreve o caminho de desmarcar e marcar de novo).
- **Inspetor:** `GET /apps/mcp/api/inspector/access?uid=` (cada operação do catálogo: `allowed`, `reasonCode`, `blockingGate`, a resolução do grant com `source` e `groupIds`, e o escopo como `mode` e `count`), `GET /apps/mcp/api/inspector/path?uid=&path=` (por que as ferramentas de Arquivos alcançam ou não um caminho do usuário: `reason`, `gate`, `exclusion`, `folder`) e `GET /apps/mcp/api/inspector/calendar?uid=&module=&calendarId=&operation=` (um calendário ou lista de tarefas; `module` é `calendar` ou `tasks`). As respostas vêm de `PolicyResolver::resolveEffective()`, depois o escopo, o guard de exclusão e a ACL nativa, na ordem das ferramentas, nunca de uma regra paralela; `allowed` só é dito quando todas as verificações foram avaliadas, senão `not_evaluated` nomeia a verificação. `reason` é `allowed`, `blocked`, `out_of_scope`, `no_native_access`, `read_only` (calendários), `not_found`, `excluded` ou `not_evaluated`. Para um caminho excluído (`reason: excluded`), `exclusion` é `tag_direct`, `tag_folder`, `tag_share_origin`, `backup_of_excluded` ou `invalid_configuration`, e `folder` é o ancestral etiquetado na árvore do usuário: esse detalhe é para o administrador, enquanto as ferramentas continuam respondendo "não encontrado". Uma exclusão que não pode ser avaliada vem como `reason: not_evaluated` com `gate: exclusion` e `exclusion: null`. O inspetor não grava nada e não persiste observação. Entrada inválida responde 400 e uma política ilegível, 503.
- **Auditoria:** o `InspectorController` grava uma linha *info* por pergunta, `MCP access inspection` (`admin`, `target`, `action` = `inspect_access`, `inspect_path` ou `inspect_calendar`, `module`, código de `result`, `timestamp`), nunca um caminho, um calendário ou um título; uma falha grava uma linha de *erro* `MCP access inspection failed` só com a classe da exceção. Como na auditoria do escopo, as linhas *info* só são gravadas com o `loglevel` do servidor em 1 ou menos (o padrão, 2, não grava), então isto não é uma trilha de auditoria garantida.

## Restrição por recurso (1.1.0)

`ScopeGuard`, `ResourceScopeMapper`, `NativeResourceEnumerator`, `ScopeActivation`, `FilesScope` e `FilesAccessGuard` implementam a lista opcional de recursos permitidos por usuário. `ScopeActivation::MODULES` tem `'files' => true` (B5: todo consumidor de Arquivos é estreitado pela porta de Arquivos), `'calendar' => true` e `'tasks' => true` (B6, por meio da `ScopedCalendarAccess`), então um escopo pode ser gravado em qualquer módulo e nenhum responde 422 `ScopeInactive`.

- **Esquema (`Version001100Date20261015020000`):**
  - `mcp_scope_modes`: `(user_key, module, user_id, policy_rev)`, PK `(user_key, module)`. A presença de uma linha significa que o usuário está no modo `restricted` naquele módulo; a ausência significa `all` (irrestrito).
  - `mcp_scope_items`: `(user_key, module, resource_key, resource_id)`, PK `(user_key, module, resource_key)`, até 200 itens por `(usuário, módulo)`. `user_key` e `resource_key` são resumos SHA-256 do ID do usuário e do módulo e ID do recurso, para manter as chaves primárias compactas, enquanto os textos exatos `user_id` e `resource_id` são gravados e conferidos na leitura.
- **Precedência e uniformidade:** `Restrição por recurso > Exclusão por etiqueta de sistema > ACL nativa do Nextcloud`. Após as verificações de acesso e da permissão da operação, uma restrição por recurso ilegível responde 503 antes da busca de qualquer item. Um calendário ou lista de tarefas fora do escopo devolve `CalendarException::notFound()`, a recusa de um calendário que não existe; um escopo que não pode ser lido faz a operação falhar com `PolicyUnavailable` (503), também para um calendário que não existe (`ScopeReader::assertReadable()` roda antes da busca nativa, então a existência nunca se distingue por um 503). Em Arquivos, a `FilesAccessGuard::assertScopeReadable()` lê o escopo antes de a ferramenta fazer qualquer coisa, então um escopo ilegível responde 503 em toda ferramenta `files_*`, em `nc://files` (`ResourceRegistry`) e no `files_checkout`, qualquer que seja o caminho pedido; um nó fora do escopo é recusado exatamente como um nó oculto ou inexistente.
- **Módulos:**
  - `files`: pastas permitidas por ID de arquivo, cobrindo cada pasta selecionada e seus descendentes. Um nó está dentro do escopo quando ele mesmo ou um de seus ancestrais é uma pasta selecionada, na cadeia em que o usuário a alcança: a própria árvore dele ou, acima da raiz de um compartilhamento montado, a cadeia do dono (a `FilesScope::candidates()` sobe por metadados, sobre o `VisibilityGuard::parentOf()`, e resolve a cadeia do dono de cada raiz de compartilhamento que atravessa). Uma cadeia que não pode ser resolvida fica fora do escopo, nunca dentro. A `FilesAccessGuard` estende o `VisibilityGuard`: `isVisible()` aplica primeiro o escopo e depois a exclusão, enquanto `isTraversable()` mantém só a exclusão, de modo que ancestrais cruzados apenas no caminho até um destino (criar uma pasta em uma pasta selecionada ou abaixo dela) respondem apenas à exclusão. A `FilesScope::roots()` substitui `/` em uma listagem pelas pastas selecionadas mais externas, em seus caminhos reais, quando a própria raiz está fora do escopo. Notas (D4), as páginas de admin e a enumeração nativa mantêm o `VisibilityGuard` simples. Os itens vêm do instantâneo de política da operação (`GrantPolicy::scopeItems()`), então uma operação nunca mistura dois escopos.
  - **Limites do escopo de Arquivos (declarados):**
    - **Backups (N2):** `BackupLocation` fornece o nome configurado na raiz e todos os nomes históricos reservados. As cópias usam esse destino quando ligadas; excluir contato sempre exige cópia. Cópias internas podem ficar fora do escopo Files selecionado, sem conceder acesso de leitura a elas. Etiquetas de exclusão são aplicadas antes do conteúdo; falha na cópia obrigatória recusa a escrita original. `BackupFolderMatcher` reconhece apenas candidatos na raiz do dono, inclusive nomes históricos, e usa snapshot por requisição na listagem; fronteiras de escrita releem a configuração.
    - **Uma raiz selecionada não pode ser renomeada (N2):** o `Reorganization::destination()` resolve o pai do destino pela porta, e o pai de uma pasta selecionada mais externa está fora do escopo, então renomeá-la pelo MCP é recusado. Mover e copiar dentro do escopo continuam funcionando.
    - **O dono moveu a origem em outro processo (N4):** a `FilesScope` memoriza as cadeias resolvidas e as cadeias de dono por operação e as invalida em `NodeRenamedEvent`, `NodeCopiedEvent` e `NodeDeletedEvent` do mesmo processo. Uma movimentação feita pelo dono em outro processo enquanto uma requisição roda pode, portanto, ser julgada pela cadeia antiga só naquela requisição; a requisição seguinte lê a nova. Mesma janela do cache das etiquetas de exclusão.
    - **Montagens:** os IDs gravados são os IDs de arquivo que `Node::getId()` devolve, então a limitação das etiquetas de exclusão vale de forma idêntica: montar o mesmo diretório externo com raízes diferentes cria dois armazenamentos com IDs próprios, cada um protegendo só o que é lido por ele, enquanto dois montes da mesma raiz (um alias) compartilham os IDs e ficam protegidos juntos.
    - **Cache da lista de etiquetas de exclusão (~3 s entre processos):** uma mudança na lista de etiquetas de exclusão feita por outro processo ou nó (o `occ`, ou outro nó web de uma instalação com vários nós) pode levar cerca de 3 segundos para valer; uma mudança pela página de admin no mesmo nó vale imediatamente. Essa janela é distinta da janela de uma requisição da cadeia do dono descrita acima. Nada no escopo precisa de `occ`.
  - `calendar`: calendários de eventos (`VEVENT`) permitidos, identificados pelo id do calendário no backend (um compartilhamento o mantém do calendário do dono e um renomear não o muda; a URI, o nome de exibição e o caminho nunca são chave). O `ScopedCalendarAccess` envolve o `CalendarAccess` para as ferramentas de calendário (`ListCalendars`, `ListEvents`, `CreateEvent`, `UpdateEvent`, `DeleteEvent`, `MoveEvent`, `SharedCalendarFinder`) e para as referências a eventos do Talk (`ReferenceLinker`); o escopo vem antes da checagem de escrita, então um calendário fora dele está ausente, nunca "somente leitura". Mover ou transferir um evento exige que tanto o calendário de origem quanto o de destino estejam no escopo (o `EventRelocator` resolve os dois por ele).
  - `tasks`: calendários de tarefas (`VTODO`) permitidos, independentes de `calendar` mesmo quando um mesmo calendário subjacente guarda os dois: o componente decide o módulo de escopo (`VEVENT` → `calendar`, `VTODO` → `tasks`). O `TasksModule` usa o mesmo envoltório, e um objeto lido pelo UID olha só o componente da ferramenta (`CalendarStore::objectByUid($id, $uid, $component)`), então um evento e uma tarefa com o mesmo UID nunca respondem um pelo outro. As páginas de admin e a enumeração nativa de recursos mantêm o `CalendarAccess` sem escopo, então um escopo nunca esconde um calendário de quem o configura.
  - **Notas (`notes`) fica fora do escopo de pastas de Arquivos** e não é restringido pelos itens de escopo de `files`.
  - **Não suportado na 1.1.0:** escopo por recurso para `notes`, `contacts`, `deck` e `talk`; escopo por recurso por grupo (grupos só concedem; o escopo por recurso de um usuário continua restringindo-o mesmo quando sua permissão de módulo vem de um grupo); redação automática de texto livre.
- **Garantias operacionais:**
  - Alterar o escopo por recurso de um usuário grava via `PolicyWriter::setResourceScope` (exigindo a `revision` atual; uma desatualizada responde 409) e **não revoga** as sessões OAuth do usuário: o novo escopo vale a partir da próxima requisição.
  - Consultas administrativas de escopo (`GET /apps/mcp/api/scope/{uid}/{module}`, `GET /apps/mcp/api/scope/{uid}/{module}/candidates`) e alterações (`PUT /apps/mcp/api/scope/{uid}/{module}`) são gravadas no log do Nextcloud em nível *info* (`MCP resource scope admin request`: administrador, usuário-alvo, ação, resultado, módulo e contagens, nunca nome, caminho ou título de recurso). Só aparecem com o `loglevel` do servidor em 1 ou menos; o padrão (2) não grava linhas *info*, então isto não é uma trilha de auditoria garantida. Cada usuário lê o próprio escopo, somente leitura, em *Configurações pessoais → Restrição por recurso* (`GET /apps/mcp/api/my/scope`, `js/personal-scope.js`): ele nomeia as pastas, calendários ou listas de tarefas de cada módulo, diz "todos os …" para um módulo irrestrito e avisa quando o escopo não pode ser lido, nunca "irrestrito". O efeito de um escopo sobre um usuário pode ser inspecionado com o inspetor acima.
  - **Contas excluídas (B3):** o `UserCauseListener` captura a revisão de política `R_b` no `BeforeUserDeletedEvent` (em autocommit, fora de transação) e a `ScopeCleanup::deleted()` remove, no `UserDeletedEvent`, os escopos salvos até `R_b` (`ResourceScopeMapper::removeUpTo()`, sobre `mcp_scope_modes.policy_rev`), então um escopo salvo depois de a exclusão ter começado é mantido. Sem sinal, nada é removido: quando o evento se perde (o Before rodou dentro de uma transação ou falhou, ou o After nunca veio porque a exclusão foi desfeita), a restrição fica. O último passo do `ReconcileJob` chama a `ScopeCleanup::reconcile()`, que não remove nada e não grava política: ela percorre por páginas os usuários que ainda têm escopo (`RECONCILE_BATCH`, a partir do app config `scope_cleanup_cursor`) e os conta em uma linha *info* `MCP resource scope diagnostic pass` (`users`, `kept_account_exists`, `absent`, `blocked_or_failed`, `orphan_item_users`). Provar que uma conta sumiu não está nas mãos do app (um backend de diretório inacessível pode responder "não existe tal usuário", e a conta pode ser recriada entre a prova e a escrita), então uma restrição órfã é mantida: uma conta recriada com o mesmo UID continua restrita, o que só estreita.

## Configurar

1. **Administração → MCP for Cloud** (entrada própria, com ícone, no menu de configurações): na aba **Visão geral**, marcar *Serviço MCP ativado*; na aba **Acesso e permissões**, usar a matriz de **Permissões** e o editor de **Permissões de grupo**.
   - A página tem cinco abas, cada uma acessível pelo teclado e por endereço (`#overview`, `#access`, `#clients`, `#protection`, `#advanced`); um link abre a aba que ele nomeia, e uma configuração de exclusão ilegível é sinalizada na Visão geral com o caminho para o reparo.
   - O bloco **Status** da Visão geral mostra o endpoint (com copiar), o serviço, a versão do app, quantos usuários podem conectar e quantos estão conectados, as conexões OAuth ativas e o **limite de envio do checkout** (`files_checkout`), editável em MiB, com o limite efetivo e o teto `post_max_size` do PHP ao lado. Antes isso só mudava por `occ`.
   - As demais abas: **Acesso e permissões** (editor de **Permissões de grupo**, matriz de **Permissões** com a redefinição de overrides individuais, o **Inspetor de acesso** e a **Restrição por recurso**, em gavetas laterais), **Clientes e conexões** (**Clientes OAuth** e **Conexões ativas**), **Proteção de dados** (**Excluídos do acesso MCP**) e **Avançado** (**Log do servidor**, **Privacidade do log** e **OCR**). Os grupos do log do servidor e as etiquetas de exclusão são escolhidos em listas com busca e resumo.
   - Em **Permissões**, a busca procura por nome, ID ou e-mail. Os filtros são por grupo e por "só quem pode conectar / só conectados" (feitos no servidor, com total exato; a lista começa pelos usuários que podem conectar), por aplicativo ("Mostrar apps", guardado no endereço como `#access?app=<módulo>`, aplicado só no navegador, um módulo desconhecido volta para todos os apps) e **Todos | Com exceções** (as pessoas da página com um valor individual diferente do que herdam). A tabela mostra 50 usuários por página, com contador e paginação em cima e embaixo; as colunas de seleção, usuário e *Pode conectar* ficam fixas na rolagem lateral, e o foco do teclado nunca fica escondido sob elas.
   - A matriz mostra **um nível por módulo** (*Nenhum*, *Ler*, *Editar*, *Total*; `js/admin-levels.js`) em vez de uma caixa por operação. O nível é só uma forma de escolher um conjunto de operações (faixas cumulativas que seguem o catálogo; o servidor nunca o vê): escolher uma célula abre uma janela (`js/admin-level-popover.js`) com os níveis e o que cada um permite, o que a pessoa herdaria e *Herdar*; um conjunto de operações que não é nenhum nível aparece como *Personalizado* e é editado na visão **Operações**, que mantém a caixa de três estados por operação. Escolher grava na hora, com *Desfazer* por 10 segundos (um cronômetro do navegador que pausa com o mouse e o foco; ele restaura os valores anteriores exatos, inclusive a ausência de definição individual; se a política mudou nesse meio-tempo, desfazer é recusado com 409 e a tabela é recarregada; o recibo da mudança no servidor expira em 600 segundos); uma mudança ou desfazer roda por vez. *Pode conectar* é uma célula como as outras, e desligá-lo mostra antes quantas conexões terminam. Só as **exceções** são marcadas (`js/admin-exceptions.js`): um valor definido para a pessoa e diferente do que ela herda tem um ícone de pessoa, um valor vindo de um grupo tem um ícone de grupo mais discreto, e um padrão, ou um valor que só repete a herança, não tem marca; quando a conta está desativada ou *Pode conectar* está desligado, um aviso substitui as células de permissão, e um app ou papel de log indisponível é marcado com ⊘, com o motivo ao passar o mouse e para leitores de tela. Um aviso oferece **revisar** os valores individuais que repetem o que a pessoa já herda (hoje não mudam nada, mas impedem que mudanças nos grupos cheguem à pessoa), abrindo a prévia da redefinição só com essas células.
   - Cada linha tem um **menu de ações** (`js/admin-row-actions.js`: *Inspecionar acesso*, *Restringir recursos*, *Voltar tudo à herança…*, *Copiar ID do usuário*) e uma caixa de seleção. Com pessoas selecionadas, uma **barra de seleção** (`js/admin-overrides.js`) define o nível de um módulo, ou *Pode conectar*, para todas elas, ou devolve os valores delas à herança, depois de uma confirmação que conta os usuários que mudam, os deixados de fora porque a permissão está indisponível ou desconhecida para eles e os que já têm o valor (nada é enviado quando ninguém muda). Ela substitui os menus *Todos* que os cabeçalhos tinham.
   - Em **Permissões de grupo** (`js/admin-groups.js`), os grupos formam uma lista ao lado do grupo aberto, com rolagem própria, uma linha por grupo (nome e ID, um resumo curto), uma busca e o filtro **Todos | Com concessões | Bloqueados** (`filter=all|granted|blocked` do diretório; o servidor filtra e pagina, 50 por página, com as contagens de cada filtro); um grupo que não pode conceder mostra um cadeado, e um aguardando confirmação ou em exclusão mostra um aviso, sempre com texto. No celular um seletor abre e fecha a lista. O grupo aberto é editado com os mesmos níveis da matriz, com uma barra **Revisar e salvar**: a prévia (permissões adicionadas e removidas, membros atuais, titulares de credencial que podem ser desconectados; uma estimativa, não o acesso efetivo exato de cada membro) vem antes de salvar, e o administrador confirma a política atual de um grupo suspenso. *Ver na matriz* abre a matriz filtrada por aquele grupo e por *Com exceções*, mostrando as pessoas da página atual cujos valores individuais diferem do que herdam.
   - Em **Restrição por recurso** (`js/admin-scope.js`, 1.1.0), uma gaveta lateral aberta pelo menu de ações de um usuário ou por *Restringir os recursos de uma pessoa…*, um usuário por vez: para cada módulo (Arquivos, Calendário, Tarefas) escolha "Todos os recursos" ou "Somente os selecionados" e marque pastas, calendários ou listas de tarefas entre os recursos que o usuário alcança no próprio Nextcloud. Nada é decidido no navegador: o servidor valida cada item e as ferramentas aplicam a restrição; um conflito (409) relê a restrição atual em vez de repetir a gravação, e cada módulo guarda a revisão em que o rascunho dele foi lido. *Desfazer* restaura os valores anteriores por 10 segundos, como no resto da página. A matriz marca um módulo restrito como *Restrito a N* na primeira célula e abre a gaveta a partir dela, ou *Restrição desconhecida* quando a restrição não pode ser lida; a página informa que restringir não encerra as sessões do usuário. O **Inspetor de acesso** (`js/admin-inspector.js`) também é uma gaveta lateral e dá a resposta primeiro.
   - Usuários desativados aparecem marcados e não podem ser editados. Módulos cujo app não existe no servidor não aparecem na matriz; para usuário sem acesso ao app, a célula fica desabilitada. As permissões já salvas são preservadas.
   - O e-mail só entra na busca e nunca é exibido.
2. **Excluídos do acesso MCP**: escolha etiquetas de sistema para que os arquivos e pastas marcados fiquem completamente invisíveis às ferramentas MCP (leitura, busca, listagem, imagens, notas, talk, tarefas e checkout; as ferramentas do log do servidor, apenas enquanto "Esconder o texto das mensagens do log" estiver ligado). Recomendam-se etiquetas restritas ou invisíveis. A etiqueta vale para os descendentes, compartilhamento local herda a ocultação da pasta de origem do dono, compartilhamento/link/cópia/movimentação de pastas entre diretórios são recusados enquanto houver etiqueta configurada, e, na dúvida (configuração inválida, falha na consulta), o app recusa; ver [Etiquetas ocultas (1.0.6 e 1.1.0)](#etiquetas-ocultas-106-e-110).
   - Serviço, elegibilidade e conexão pessoal começam desligados para todos, inclusive administradores. Leitura começa permitida; escrita, exclusão, transferência e compartilhamento começam negados. Em Files, `files.share` (compartilhar com pessoa ou grupo) e `files.link` (link público) são duas operações separadas, para que o admin possa liberar uma sem a outra; ambas vêm desligadas. Listar compartilhamentos continua sendo leitura.
   - A página usa a API JSON admin-only `GET /apps/mcp/api/grants` (`search`, `group`, `filter` = `eligible`/`connected`, `page`), `PUT /apps/mcp/api/grants/{uid}`, `POST /apps/mcp/api/grants/bulk`, `POST /apps/mcp/api/grants/commands`, `POST /apps/mcp/api/grants/commands/preview`, `POST /apps/mcp/api/grants/undo`, `GET /apps/mcp/api/inspector/access`, `GET /apps/mcp/api/inspector/path`, `GET /apps/mcp/api/inspector/calendar`, `GET /apps/mcp/api/group-directory`, `GET /apps/mcp/api/group-directory/detail`, `GET`/`PUT /apps/mcp/api/group-grants`, `POST /apps/mcp/api/group-grants/preview`, `GET`/`PUT /apps/mcp/api/scope/{uid}/{module}`, `GET /apps/mcp/api/scope/{uid}/{module}/candidates`, `PUT /apps/mcp/api/service`, `GET`/`PUT /apps/mcp/api/checkout-limit` (`{mib}` inteiro ≥ 1) e, para as conexões, `GET /apps/mcp/api/connections`, `DELETE /apps/mcp/api/connections/{id}` e `DELETE /apps/mcp/api/connections/users/{uid}`. Para as etiquetas de ocultação e a opção do log, `GET`/`PUT /apps/mcp/api/admin/tags` e `GET`/`PUT /apps/mcp/api/logs-privacy` (`{hideFileNames}`). Nenhuma resposta traz hash de token.
3. **Clientes OAuth**: o bloco *OAuth clients* da seção **MCP for Cloud** edita os hosts de cliente permitidos e liga o cliente nativo para programas locais, sem passo de terminal. A API é `GET /apps/mcp/api/oauth-clients` e `PUT /apps/mcp/api/oauth-clients` (admin-only, com CSRF do Nextcloud), aceita `hosts` e/ou `nativeClientEnabled`, valida tudo antes de gravar e recusa uma lista de hosts inválida em vez de escrevê-la. Desligar o cliente nativo revoga na hora os tokens já emitidos para ele.
4. **Configurações pessoais → MCP for Cloud**: o próprio usuário clica em *Connect*. A página mostra o estado (serviço, permissão do administrador, conexão) e a lista **Seus clientes conectados** (cliente, conectado em, expira em) com *Revogar*, pela API `GET /apps/mcp/api/my/connections` e `DELETE /apps/mcp/api/my/connections/{id}`, restrita às conexões do próprio usuário.
5. Em **Configurações pessoais → Segurança**, o usuário cria uma senha de app. O cliente MCP usa autenticação HTTP Basic com o ID do usuário e essa senha de app. O app nunca pede nem guarda a senha principal.

Risco residual nas escritas: colisões com destinos ocultos usam a mesma recusa genérica de destinos sem permissão, mas a diferença entre recusa e criação possível ainda permite inferir que um caminho está indisponível.

O login pelo navegador via OAuth está descrito em [Conectar pelo claude.ai (OAuth)](#conectar-pelo-claudeai-oauth) e, para ChatGPT e Gemini CLI, em [Conectar pelo ChatGPT e pelo Gemini CLI (OAuth)](#conectar-pelo-chatgpt-e-pelo-gemini-cli-oauth).

| usuário, app `mcp` | `connected` | `1` conexão pessoal ativa |

| tabelas próprias | `mcp_group_grants`, `mcp_group_life` | concessões por grupo (`group_key`, `group_id`, `module`, `operation`) e estado de ciclo de vida do grupo (`active`, `needs_confirm`, `pending_delete`, `gen`, `policy_rev`) |

| app `mcp` | `oauth_client_hosts` | lista de hosts separados por vírgula; ausente ou vazia vale o padrão `claude.ai,chatgpt.com` |
| tabela própria | `mcp_oauth_clients` | os clientes OAuth do administrador, uma linha por cliente (`client_id` PK, `kind` native/custom, `name`, `enabled`, `redirect_uris` JSON, `gen` BIGINT, `position`): o interruptor do cliente nativo e os clientes auto-hospedados (`nextcloud-mcp-custom-<12 hex>`). Única fonte da admissão: lida do banco pelo consentimento, troca e renovação sob o mutex da política e por toda checagem de Bearer, nunca pelos caches do AppConfig; gravada só pelo comando de admin. Sem linha do nativo = desligado. `gen` avança a cada retirada e nunca volta; uma linha inválida recusa o cliente |

A chave `enabled` do app `mcp` pertence ao Nextcloud, que a usa para marcar o app como habilitado (`yes`), e não é o liga/desliga do MCP. O app nunca lê nem grava `enabled`, `installed_version`, `types`, `levels` ou `ocsid`. Para diagnóstico: `occ config:app:get mcp service_enabled`.

## Conectar pelo claude.ai (OAuth)

No claude.ai, em **Personalizar > Conectores > Adicionar conector personalizado**, cole a URL exibida na página pessoal (ex.: `https://<instância>/apps/mcp/`), com a barra final, e deixe o cliente OAuth em **identidade publicada do Claude (CIMD)**. O Claude abre o login do Nextcloud e a tela "Permitir"; permitir equivale a ativar a conexão pessoal. Tudo fica sob `/apps/mcp`, sem mudança de Apache/DNS:

- `401` com `WWW-Authenticate: Bearer resource_metadata=".../apps/mcp/.well-known/oauth-protected-resource"`;
- metadata do servidor de autorização em `/apps/mcp/.well-known/openid-configuration` e `/apps/mcp/.well-known/oauth-authorization-server` (issuer `https://<instância>/apps/mcp`);
- `oauth/authorize` (consentimento) e `oauth/token` (PKCE S256, refresh com rotação). Access token 1 h, refresh 30 dias; só hashes vão ao banco.

Três tipos de cliente são aceitos: clientes CIMD com host na allowlist, o cliente nativo quando habilitado e os clientes auto-hospedados que o administrador adicionou. O redirect URI é comparado de forma exata para todos, exceto que um URI `http` loopback (`127.0.0.1`, `[::1]`, `localhost`) ignora a porta (RFC 8252 7.3) só para os clientes CIMD e nativo; o cliente auto-hospedado compara o URI gravado byte a byte, porta incluída. App passwords (HTTP Basic) são independentes de qualquer cliente OAuth. A allowlist padrão é `claude.ai,chatgpt.com` e é editada sem terminal em **Administração → MCP for Cloud → Clientes OAuth → Hosts de clientes permitidos** (host exato, sem `https://`, porta, caminho ou `*`, ao menos um; salvar substitui a lista inteira e remover um host recusa o cliente na hora, mesmo com o documento em cache). A chave `oauth_client_hosts` não precisa ser gravada à mão: um valor salvo antes da 0.8.0 é preservado e o padrão só vale quando a chave está ausente ou vazia. A mesma seção liga **Permitir programas locais (cliente nativo)**, que habilita o `client_id` público fixo `nextcloud-mcp-native` (desligado por padrão) para programas locais como o Gemini CLI, e mostra os redirect URIs loopback aceitos. **Clientes auto-hospedados (URIs de redirecionamento personalizadas)** lista os clientes públicos que o administrador adiciona (nenhum por padrão, no máximo 20): cada um tem um nome (único, até 64 caracteres, exibido na tela de consentimento e nas listas de conexões), a opção **Ativado**, um `client_id` aleatório próprio `nextcloud-mcp-custom-<12 hex>` e de 1 a 20 redirect URIs exatos (`https` absoluto, `http` só em loopback; sem userinfo, `*` ou fragmento; até 2000 bytes; os três tipos de cliente diferem em como o redirect URI é comparado, veja abaixo). Desligar o cliente nativo, ou desativar um cliente auto-hospedado, excluí-lo ou remover um dos redirect URIs dele, revoga só aquele cliente, nunca os outros clientes do usuário: a mudança da configuração e a exclusão dos tokens, códigos pendentes e registros de renovação gastos daquele cliente são uma transação sob o mutex da política (`OAuthClientsService`, `PolicyWriter::runAdmin` com `expectedRevision`; uma tela desatualizada recebe 409 com o estado atual, uma exclusão que falha desfaz a mudança), e consentimento, troca de código e renovação admitem o cliente de novo sob esse mesmo mutex, então uma unidade que leu o estado antigo antes da mudança não grava nada depois dela. Uma tela de consentimento aberta antes é revalidada ao permitir e ao negar, e uma geração por cliente (avança quando o cliente é desativado ou perde um redirect URI) impede que um cliente desativado e ativado de novo a ressuscite. Um cliente desativado ou excluído não troca código, não renova e não autentica (o Bearer lê a configuração de novo a cada requisição). Os clientes ficam na tabela própria `mcp_oauth_clients`, que toda decisão de admissão lê do banco (nunca do AppConfig, cujo carregador de cache pode publicar um snapshot anterior a uma retirada); a atualização importa para ela o interruptor do nativo da 1.0.8 sem nenhum passo no terminal.

Todo redirecionamento de volta a um cliente carrega `iss` com o emissor (RFC 9207), inclusive na negação e em erros redirecionáveis; erros anteriores à validação do redirect continuam locais. Clientes sem documento de identidade próprio, como o Gemini CLI, são recusados com `invalid_client` enquanto o cliente nativo estiver desligado.

Disconnect pessoal, perda de elegibilidade (inclusive em lote ou por grupo), serviço desligado e conta desabilitada ou apagada invalidam imediatamente os tokens access/refresh e códigos pendentes (exceto no caso único de revalidação sem data capturada em transação alheia em que o usuário permanece elegível; ver [Permissões por grupo e ciclo de vida da política (1.1.0)](#permissões-por-grupo-e-ciclo-de-vida-da-política-110)). Reativar o serviço ou a elegibilidade não restaura credenciais antigas; conecte novamente. O Claude sai de `160.79.104.0/21`; se a proteção brute force do Nextcloud atrasar o endpoint de token, libere essa faixa. Basic + app password continua valendo para outros clientes.

## Conectar pelo ChatGPT e pelo Gemini CLI (OAuth)

Passos para o usuário, com a mesma URL e a mesma tela "Permitir", estão no README da raiz, nas seções ChatGPT e Gemini CLI. Resumo do que o servidor exige de cada um:

- **ChatGPT**: CIMD em `chatgpt.com`, aceito pela allowlist padrão. O documento real traz `token_endpoint_auth_methods_supported: [none, private_key_jwt]` e o singular `private_key_jwt`; o plural vence, e `none` está na lista, então o cliente é aceito como público.
- **Gemini CLI**: não publica documento de identidade, então usa o cliente nativo estático. O usuário cola o `client_id` exibido na seção do admin em `~/.gemini/settings.json` → `mcpServers.<nome>.oauth.clientId` e roda `/mcp auth`. O redirect `http://localhost:<porta>/oauth/callback` casa porque `RedirectUriMatcher` ignora a porta em loopback para o cliente nativo (RFC 8252 7.3).

- **Harnesses auto-hospedados**: um harness que aceita um `client_id` configurado à mão e retorna ao próprio domínio usa um cliente auto-hospedado que o administrador adicionou para ele. O `ClientMetadata::allowsRedirect` compara o `redirect_uri` pedido com a lista gravada daquele cliente de forma exata, porta incluída, também para entradas loopback (a porta livre é só do cliente nativo e dos CIMD); a tela de consentimento mostra o nome que o administrador deu ao cliente, diz que ele foi adicionado pela administração e mostra o host de retorno. Os passos estão no README da raiz.

`iss` é obrigatório porque o Gemini CLI rejeita retorno sem ele.

## Revogar

*Disconnect* na página pessoal bloqueia a próxima requisição MCP, inclusive com a mesma senha de app. A senha de app continua válida no Nextcloud e deve ser revogada em **Segurança**. Na mesma página, *Revogar* corta um cliente OAuth específico do próprio usuário. O administrador também pode remover a elegibilidade do usuário ou desativar o serviço; ambos valem na próxima requisição. No bloco **Conexões ativas**, o administrador revoga uma conexão OAuth específica, ou todas de um usuário, na hora; o usuário continua habilitado e pode entrar de novo.

## Teste manual após a instalação

```sh
URL=https://<instância>/apps/mcp/
AUTH='<usuário>:<senha-de-app>'
H='-H Content-Type:application/json -H Accept:application/json,text/event-stream'

curl -s -u "$AUTH" $H -d '{"jsonrpc":"2.0","id":1,"method":"initialize","params":{"protocolVersion":"2025-06-18","capabilities":{},"clientInfo":{"name":"curl","version":"1"}}}' "$URL"
curl -s -o /dev/null -w '%{http_code}\n' -u "$AUTH" $H -H 'MCP-Protocol-Version: 2025-06-18' -d '{"jsonrpc":"2.0","method":"notifications/initialized"}' "$URL"   # 202
curl -s -u "$AUTH" $H -H 'MCP-Protocol-Version: 2025-06-18' -d '{"jsonrpc":"2.0","id":2,"method":"tools/list"}' "$URL"
curl -s -u "$AUTH" $H -H 'MCP-Protocol-Version: 2025-06-18' -d '{"jsonrpc":"2.0","id":3,"method":"tools/call","params":{"name":"mcp_status","arguments":{}}}' "$URL"
```

Respostas esperadas:

| Situação | HTTP |
| --- | --- |
| Sem credencial, credencial inválida ou usuário desativado | 401 com `WWW-Authenticate: Basic` |
| Serviço desligado, usuário inelegível ou desconectado | 403 |
| Elegibilidade temporariamente incerta (a única fonte é um grupo em `needs_confirm`, ou uma revalidação pendente não pôde ser processada) | 503 |
| `Origin` de outro host | 403 |
| Faltando `Accept: application/json, text/event-stream` ou `Content-Type: application/json` | 406 |
| `MCP-Protocol-Version` desconhecida ou malformada: responde `UnsupportedProtocolVersionError` (`-32022`, `data.supported`). As versões legadas aceitas depois do `initialize` são 2025-03-26, 2025-06-18 e 2025-11-25; header ausente vale 2025-03-26, e no `initialize` o header é ignorado. Também dá 400 quando `MCP-Protocol-Version`, `Mcp-Method` ou `Mcp-Name` divergem do corpo (`-32020`). O motivo de cada 400 vai para o log em nível debug. | 400 |
| JSON inválido (`-32700`), lote ou envelope inválido (`-32600`) | 400 |
| Método desconhecido (`-32601`) ou parâmetros inválidos (`-32602`) | 200 com erro JSON-RPC |
| GET ou DELETE | 405 |
